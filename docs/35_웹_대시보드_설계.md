# 35. 웹·대시보드 설계

> **성격**: 이 문서는 **설계만** 다룬다. 언제 구현할지(Build Order ⑤ 구현 범위)는 `90` 리스크 42④가 이미 "지금 결정할 사안이 아니다"로 미뤄 뒀고, 여기서도 안 정한다.
> **전제 (이미 확정된 것, 여기서 다시 정하지 않는다)**:
> - 대시보드·웹은 **새 기능 번호를 받지 않는다** — 이미 있는 G1~G12 산출물을 재노출할 뿐, 새 산출물을 안 만든다(`33` D20).
> - **웹 ⊃ (대시보드 + G12)** — 대시보드(목록형 뷰)와 G12(대화형 질의)는 같은 웹 안에 있는 서로 다른 두 창구다(`34` 6절). 이 문서는 대시보드(목록형 뷰) 쪽을 설계한다. G12는 이미 스킬로 존재하므로 여기서는 "그 결과를 웹 화면 어디에 배치하는가"만 다룬다.
> - 기업이 실제로 요구한 것: *"해외 고객 발굴부터 영업까지 하는 대시보드, 업무 효율"* + *"담당자 컨택포인트까지 확보하는 대시보드"*(`13S` F9·F22). 이 두 문장이 아래 화면 우선순위를 정하는 근거다.
> - 사람이 **반드시** 개입하는 지점은 둘뿐이다 — U2(G5 발송 직전 승인, 무관용)와 U5(G7 회신 확인 이후 판단)(`34` 5절). 대시보드 설계에서 이 둘만 "액션 가능"이고 나머지는 전부 읽기 전용이다.

## 4. 화면 4 — 승인 대기함 (유일한 실제 "액션" 화면, 설계상 가장 중요)

여기가 **지금 마크다운 파일 편집으로 하던 일을 실제로 웹으로 옮기는 지점**이라 가장 신중하게 설계해야 한다.

### 4-1. 표시

`발송대기/{세그먼트ID}-{작성일}.md`를 파싱해 건별로: 수신 기업·문안 미리보기(제목+본문)·번역 검증 결과·법정 표시 4종 체크리스트·인용 근거. **`docs/50` 1-2절 "승인 화면 형태"가 정본**이므로, 그 절이 값을 바꾸면(예: R2 답이 와서 형태가 바뀌면) 이 화면도 같은 변경을 반영한다 — 문서 따로 화면 따로 두 곳을 고치는 사고(`90` 리스크 26류)를 만들지 않으려면, 화면이 보여줄 항목 목록 자체를 `docs/50` 1-2절에서 읽어오는 게 아니라 **그 절이 확정되면 화면 구현도 같은 커밋에서 함께 바꾼다**는 규칙만 여기 박아 둔다(설계 문서가 실시간으로 그 문서를 읽어 렌더링할 필요는 없다 — 그건 과설계다).

### 4-2. 승인/거부 버튼을 눌렀을 때 — 설계상 가장 중요한 결정

지금 승인은 "사람이 파일을 직접 열어 「승인 / 거부」 칸에 문자열을 적는 것"이고, 방금 만든 **H12(발송 승인 게이트)**가 그 편집을 Claude Code PostToolUse 훅으로 감지해 발송 모드를 자동으로 튼다. **이 메커니즘은 Claude Code 안에서 편집할 때만 작동한다** — 웹 버튼을 누르는 것은 Claude Code 밖의 사건이라 H12가 못 본다(`Harness/hook/h12-approval-send-gate.md`가 이미 이 한계를 명시해 뒀다).

**설계**: 웹의 승인 버튼은 두 가지를 **한 번에** 한다 — ① 파일의 「승인 / 거부」 칸을 그대로 채워 쓴다(형식은 기존과 동일하게 유지 — 나중에 누군가 Claude Code로 그 파일을 열어도 똑같이 읽힌다) ② **H12가 하던 것과 같은 후속 호출**(`/g5-제안메일제작발송 발송 <경로>`에 해당하는 발송 절차)을 웹 서버가 직접 트리거한다. 즉 웹이 존재하는 시점부터 **H12는 이 경로에서는 더 이상 필요하지 않다** — 웹 서버 자체가 "승인 편집 + 발송 트리거"를 원자적으로 묶어서 하기 때문이다(Claude Code 훅에 의존하지 않는, 더 직접적인 형태). H12는 "웹 없이 Claude Code만으로 운영하던 과도기"의 장치였다는 뜻이고, 이 문서가 그 전환을 명시적으로 기록해 둔다 — 나중에 웹을 실제로 만들 때 `docs/90` 리스크 43("승인이 웹으로 옮겨가면 재검토")을 여기로 연결해서 닫는다.

**거부 버튼**도 같은 파일에 「거부」+사유를 적는 것으로 끝난다 — 후속 호출 없음(발송 모드가 거부 건을 건드리지 않는 것은 지금과 동일).

## 5. 화면 6 — 회신함 (U5, 사람 판단 지점)

G7 레코드(`replies/*.md`)를 목록으로 보여주되, **버튼으로 뭔가를 실행하지 않는다** — U5는 "조회 또는 도구 밖 판단"이라 이 프로젝트의 실행 범위 밖이다(`34` 5절, 리스크 21 해소 결정과 같은 논리: 회신 수락 이후는 사람이 알아서 한다). 화면이 하는 일은 딱 하나, **"이 회신이 무엇을 요구하는지 한눈에 보이게"** 하는 것이다 — 8분류 라벨, 상대 요구·기한, 원문 링크. 이게 리스크 21이 "이미 충족돼 있다"고 판정한 그 요구사항의 실물 구현이다.

## 6. 화면 11 — 기준 카드: H9(기준 정합성 검토) 자동 검토

> **2026-08-14 추가, 같은 날 정정.** 처음엔 H9 로그를 `/qna`(질의응답) 목록 안에 배지로만 구분해 넣는 안으로 설계했으나, **사용자가 기각했다** — "질문에 쓰는 것과 같은 G12 기능을 이용하긴 하지만 결과물의 성격이 전혀 다르다"는 지적이었다. 사람이 묻는 질문(그때그때 다른 주제, 1회성)과 H9의 정합성 검토(특정 기준 파일 1개에 계속 쌓이는, 그 파일을 볼 때 같이 봐야 하는 상태)는 같은 화면에 같은 무게로 섞여 있으면 안 된다 — **기준 카드마다 자기 검토 결과를 데리고 있는 전용 화면**으로 다시 설계한다. H9 자체는 새 기능이 아니다(`33` D20과 같은 이유로 G/H 번호를 새로 받지 않는다) — 이미 있는 `기준/*.md`와 H9가 채우는 `질의응답로그/`를 웹에서 묶어 보여주는 것뿐이다.

**2026-08-14 재정정 — 읽기 전용에서 "제안→확인→적용"으로 확장.** 사용자가 웹에서 직접 수정까지 원한다고 확정했고, 수정 방식은 자연어 프롬프트를 LLM에 넘기는 쪽으로 정했다("레퍼런스 문서 수정 요청이니 문제없을 것 같다"). 다만 **LLM이 곧바로 파일을 고치게 두지 않는다** — 이 프로젝트가 이미 G5(제안 메일 발송)에서 "AI가 만들고 AI가 그대로 내보내는" 완전자동 경로를 브리프 위반으로 명시적으로 막은 것과 같은 리스크 형태이기 때문이다(판정 로직의 손잡이인 기준 카드를 한 줄 자연어로 즉시 덮어쓰면, 의도와 실제로 바뀐 것이 다를 때 확인할 자리가 없다). 그래서 G5의 승인 게이트와 같은 형태로 **제안(propose) → 사람이 diff 확인 → 적용(apply)** 3단계로 가른다 — 6-4절.

**적용 시점의 자동 검토는 H9(Claude Code PostToolUse 훅)에 기대지 않는다.** 이 화면의 파일 쓰기는 웹 서버 프로세스가 직접 하는 것이라 Claude Code의 Edit 도구를 거치지 않고, `docs/90` 리스크 60이 이미 "Git Bash로 직접 돌린 `claude -p` 경로에서 H9가 실제로 걸리는지 확인된 적이 없다"고 남겨 둔 것과 같은 불확실성을 새로 떠안을 이유가 없다. 대신 **웹 서버가 파일을 쓴 직후 G12 검토를 직접 호출한다** — H9와 완전히 같은 질문 템플릿을 재사용하므로(6-3절) 결과는 기존 판별 로직에 그대로 잡혀 이 화면에 뜬다. H9가 실제로 걸리는지 여부와 무관하게 검토는 항상 보장된다.

### 6-1. 데이터 접근 — 새 읽기 경로가 필요하다

`web/data_source.py`의 `data_root()`는 `specs/`로 고정돼 있고, `_safe_path`가 그 밖으로 못 나가게 막는다(`.env` 등 저장소 루트 파일 노출을 막으려고 project-critic이 2026-08-13 지적해 넣은 방어선). `기준/`은 `specs/`의 하위가 아니라 저장소 루트의 **형제 디렉터리**라 지금 구조로는 아예 못 읽는다. **`data_root()`를 저장소 루트로 넓히지 않는다** — 그러면 `.env`까지 다시 열린다. 대신 `기준/`만을 위한 별도의 좁은 읽기 경로(자체 루트 고정 + 자체 경로탈출 방어, 같은 `_safe_path` 패턴을 `기준/`에 한 벌 더)를 추가한다 — 노출 범위를 `기준/` 한 디렉터리로만 늘린다.

| 카드 1개 = 기준 파일 1개 | 파일명(예: `G2_세그먼트기준.md`) + **최근 자동 검토** 칸 |
| 최근 자동 검토 칸 | H9가 만든 로그 중 이 파일을 대상으로 한 것 중 **가장 최근 것**의 답변을 짧게(약 180자) 보여주고, 전체 로그로 가는 링크를 붙인다. 검토 이력이 아직 없으면 "아직 자동 검토 없음" |
| 어느 로그가 이 파일 것인지 판별 | H9 질문 템플릿이 `{파일명}의 내용이 다음과 같이 바뀌었다`로 시작하므로, 그 파일명 부분을 그대로 뽑아 대응시킨다(6-3 그대로 재사용 — 새 스키마 없음) |
| 액션 | **있음 — 자연어 수정 요청** (카드마다 입력창 1개, 6-4절) |

### 6-3. H9 로그 판별 — 6절(2026-08-14 최초 설계)에서 그대로 가져온다

판별 방법(질문 원문이 고정 템플릿으로 시작·끝나면 H9 기원)과 그 한계(사람이 우연히 같은 문장을 치면 오분류 — 무관용 아니라 감수)는 최초 설계 그대로 쓴다. 다만 **쓰이는 자리가 바뀐다**: `/qna` 목록의 배지가 아니라, 그 로그가 가리키는 기준 파일의 카드 안에 인라인된다. `/qna` 화면 자체는 손대지 않는다(H9 로그가 거기 섞여 나오는 것 자체는 사실이므로 막지 않되, 사람이 "이 기준 파일 지금 어떤 상태냐"를 물을 곳은 `/qna`가 아니라 이 화면이 된다).

### 6-4. 수정 흐름 — 제안(propose) → 확인 → 적용(apply)

| 단계 | 하는 일 | 안전장치 |
|---|---|---|
| **① 제안** | 사람이 카드 입력창에 자연어로 요청을 치면, 그 파일의 **현재 전체 내용을 프롬프트에 그대로 인라인**해서 LLM에 넘긴다(LLM이 `Read`로 직접 열게 하지 않는다 — 툴 왕복을 줄이고, 파싱해야 할 자유도도 줄인다). LLM은 `[변경 전]`/`[변경 후]`/`[설명]` 형식으로만 답하고 **파일을 쓰지 않는다** | 프롬프트 지침("쓰지 마라")만으로 끝내지 않는다 — `--disallowedTools=Write,Edit,MultiEdit,NotebookEdit,Bash,PowerShell,Agent`로 이 호출 자체의 쓰기 도구를 실제로 뗀다. 이유: `docs/90` 리스크 62가 이미 확인했듯 이 환경의 무인 실행에서 Write·Edit은 승인 없이 그냥 동작한다 — 말로만 막는 건 리스크 41류의 "거짓 안전장치"와 같다. **PowerShell·Agent까지 같이 막는 이유는 이 저장소의 스킬 12개 전부가 이미 같은 목록을 쓰기 때문**이다(`Bash`만 막으면 PowerShell로 우회하거나 `Agent`로 웹 권한 있는 다른 실행체에 위임하는 길이 남는다 — `g10-재수집판단/SKILL.md`가 이미 이 이유를 명문화해 뒀다). 이 호출은 이 저장소에서 **스킬을 거치지 않고 맨 프롬프트를 던지는 유일한 자리**라 `SKILL.md` frontmatter의 방어를 못 받으므로, CLI 플래그가 그 frontmatter와 최소한 같은 목록을 막아야 한다는 걸 2026-08-14 `change-reviewer` 검토가 지적해 정정했다 |
| **② 확인** | 화면이 변경 전/후를 나란히(빨강/초록 두 칸) 보여주고, LLM이 붙인 한 줄 설명도 같이 보여준다. 사람은 "적용" 또는 "취소"만 고른다 — 텍스트를 손으로 더 고치는 기능은 이번엔 안 만든다(고치고 싶으면 새 요청으로 다시 제안받는다) | 사람이 실제로 눈으로 diff를 보기 전에는 아무것도 안 바뀐 상태 그대로다 |
| **③ 적용** | "적용"을 누르면 **LLM을 다시 부르지 않는다** — 제안 단계에서 이미 받은 정확한 `old`/`new` 문자열로 평범한 텍스트 치환을 한다(Claude Code의 Edit 도구와 같은 유일성 규칙: `old`가 파일 안에 정확히 1번만 있어야 하고, 0번이면 "그 사이 파일이 바뀌었다", 2번 이상이면 "특정이 안 된다"로 되돌리고 다시 제안받게 한다). 쓴 직후 웹 서버가 **직접** G12 검토를 호출한다(H9에 기대지 않는 이유는 6절 본문) | 적용 자체는 결정적 텍스트 치환이라 **정상 UI 경로에서는** LLM이 제안 내용과 다른 걸 쓸 수 없다. **다만 `/criteria/apply`는 그 직전 `/criteria/propose` 호출과 토큰으로 묶여 있지 않다** — API를 직접 두드리면 제안을 거치지 않고 임의의 `old`/`new`를 적용할 수 있다(`old`가 파일에 정확히 1번 있어야 한다는 제약은 그대로 걸린다). 이건 숨겨진 구멍이 아니라 아래 문단의 의도된 절충이다. 검토 호출은 H9와 같은 템플릿을 재사용해 6-3절 판별 로직을 그대로 통과한다 |

**이 화면이 새로 여는 쓰기 경로는 딱 하나다** — `기준/` 디렉터리, 그것도 **이미 존재하는 파일의 본문 치환만** 허용한다(새 기준 파일 생성·`기준/` 아래 새 폴더 생성은 이 화면의 일이 아니다, 6-1절 `write_criteria`). CSRF 토큰 등 세션 보안은 이 화면만 특별 취급하지 않는다 — 현재 저장소의 다른 쓰기 액션(승인/거부)과 같은 수준을 그대로 따른다(둘 다 담당자 1인·로그인 없는 내부 도구라는 같은 전제 위에 있다).

## 7. 기술 구조 — 가볍게 간다

**원칙**: 이 프로젝트는 부트캠프 산출물이고 데이터가 전부 마크다운 파일이다. 별도 DB로 옮기지 않는다 — 옮기는 순간 "파일이 정본"이라는 이 저장소 전체의 원칙(`CLAUDE.md`)이 깨지고 이중 관리가 생긴다.

- **서버**: 요청이 올 때마다 해당 디렉터리의 `.md` 파일을 읽어 파싱해서 JSON으로 응답하는 얇은 API 하나. 캐싱·실시간 동기화 같은 건 지금 만들지 않는다(파일 몇십~몇백 개 수준에서 매 요청 다시 읽는 비용은 무시할 만하다).
- **프런트**: 화면 1~9는 표/카드 렌더링뿐이라 프레임워크 선택은 자유(React든 뭐든 무관 — 이 저장소가 강제하는 건 없다). 화면 4(승인)만 쓰기 액션이 있다.
- **인증**: 담당자 1인 체제로 보이므로(캐파·시간 등 운영 변수가 전부 "담당자" 단수로 서술돼 있다, `docs/50`) 지금은 로그인 없이 내부용으로 열어도 된다 — 필요해지면 그때 추가한다(과설계 금지).
- **G12 연동**: 대화창 컴포넌트 하나가 사용자 질문을 받아 G12 스킬 호출 결과를 그대로 표시한다. 새 파싱 로직 불필요 — `specs/질의응답로그/`에 이미 쌓이는 형식을 그대로 읽으면 된다.
