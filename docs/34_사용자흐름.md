# 34. 사용자 흐름 — 완성 시 실제로 어떻게 쓰이는가

> **이 문서의 위치**: `31_기능구조.md`가 기능 경계·입출력을 확정했다면, 여기는 **그 기능들을 사람이 실제로 언제·어떻게 마주치는가**를 시간 축으로 다시 배열한 것이다. 기능 정의·판정 기준은 여기서 새로 쓰지 않는다 — `31`·`specs/`·`기준/`을 참조만 한다. **여기서 확정하는 것은 진입점(무엇이 이 실행을 시작시키는가)과 그 뒤에 이어지는 리듬(어떤 성질로 도는가), 사람이 실제로 멈추는 지점이다.**
>
> **작성 시점(2026-08-06) 상태**: G1~G12 전 기능이 실행체를 갖췄다(`.claude/README.md`). 다만 "실행체가 있다"와 "실제 데이터로 검증됐다"는 다르다 — 상류 데이터가 아직 얇아 여러 기능이 「테스트 대기」다(`90` 3절). 이 문서는 구조를 그린다.
>
> **2026-08-06 재편**: 기존에는 리듬(조사/발송/반응) 하나로만 나눠져 있었다. 리듬은 "실행되는 동안의 성질"을 말하고, **진입점은 "그 실행이 왜 시작됐는가"를 말한다** — 서로 다른 질문이라 하나가 하나를 대체하지 않는다. 같은 리듬 안에도 진입점이 여러 개 섞여 있고(반응 리듬 하나에 Hook이 4개), 같은 성격(Hook)이 여러 리듬에 걸쳐 있어서, 진입점을 1차 분류축으로 세우고 리듬은 그 아래 종속시킨다.

---

## 0. 두 축 — 진입점과 리듬

- **진입점**: 사용자 요청(사람이 의도를 갖고 시작시킴) 또는 Hook(사건·시간이 자동으로 시작시킴). Hook으로 발생되는 것도 "사용"으로 본다 — 사람이 매번 타이핑하지 않아도 이 흐름을 쓰고 있는 것이다.
- **리듬**: 진입점이 실행을 시작시킨 뒤, 그 실행이 어떤 속도로 도는가 — 즉시 연쇄(조사)·정지점(발송)·비동기(반응).
- **진입점이 아닌 것**: 이미 나온 결과를 사람이 열어보는 것(예: G6 상태 파일, G7 회신 레코드, G10 재수집대상 파일을 직접 여는 것)은 진입점이 아니다 — 그 열람이 다른 실행을 다시 트리거하지 않기 때문이다. 그런 열람이 필요하면 정식 통로는 G12(아래 **U5**)다.

## 3. 진입점을 맞대어 보고 확인된 것

- **G1은 진짜 이중 입구다.** U1(요청)이 기본이고 H5(주기)가 보완이며, 둘 다 같은 목적지(G1 실행)로 모인다.
- **G5는 이중 입구가 아니다.** "제작"(H6, Hook만)과 "승인"(U2, 사용자만)은 서로 다른 두 진입점이다 — 하나의 함수를 두 경로로 부르는 게 아니라, 순서대로 이어지는 별개 단계다.
- **G11도 이중 입구가 아니라 순차 단계다.** "집계 실행"(H8, Hook)과 "제안 검토·기준 반영"(U4, 사람)은 같은 흐름의 앞뒤이지 같은 목적지로 모이는 두 경로가 아니다.
- **H12(발송 승인 게이트)와 웹 승인은 현재 공존하는 중복 경로다.** H12는 승인란을 Claude Code로 직접 고칠 때만 작동하도록 설계된 과도기 장치(`Harness/hook/h12-approval-send-gate.md`, `docs/35` 4-2절, `web/README.md` 23절)이고, 웹 승인이 실제 구현되면 웹 서버가 "승인 편집 + 발송 트리거"를 원자적으로 묶어 처리하므로 그 경로에서는 H12가 더 이상 필요하지 않다 — 웹 승인 도입 시 H12는 Claude Code 직접 편집 경로 쪽만 남는다. 둘 다 켜진 지금은 같은 승인 한 건에 H12와 웹 dispatch.py(`decide()`의 `trigger_dispatch`)가 모두 `claude -p`를 호출할 수 있는 구조이며, 중복 발송 방지는 G5 발송 모드의 멱등성에 맡긴다(아직 미확인 가정 — `docs/93_구현_검증대기.md` 등록). 이 관계는 `docs/35`가 정본이고 `docs/34`는 참조만 한다.
- **G6·G10은 사용자 요청 진입점이 없다.** 문서화된 "의도한 사용" 범위 안에 사용자가 직접 이 둘을 호출하는 경로가 없다 — 상태 판정·재수집 여부는 사람이 부르는 일이 아니라 시스템이 감지하는 일이라는 의도로 보이지만, 의도적으로 막아 둔 것도 적극적으로 열어 둔 것도 아니고 그냥 문서에 없다. **열린 질문으로 남긴다** — 필요해지면 그때 추가한다.
- **결과 열람은 어느 쪽 진입점도 아니다.** G6 상태·G7 회신 레코드·G10 재수집대상 파일을 사람이 여는 것은 전부 같은 종류(실행 결과로 남은, 필요하면 들여다볼 수 있는 데이터)다. 이 필요를 정식으로 받는 통로가 U5(G12)이고, 그래서 G12에 "criteria 정합성 검토"까지 얹을 때도 새 기능을 만들지 않고 이 진입점을 재사용했다(`33` D28).

## 4. 리듬으로 본 실행 성질

### 4-1. 조사 체인 (U1·H5 진입, 온디맨드/주기, 자동 연쇄)

| 순서 | 기능 | 범위 | 사람이 하는 일 |
|---|---|---|---|
| 1 | G1 대상 기업 발굴 | MVP | 없음 — 진입점(U1·H5)에서 이미 트리거됨 |
| 2 | G2 세그먼트화 | MVP | 없음 — G1 산출물로 자동 진행 |
| 3 | (부가) G3 적합도 평가 | 부가 | 없음 — 착수되면 자동으로 이 자리에 낌 |
| 4 | G4 연락처 확보 | MVP | 없음 — 세그먼트 대표 우선으로 자동 진행(부가 착수 시 적합도 우선으로 전환) |

**이 구간엔 사람이 멈출 이유가 없다.** 아직 아무것도 밖으로 나가지 않기 때문이다 — `31` 1-5절("컨택 기회 확보가 1순위")이 사전 검증 게이트를 없앤 것과 같은 이유로, 여기서 사람이 매번 승인할 필요는 없다.

### 4-2. 발송 (H6 진입, 필수 승인 게이트, 무관용)

| 기능 | 범위 | 사람이 하는 일 |
|---|---|---|
| G5 제안 메일 제작·발송 | MVP | **대표 문안 + 번역 검증 결과를 보고 승인한다(U2) — 승인해야만 발송된다** |

**이게 이 흐름 전체에서 가장 중요한 지점이다.** 승인 없이 발송되는 경로가 있으면 브리프 요구 ③(반자동)을 정면 위반한다(`specs/G5` 무관용 성공 기준 1번). 오케스트레이터가 "타임아웃 시 자동 승인" 같은 걸 넣으면 안 되는 이유가 여기 있다 — 8절 참조.

### 4-3. 반응 (H1~H4 진입, 비동기, 기다려야 온다)

| 기능 | 범위 | 사람이 하는 일 |
|---|---|---|
| G6 발송 결과 판정 | MVP | 없음 — 바운스/무응답/회신 상태 자동 판정 |
| G7 회신 해석·정리 | MVP | 회신이 오면 원문+한국어 해석+분류가 남는다 — **필요하면 U5(G12)로 조회**, 다음 실무 행동은 도구 밖 판단 |
| (부가) G8 원인분석 | 부가 | 없음 — H10으로 G6 판정에 바로 이어 자동 실행, 재시도 가치高는 G9로 넘어감 |

**G7 다음은 이 프로젝트 밖이다.** 기업이 직접 그렇게 말했다 — *"담당자와 접촉이 성립됐을 때는 아마 대응이 좀 필요하잖아요… 보내기에 집중하기보다는 그분들과 관계를 형성해 나가는 부분에 집중할 것"*(`13S` F16). 미팅·견적·계약은 설계하지 않는다(`31` G7절).

### 4-4. 부가 확장의 사람 개입 (U3·U4, H7·H8·H11 진입)

| 기능 | 리듬 | 사람이 하는 일 |
|---|---|---|
| G9 사람 접촉 위임 브리프 | 큐(H11, 주 1회) | 브리프를 보고 사람이 직접 접촉(주변·협력사, U3) — 찾은 연락처는 G4로 되돌아감 |
| G10 재수집 판단 | 주기(H7) | 없음 — 무엇을 다시 열지는 자동 판단, 결과가 G1·G4로 되돌아감 |
| G11 반응 집계·기준 조정 | 주기(H8) → 검토(U4) | **조정 제안을 검토·승인한다 — 승인해도 자동 반영되지 않고, 승인 후 별도 작업으로 `기준/`에 반영한다**(`specs/G11` 도구 권한: G2·G3 쓰기 불가) |

## 5. 사람이 실제로 멈추는 지점 — 요약

전체 흐름에서 사람이 **반드시** 개입하는 지점은 둘뿐이다.

1. **U2 — G5 발송 직전 승인** — 무관용, 건너뛸 수 없음
2. **U5 조회 또는 도구 밖 판단 — G7 회신 확인 이후** — 이 흐름의 종점, 이후 판단은 도구 밖

부가 기능이 붙으면 늘어난다 — U3(G9 위임 처리, 선택적·큐가 있을 때만), U4(G11 검토, 승인해야 의미가 생김). U1은 "반드시"는 아니다 — H5가 대신 트리거할 수 있기 때문이다.

## 6. 대시보드·웹과의 관계

기업이 요구한 "대시보드"(`13S` F9·F22)는 위 산출물(G1+G2+G4, 부가 시 G3)을 한 화면에서 보는 것이다. 웹으로 구현되든 다른 형태든, 화면 자체는 새 산출물을 만들지 않으므로 별도 기능 번호를 받지 않는다(2026-08-05 확정). **웹이라는 그릇 안에 대시보드(목록형 뷰)와 G12(U5, 대화형 질의)가 함께 담긴다 — 웹=대시보드가 아니라 웹 ⊃ (대시보드 + G12).**

## 7. 추가 사항 — 오케스트레이터에 반영할 내용

> **2026-08-05 — 반영 완료.** 오케스트레이터가 `.claude/agents/run-orchestrator.md`로 만들어졌고 아래 5개 항목이 그 정의에 반영됐다(근거 `33` D23). **이 절은 이제 대기 항목이 아니라 그 에이전트가 매 실행 참조하는 요구 목록이다** — 여기 진입점·리듬·정지점이 바뀌면 `run-orchestrator`가 이긴 것이 아니라 이 문서가 이긴다.
>
> 아래 5개가 실제로 어떤 형태로 반영됐는지: 2번(자동 재개 금지)은 **금지 문장이 아니라 「정지점에서 대기하지 않고 종료」**로 구현됐다 — 대기 루프가 없으면 타임아웃이 걸릴 자리 자체가 없다. 그 대가로 상태를 파일에 남긴다.

사용자 흐름(1~6절)이 실행 구조에 요구하는 것 — G12 자체 설계와는 별개다.

1. **오케스트레이터는 단일 선형 체인이 아니라 진입점별로 다르게 취급해야 한다.** U1·H5가 여는 조사 체인은 즉시 연쇄 실행 가능하지만, H1~H4가 여는 반응은 발송과 시간차가 있어 별도 트리거로 재개돼야 하고, H6~H8이 여는 부가 확장은 주기 실행이라 온디맨드 체인에 끼워 넣으면 안 된다.
2. **U2(G5 승인 게이트)는 "자동으로 재개되지 않는 정지점"으로 구현해야 한다.** 타임아웃 등으로 오케스트레이터가 자동 진행시키면 반자동 무관용 요건(`specs/G5`)을 위반한다.
3. **H4(G7 정정 신호)를 배선에서 빠뜨리면 안 된다.** 수신거부 의사 → 발송금지 목록(G4·G5가 다음 발송 전 반드시 참조), 자동응답 판정 → G6 상태 정정. 단방향 파이프로만 짜면 누락된다(`31` 3-3절 고아검사에서 실제로 한 번 누락됐던 이력).
4. **U5(G12)는 파이프라인 스텝이 아니라 별도 진입점으로 배선해야 한다.** 조사 체인·발송·반응 어느 순서에도 끼워 넣지 않는다. 읽기 전용이라 다른 스텝의 완료를 기다릴 필요가 없다.
5. **사람이 실제로 멈춰서 기다리는 지점은 두 곳(U2, G7 이후 판단)뿐임을 오케스트레이터의 상태 모델에 명시적으로 표현해야 한다.** 부가 기능(U3·U4)이 붙기 전까지는 이 둘 외에 "사람 대기" 상태를 만들 필요가 없다.
