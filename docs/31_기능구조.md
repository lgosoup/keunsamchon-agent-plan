## 1. 전체 목표

### 1-1. 기업이 파는 것 — 이것이 플로우의 출발점

**Clo.D AI-Studio**: 제품 또는 제품 사진만 있으면, 상대적으로 저렴한 가격에 **AI로 모델을 생성해 광고용 사진·영상을 만들어 준다.**

이 한 문장이 타겟 조건을 그대로 결정한다.

| 조건 | 왜 이 조건인가 | 우선순위 |
|---|---|---|
| **제품이 있다** | 제품이 없으면 만들 것이 없다. 제품 사진이 있으면 최적이고, 없으면 제품 실물을 받아 직접 촬영한다 | **필수** |
| **커머스가 있다** | 광고 사진·영상을 쓸 자리가 있다는 뜻. 커머스를 운영하면 제품 사진도 이미 존재한다 | **높음** |

> `30` ④의 "이미지 전문성 전문/비전문"이 1차 판별축이었던 구조는 여기서 교체된다. 1차는 **제품·커머스 보유**다 (`13S` H4).

### 1-2. 왜 막혀 있는가 — 기업의 실제 상태

기업은 해외에 AI-Studio를 쓰게 하고 싶다. 그런데,

- **직접 일본에 가서 해봤고, 어려웠다.** 시장 조사부터 잠재고객 수집까지 쉽지 않았다 (`13S` F10)
- **협력사 의존적이다.** 협력사를 통해야 진행되고, 협력사는 자기가 경험한 영역만 다룬다 (`13S` F10)
- **지금은 일본 협력사의 시간이 나지 않아 진행 자체가 멈춰 있다**

→ **그래서 이 접촉 과정을 AI로 반자동화 루틴으로 만든다.** 사람을 없애는 것이 아니라, **협력사 일정에 묶여 멈추는 구조를 푸는 것**이 목적이다.

### 1-3. 왜 일본인가

| 이유 | 내용 |
|---|---|
| 거리 | 가장 가깝다 |
| K문화 적합도 | 높다 |
| **이미 접점이 있다** | 기업에 일본 협력사가 존재한다 |

**일본 하나로 만들고, 성공하면 다른 국가로 확대한다.** 따라서 플로우는 일본에 맞춰 구체화하되, **국가가 바뀌면 갈아 끼울 부분과 그대로 쓸 부분을 구분해 설계한다.**

### 1-4. 목표 문장

> **일본에서, 제품과 커머스를 가진 기업을 찾아 연락 가능한 담당자에 도달하고, 세그먼트별로 설계된 제안 메일을 일본어로 보내고, 그 반응을 사람이 판단할 수 있는 형태로 되돌리는 — 반자동 접촉 플로우를 설계한다.**

### 1-5. 브리프 3대 요구와의 대응

| 브리프 요구 | 이 플로우에서 담당하는 기능 |
|---|---|
| 잠재고객 **자동 탐색·목록화** | F1 → F2 → F3 → F4 |
| **고객 특성에 맞춘** 제안 메일 | **F6 세그먼트 그룹화 + F7 그룹별 메일 원형** — 맞춤의 단위가 개별 기업이 아니라 **세그먼트**다 |
| **반자동** 작성·발송 | 사람 필수 개입 3지점 (2-4절). 완전자동 발송 경로 없음 |

> **`30` ⑤ (Clo.D / AI-Studio 매칭)이 여기서 대체된다.** 제안할 서비스가 AI-Studio 하나로 좁혀지면 "둘 중 무엇을 제안할지" 판별은 성립하지 않는다. 브리프 요구 ②를 담당하는 것은 이제 **세그먼트별 메일 유형 설계**다. `30` ⑤와 ⑦의 "Clo.D / AI-Studio 적합도 판별" 단계는 폐기 대상이다.

## 2. 기능 구조

### 2-1. 전체 흐름

```
[1단계] 대상 확보
  F1 기업 후보 수집  ──→  F2 세그먼트 분류  ──→  F3 적합도 평가
                                                      │
                                              F4 연락처 탐색
                                                 ┌────┴────┐
                                            확보 │         │ 미확보
                                                 ▼         ▼
[2단계] 접촉                                              F5 사람 위임 큐 ◀──┐
  F6 그룹 대표 메일 집중 제작 (사람+AI)                        (연락처 경로)   │
        │                                                                    │
        ▼                                                                    │
  F7 그룹 전체 메일 생성 (AI)                                                │
        │                                                                    │
        ▼                                                                    │
  F8 번역 검증  ──→  F9 승인·발송 (사람 승인 필수)                           │
                          │                                                  │
[3단계] 반응              ▼                                                  │
                    F10 발송 결과 판정                                       │
              ┌───────────┼───────────┐                                      │
         회신 │      무응답 │     주소오류 │                                  │
              ▼            ▼            ▼                                    │
        F11 회신 처리    F12 무응답·미도달 원인 분석                          │
        (번역·분류)           │                                              │
              │               └── 재시도 가치 높음 ──→ F13 사람 위임 브리프ㅡ┘
              ▼                                        (재시도 경로)
        사용자에게 한국어로
```

**F5와 F13은 출력 형태가 같다.** 둘 다 *"사람이 직접 움직여야 하는 기업"*을 사용자에게 넘기는 창구이고, 유입 경로만 다르다 — F5는 **연락처를 못 찾은 경우**, F13은 **보냈는데 안 통한 경우**. 하나의 위임 큐로 두고 유입 사유만 구분한다.

**F3(적합도 평가)은 두 곳에서 재사용된다.** F5·F13 모두 *"사람이 시간을 들일 가치가 있는가"*를 적합도로 판단한다. 그래서 적합도 평가를 F1·F2에 섞지 않고 **독립 기능**으로 뺀다.

### 2-2. 기능 단위 정의 — 입력 / 출력 / 담당

#### 1단계 — 대상 확보

| | 기능 | 입력 | 출력 | 담당 |
|---|---|---|---|---|
| **F1** | 기업 후보 수집 | 국가(일본), 타겟 조건(제품 보유 / 커머스 보유), 탐색 소스 | 기업 후보 목록 — 기업명·URL·취급 품목·**제품 사진 보유 여부**·**커머스 보유 여부**, 각 항목의 **관찰 근거**(어디서 봤는지) | AI |
| **F2** | 세그먼트 분류 | F1 목록 | 세그먼트 정의 + 각 기업의 소속 + 분류 근거. 분류 축은 **품목 종류·기업 규모** 등 *"메일을 같은 방식으로 써도 될 것 같은가"* 기준 | AI 제안 → 사람 확인 |
| **F3** | 적합도 평가 | F1 관찰 결과 + F2 세그먼트 | 기업별 적합도 + **그 판단의 근거**. 사람 개입 가치를 재는 공통 척도 | AI |
| **F4** | 연락처 탐색 (딥서치) | 기업별 F1 결과 | 기업별 연락처 상태 — **유효 이메일 확보 / 미확보**, 확보 시 출처, 미확보 시 **어디까지 찾아봤는지** | AI |

- **F4의 "유효"는 존재 여부가 아니라 의미 있는 창구인지**다. 담당자·제안 접수처에 닿는 주소인지를 본다. 일반 문의 폼만 있는 경우와 담당자 주소를 확보한 경우를 구분한다.
- **F1의 근거 칸이 뒤 단계 전체의 재료다.** 메일 본문의 "귀사의 공개 정보에서 이런 점을 확인했다"와 F13 브리프의 "우리 회사와 맞는 이유"가 모두 여기서 나온다. 근거 칸이 비면 맞춤 근거도 빈다.

#### 2단계 — 접촉

| | 기능 | 입력 | 출력 | 담당 |
|---|---|---|---|---|
| **F5** | 사람 위임 큐 (연락처 경로) | F4 미확보분 + F3 적합도 + F1 근거 | 대시보드 항목 — 이 기업이 어떤 곳인지, 적합도와 그 근거, 어디까지 찾아봤는지 | AI가 재료 준비 → **사람이 판단·실행** |
| **F6** | 그룹 대표 메일 집중 제작 | 세그먼트 1개 + **그 그룹 대표 기업 1곳**의 조사 결과 | 그 그룹의 **메일 원형**(일본어) — 구성·논리·톤 | **사람 + AI 집중 협업** |
| **F7** | 그룹 전체 메일 생성 | F6 원형 + 그룹 내 각 기업의 F1 결과 | 기업별 메일 초안(일본어) | AI |
| **F8** | 번역 검증 | F7 초안 + 원 의도(한국어) | 검증 결과 — 의도와 어긋난 지점 | AI (+ 사람 최종 확인) |
| **F9** | 승인·발송 | 검증 통과 초안 | 발송 기록 | **사람 승인 → 자동 발송** |

- **F6이 이 플로우의 품질 결정 지점이다.** 그룹당 한 번만 사람이 집중해서 만들고, 그 결과를 AI가 그룹 전체로 확장한다. **사람의 노력을 기업 수가 아니라 그룹 수에 비례하게 만드는 것**이 이 구조의 핵심이다.
- **F5는 사람이 "주변·협력사를 돌려" 연락처를 찾는 경로다.** 협력사 의존을 없애는 게 목표지만(1-2절), 공개 정보로 닿지 않는 곳은 사람이 움직이는 게 맞다. 다만 **적합도가 높은 곳에만** 그 시간을 쓴다.

#### 3단계 — 반응

| | 기능 | 입력 | 출력 | 담당 |
|---|---|---|---|---|
| **F10** | 발송 결과 판정 | 발송 기록 + 메일 서버 응답 | 상태 분류 — **회신 / 무응답 / 주소 오류** | AI |
| **F11** | 회신 처리 | 회신 메일(일본어) | **한국어 번역·요약** + 회신 성격 분류 + 번역 검증 결과 | AI → 사람 |
| **F12** | 무응답·미도달 원인 분석 | 무응답·주소오류 기업 + 발송 이력 + F1 근거 | 원인 가설(무시 / 도달 실패 / 조사 오류) + **재시도 가치 판단** | AI |
| **F13** | 사람 위임 브리프 (재시도 경로) | F12에서 재시도 가치 높은 기업 | 사용자용 브리프 — **① 이 기업이 어떤 곳인지 ② 우리 회사와 잘 맞는 이유와 그 근거** | AI 작성 → **사람 판단·접촉** |

- **F13의 설계 목적은 "사용자가 시간을 크게 들이지 않고 그 기업을 알게 되는 것"이다.** 자료를 넘기는 게 아니라 **판단할 수 있는 상태로 넘기는 것**이 출력 조건이다.
- **F12는 원래 브리프에 없던 기업 직접 요구다** (`13S` F24). "그냥 안 읽은 건지, 주소가 틀린 건지"를 구분해 달라는 것.

### 2-3. 횡단 요구 — 언어와 검증

플로우 전체를 관통하므로 기능 단위와 별도로 둔다.

| | 요구 | 대상 기능 |
|---|---|---|
| **X1** | **발신은 일본어**로 한다 | F6, F7 |
| **X2** | **수신(회신)은 일본어 → 한국어로 해석**해 사용자에게 보여준다 | F11 |
| **X3** | **번역이 정확한지 검증한다 — 보낼 때도, 받을 때도** | F8, F11 |

**X3이 가장 위험한 요구다.** 회사 이름으로 나가는 메일이 의도와 다른 뜻이 되거나, 회신을 잘못 해석해 사용자가 잘못 판단하면 플로우 전체의 신뢰가 무너진다. **"AI가 번역하고 AI가 검증한다"는 같은 실수를 두 번 반복할 수 있으므로**, 검증 방식은 Spec 단계에서 별도로 설계한다 (역번역 대조 / 사람 검수 지점 등).

### 2-4. 사람이 반드시 개입하는 지점 — "반자동"의 정의

기업은 `12` Q6의 (a)/(b)/(c)를 고르지 못했고 판단을 우리에게 위임했다(`13S` U12). 이 플로우가 그 답이다.

| # | 개입 지점 | 왜 사람인가 |
|---|---|---|
| 1 | **F2 세그먼트 확인** | 어떤 기업들을 "같은 방식으로 대해도 되는가"는 사업 판단이다 |
| 2 | **F6 그룹 대표 메일 제작** | 메일의 논리와 톤을 여기서 결정한다. 그룹당 한 번, 집중해서 |
| 3 | **F9 발송 승인** | 브리프가 요구한 반자동. 완전자동 발송 경로를 두지 않는다 |
| 4 | **F5·F13 위임 큐 처리** | 공개 정보로 닿지 않는 곳에 사람이 직접 움직이는 경로 |

→ **`12` Q6 기준으로는 (b)에 가장 가깝고, F6이 (b)보다 앞선 단계에 사람을 한 번 더 넣은 형태다.** 이 정의를 기업에 실물로 보여주고 승인받는다 (`13` 7-2절).

## 3. 국가가 바뀌면 무엇이 바뀌는가

일본에서 성공하면 확대한다는 전제(1-3절)를 설계에 반영해 둔다.

| | 국가가 바뀌면 |
|---|---|
| **그대로 쓴다** | F2 분류 방식 · F3 적합도 평가 구조 · F6→F7 확장 구조 · F10~F13 반응 처리 · 사람 개입 4지점 |
| **갈아 끼운다** | F1 탐색 소스 · F4 연락처 관행 · X1·X2 언어 · 콜드메일 규제 |

→ **플로우 자체가 산출물이고, 일본은 그 첫 적용 대상이다.**

## 4. 이 문서가 무효화하는 기존 설계

| 기존 | 상태 |
|---|---|
| `30` ⑤ Clo.D / AI-Studio 매칭 로직 | **폐기.** F2+F6(세그먼트별 메일 유형)이 대체 |
| `30` ⑦ 파이프라인의 "Clo.D / AI-Studio 적합도 판별" 단계 | **폐기.** F3(적합도 평가)로 성격이 바뀜 |

## 5. 내가 이해한 것 중 확인이 필요한 지점

플로우 자체는 이해했고, 아래 5개는 Spec 단계로 넘어가기 전에 갈라야 한다.

| # | 확인할 것 | 왜 갈리는가 |
|---|---|---|
| **1** | **F2의 초기 분류와 F6의 메일 그룹화가 같은 분류인가?** | 같으면 기능 하나, 다르면 분류 축이 둘이다(정리용 축 / 메일 유형 축). 지금은 **하나로 보고 F2에서 정의해 F6이 그대로 쓰는 것**으로 정리했다 |
| **2** | **"읽음 / 안 읽음"을 분기 조건으로 쓸 수 있는가?** | 읽음 추적은 픽셀 방식이라 차단·규제로 정확도가 낮다(`90` 리스크 3). 확실히 아는 것은 **주소 오류(바운스)와 회신 유무**뿐이다. 그래서 F10을 **회신 / 무응답 / 주소 오류 3분기**로 정리했다 — 말씀하신 "봤지만 회신 없음 = 무시한 것과 같게 본다"와 결과적으로 일치한다. 읽음 여부는 보조 신호로만 |
| **3** | **F6의 "사람"이 일본어를 다룰 수 있는가?** | 메일 원형을 사람이 만드는데 일본어 판단이 안 되면, F6의 사람 개입이 한국어 기획까지만이고 일본어는 전부 AI가 된다. X3 검증 설계가 여기서 갈린다 (`12` Q13 미확인) |
| **4** | **F5·F13을 하나의 위임 큐로 합쳐도 되는가?** | 출력 형태가 같아 합치는 것으로 정리했다. 사용자가 두 경로를 다르게 다루고 싶다면 분리한다 |
| **5** | **F3 적합도를 F5와 F13에서 같은 척도로 쓰는가?** | 같으면 기능 하나. 다르면 "연락처 찾을 가치"와 "재시도할 가치"를 따로 정의해야 한다 |
