# 50. 실사용 도입 설계 — 운영 변수의 단일 출처 (2026-08-03 갱신)

> **이 문서의 성격**: `01` 다음 액션과 `90` 리스크 22가 요구한 산출물이며, **2026-08-03부터 이 프로젝트의 운영 변수(캐파·승인 시간·발송 상한 등) 값을 갖는 유일한 문서다.** 담당자·캐파·운영비의 정확한 값은 기업 답(`12` Q9·Q10·Q11·Q14) 대기 중이지만, **가정치로 지금 작성한다** — 가정을 명시하고 근거를 붙이면 답이 온 뒤에는 숫자만 바꾸면 된다.
> **다른 Spec·기준 카드는 이 값을 복제하지 않고 이 문서를 참조만 한다.** 같은 값(예: 캐파)이 여러 곳에 각자 "(미확인)"으로 박혀 있으면 값이 왔을 때 한 곳만 고치고 나머지가 썩는다 — 실제로 이 사고가 `90` 리스크 26(가격 구조 확인 후 8곳 중 일부 미갱신)으로 한 번 났다. 참조 방식·규칙은 `CLAUDE.md` 5절 "그 외"에 정본으로 있다(`31`에 별도 절을 만들지 않기로 했다 — 이유는 `33` D16).
> **가정과 사실을 섞지 않는다.** 아래 표의 값 중 출처가 없는 것은 전부 "가정"이고, 기업 답이 오면 즉시 갱신 대상이다.
> **비공개 처리 준수**: 회사가 제공한 비공개 가격표의 구체 수치는 여기서도 인용하지 않는다(`CLAUDE.md` 6절 예외 조항). 손익 비교는 조건문 형태로만 서술한다.
> **⚠ 기본 원칙 (2026-08-03) — 상한은 기본값이 아니라 예외다.** 기업 상황(바쁨, 컨택 자체가 안 됨)상 "일단 되기만 하면 좋다"가 우선이다 — **값이 없으면 무제한으로 처리하고, 실제로 감당 못 할 만큼 나오면 그때 후보 목록(`candidates/후보목록.md`)에서 필요한 만큼만 골라 쓴다.** 미리 컷오프·배분 알고리즘을 만들어 두지 않는다 — 그 자체가 근거 없는 검증 게이트를 만드는 것과 같다.

### 1-1. 일일 발송 상한 (예외) — 왜 여기만 미리 상한을 두는가

메일을 하루에 너무 많이 보내면 수신 메일 서버가 그 발송 주소를 스팸으로 낙인찍는다. 한번 찍히면 **이번 프로젝트 메일뿐 아니라, 같은 도메인으로 나가는 회사의 기존 업무 메일(동대문 거래처와 주고받는 메일 등)까지 함께 막히거나 스팸함으로 들어간다.** "많이 나오면 나중에 줄이자"가 통하지 않는다 — 한번 도메인 평판이 깎이면 그 프로젝트와 무관한 기존 업무까지 다치고, 복구도 오래 걸린다. 이 회사는 SNS에서 같은 유형의 사고(계정 정지)를 이미 겪었다(`13S` F12). `CLAUDE.md` 5절의 무관용 판별법("어겼을 때 누가 무슨 손해를 보는가")을 적용하면 — **회사의 기존 사업이 손해를 본다.** 비용 비대칭에 해당하므로 예외로 둔다.

| 항목 | 값 | 처리 방식 |
|---|---|---|
| 발송 전용 주소 | 회사 메인 도메인과 분리된 서브도메인/별도 주소를 쓴다 (`12` Q15) | **구체적인 등록·연결 절차는 `specs/README.md`의 "발송 도메인 준비" 절 참조** — 실제 발송 도구(MCP 등)에 등록·연결하는 일회성 설정 작업이라 여기(운영 변수)가 아니라 그쪽(설정 안내)에 둔다 |
| **하루 최대 발송 건수** | `(미확인 — 지금은 낮은 값으로 시작)` | **사람이 직접, 수동으로 늘려간다.** 자동 램프업(1일차 5통→2일차 10통…) 같은 코드 로직을 만들지 않는다 — 그런 코드는 초기 며칠만 쓰이고 그 뒤로는 버려지는 코드가 된다. 대신 **이 표의 숫자를 담당자가 상황을 보며 직접 올린다**(오늘 10 → 문제 없으면 다음 주 20 → …). 이 프로그램을 처음 쓰는 동안은 어차피 사람이 직접 파악하며 조절해야 하므로, 숫자를 손으로 조절하는 것이 자동 램프업 코드보다 낫다 |
| 발송 서비스 | `(미확인)` | `12` Q15 답 대기 |

**이 숫자가 다른 문서가 참조하는 유일한 "진짜 상한"이다.** `specs/G5`의 발송 실패표는 이 값이 채워지면 그 값만큼만 처리하고, 없으면(지금 상태) 발송하지 않고 대기한다 — **①~③과 달리 값이 없다고 무제한으로 밀어붙이지 않는다.** 인프라 제약은 없다고 가정하면 실제로 사고가 나기 때문이다.

**결과 판정 (2026-08-03 기준 갱신)**: 3곳 전부 조건 1~3(제품·커머스·업종)은 O. **옛 조건 4(한국 진출 희망)는 전부 X였으나, 이 조건은 2026-08-03 완전히 삭제됐다**(`기준/G1_기업판정기준.md` 변경 이력 — 기업 후속 확인 + 이 실측 0/3이 근거가 됐다). **현행 3조건 기준으로는 3곳 모두 「포함」**이다 — 옛 조건 4로 「제외」 처리된 것은 지금은 유효하지 않다.

**측정의 한계 (정직하게 밝힌다)**:
- **웜 스타트(런 2·3)는 실제 배포 조건을 과소평가한다.** `specs/G1` 「실행체 경계」가 "기업 1곳 = 컨텍스트 1단위"를 요구하므로, 실제로는 기업마다 독립된 컨텍스트에서 두 정본 문서를 다시 읽어야 한다 — 런 1(콜드 스타트, 9분)이 실제 단가에 더 가깝다.
- 웹 요청 횟수는 회사마다 다르다(2~4회) — 회사개요 페이지 구조에 따라 갈린다.
- **정확한 토큰·API 비용은 측정하지 않았다.** 실측한 것은 웹 요청 횟수와 벽시계 시간뿐이다 — 이 이상의 금액 환산은 추정치이므로 만들지 않는다.
- **이 실측은 2026-08-03 관찰 항목 축소 이전 기준이다.** Honeys의 4회·4분 43초는 O6(자본금·종업원수 등 회사개요)까지 확인하려 하위 페이지에 들어간 값인데, 그 관찰(ⓒⓓⓔ)은 이후 완전히 삭제됐다. 현행 3조건·O6 2항목(상품 개수·채널 수) 기준으로 다시 재면 이 값보다 **빨라진다** — 불리한 쪽으로 틀린 숫자라 손해는 아니지만, 지금 표의 값은 현행 절차의 값이 아니다. 현행 기준의 재측정은 `90` 다음 액션(옛 3건 재판정)을 본다.
