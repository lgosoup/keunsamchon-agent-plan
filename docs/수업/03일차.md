## 2. 원하는 작업 정의

**문제**
> 2. 원하는 작업 정의
> ● 반복 작업:
> ● 오래 걸리는 이유:
> ● 최종적으로 받고 싶은 결과물:

**요구 형식**: 항목 3개 채우기

**앞 문제와의 연결**: 1번에서 정한 프로젝트(판정 작업)를 그대로 이어받는다.

### 답변

**반복 작업**: 일본 기업 한 곳의 공개 페이지(홈페이지·상품 목록·회사 개요 등)를 열어, 제품 사진이 있는가 / 온라인으로 살 수 있는가 / 업종이 패션·뷰티·푸드인가 / 한국 진출을 원하는 신호가 있는가 — 이 네 가지와 참고 항목(회사 규모, 광고 메일 거부 표시 등)을 관찰·기록한다. 그 관찰값만으로 포함/제외/판정 불가를 계산한다. 기업 한 곳 = 작업 한 단위이며, 새 명단이 들어오거나 일정 기간이 지나면 같은 기업을 다시 본다.

**오래 걸리는 이유**:
1. 판정에 필요한 정보(제품 사진 유무, 구매 버튼·가격 표시, 업종, 한국 진출 흔적, 광고 메일 거부 문구)는 명단에 실려 있지 않다 — 기업의 여러 페이지를 직접 열어야 나온다.
2. 판정 기준이 글로 고정돼 있지 않으면 사람마다 결론이 갈리고, 갈렸다는 사실조차 기록에 남지 않는다.
3. 조건에 안 맞아 버릴 기업도 다 열어본 뒤에야 결론이 나므로, 버릴 기업에도 통과할 기업과 같은 시간이 든다.
4. "봤는데 조건에 안 맞다"와 "아예 못 봤다"(사이트 오류, 로그인 요구, 렌더링 문제 등)를 같은 칸에 적으면, 나중에 다시 볼 때 어느 쪽을 다시 열어야 하는지 알 수 없어 처음부터 다시 보게 된다.

**최종적으로 받고 싶은 결과물**: 기업 한 곳당 관찰값 아홉 개 항목(값 또는 물음표+사유, 근거와 함께) + 그 값만으로 계산한 결론(포함/제외/판정 불가)과 사유가 담긴 파일 1개.

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| 반복 작업의 범위와 단위 | 기업 발굴 기능의 설계서 — 목표·입력 절 |
| "검증을 거치지 않아 못 썼다" | 2026-07-30 설명회에서 기업이 직접 말한 실패 사례 |
| 오래 걸리는 이유 네 가지 | 같은 설계서의 제약 절 + 판정 기준 카드의 "못 봤을 때" 규칙 |
| 결과물 형식 | 같은 설계서의 출력 형식 절 |

### 미확인

- 회사가 지금 이 검증 작업을 실제로 어떤 순서·빈도로 하고 있는지는 여전히 확인된 적이 없다.

## 3. Harness 목표

**문제**
> 3. Harness 목표
> ● 입력:
> ● 처리 과정:
> ● 출력:
> ● 성공 기준:

**요구 형식**: 항목 4개 채우기

**앞 문제와의 연결**: 2번에서 정의한 반복 작업을 그대로 하네스로 만든 것이다.

### 답변

**입력**: 기업명(원어) + 국가(일본) + 공개 페이지 URL 1개 이상(홈페이지 하나만 있어도 성립하며, 나머지 페이지는 그 안에서 링크를 따라 찾는다). 기업을 여러 곳 한꺼번에 넣지 않는다.

**처리 과정**:
1. 주어진 URL과 그 안에서 찾은 페이지를 읽어 관찰 항목 아홉 개를 채운다(관찰층) — 값이 안 보이면 물음표+사유로 남기고 규칙을 스스로 만들지 않는다.
2. 관찰값만으로 조건 4종의 충족 여부(O/X/물음표)를 계산하고, 최종 결론(포함/제외/판정 불가)과 사유를 낸다(규칙층).
3. 기업 1곳당 파일 1개로 저장하고, 아래 성공 기준으로 스스로 점검한다 — 걸리는 항목이 있으면 그 자리에서 고친다.

이 처리 과정은 **정해진 순서로 돌고 실패하면 멈추는 형태**로 만들었다 — 페이지를 못 열면 그 기업을 그대로 종료하고, 스스로 다른 경로를 찾거나 애매한 값을 O·X로 밀어 넣지 않는다. 규칙 없는 경계를 실행체가 자기 판단으로 채우면 그 판단이 어디에도 기록되지 않기 때문이다.

**출력**: 관찰값 아홉 개 항목(값+근거 또는 물음표+사유) + 그 값만으로 계산한 결론과 사유가 담긴 파일 1개.

**성공 기준**: 산출물 1건(파일 1개)마다 아래를 확인한다.
- [ ] 관찰 항목 모든 칸이 값+근거 또는 물음표+사유로 채워져 있다 (빈 칸 0건)
- [ ] 근거에 어느 페이지를 봤는지와 무엇을 봤는지가 함께 있다
- [ ] 관찰한 사실을 적는 칸에 판정 문장이 섞여 있지 않다
- [ ] 결론을 지우고 관찰값만으로 다시 계산해도 같은 결론이 나온다
- [ ] "못 봤다"가 "봤는데 아니다"와 다른 칸에 사유와 함께 있다
- [ ] 제외로 판정된 건에는 어느 조건 때문인지 적혀 있다
- [ ] 수집일과 수집 주체가 적혀 있다
- [ ] 일본어 원어 표기가 번역으로 덮어써지지 않았다
- [ ] 개인 이름·개인 SNS 계정·개인 직통 연락처가 기록되지 않았다
- [ ] 광고 메일 거부 표시가 있으면 원문과 위치가 함께 적혀 있다

**절차 자체를 점검할 때(매 건이 아니라 가끔)**: 같은 기업을 두 번 판정해도 결론이 같은가.

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| 입력·처리 과정·출력의 형태 | 기업 발굴 기능의 설계서 — 입력·제약·출력 형식 절 |
| "정해진 순서로 돌고 실패하면 멈춘다"는 실행 형태 선택 | 같은 설계서 — 실행 형태 절 |
| 성공 기준 열 개 항목 + 표본 검사 | 같은 설계서의 성공 기준 절 |

## 4. 사용할 Agents

**문제**
> 4. 사용할 Agents
> Agent 이름 | 역할 | 맡길 일

**요구 형식**: 표 (열 이름 고정: Agent 이름 / 역할 / 맡길 일)

**앞 문제와의 연결**: 3번의 처리 과정을 누가(무엇이) 실행하는지를 채운다.

### 답변

| Agent 이름 | 역할 | 맡길 일 |
|---|---|---|
| **없음 — 별도 서브에이전트를 두지 않았다** | — | — |

이 판정 작업에는 독립된 서브에이전트를 별도로 만들지 않았다. 이유는 3번 답에서 이미 처리 과정을 **"정해진 순서로 돌고 실패하면 멈추는 형태"**로 선택했기 때문이다 — 이건 상황에 따라 스스로 경로를 바꾸는 에이전트형 자율성이 필요 없는 작업이라는 뜻이다. 그리고 서브에이전트를 만들 때 반드시 정해야 하는 네 가지 경계(입력 형식 / 출력 형식 / 도구 권한 / 독립 컨텍스트)는 이미 3번 답의 하네스 목표 자체에 못 박혀 있다 — 입력은 기업 1곳분, 출력은 정해진 아홉 항목짜리 파일 1개, 도구는 공개 페이지 읽기와 결과 파일 쓰기까지만, 컨텍스트는 기업 1곳당 독립이다. 이 네 가지를 실행 절차 자체(5번의 Skill)에 실어 보냈으므로, 그걸 다시 감싸는 별도 에이전트를 하나 더 두면 같은 경계를 두 곳에 적는 셈이 된다.

**반례를 세워봤다** — "그래도 실행할 때 실제로 움직이는 주체 하나는 있어야 하지 않나?" 맞다. 다만 그 주체는 5번 답의 Skill 자신이다. 이 하네스에서는 "Agent(무엇이 실행하는가)"와 "Skill(어떤 절차로 실행하는가)"이 분리되지 않고 하나로 합쳐져 있다 — Skill 하나가 그대로 실행 단위이기도 하다.

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| 처리 과정을 "정해진 순서, 실패 시 중단" 형태로 선택했다는 사실 | 3번 답변, 기업 발굴 기능의 설계서 — 실행 형태 절 |
| 네 가지 경계(입력·출력·도구권한·독립 컨텍스트)가 이미 설계서에 정의돼 있다 | 같은 설계서 — 실행체 경계 절 |
| Skill이 그 경계를 그대로 실행한다 | 관찰·판정 절차 카드(5번 답) 본문 |

|---|---|---|
| 일본 기업 관찰·판정 | 기업 1곳의 공개 페이지 URL을 받아, 정해진 아홉 개 관찰 항목을 채우고 그 값만으로 계산한 결론(포함/제외/판정 불가)까지 담은 파일 1개를 내놓는다. 아직 규칙이 안 정해진 경계(예: 온라인으로 살 수는 있는데 구매 버튼 없이 가격만 있는 애매한 경우)는 스스로 규칙을 만들지 않고 물음표+사유로 남긴다 | 후보 명단에서 기업 한 곳을 검증해야 할 때마다 불러 실행한다. 실사용 중 애매한 경계를 만나면 그 산출물을 보고 판정 기준 카드를 그 자리에서 고치는 데도 쓴다 — 사람이 처음부터 완벽한 기준을 만들어 두는 대신, 실제로 써보면서 다듬는 방식이다 |

이 Skill을 만들어도 되는 조건 두 가지를 확인했다 — (a) 기업이 바뀌어도 똑같은 절차가 반복되는가 (b) 사람이 매번 "이 항목을 어떻게 볼지"를 같은 방식으로 판단해야 하는가. 둘 다 그렇다고 확인했으므로, 즉흥으로 매번 새로 판단하게 두지 않고 절차로 고정했다.

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| Skill의 설명·조건 두 가지 | 관찰·판정 절차 카드 본문 + Skill로 고정할지 판단하는 규칙 |
| 애매한 경계를 물음표+사유로 잠정 처리한다는 규칙 | 판정 기준 카드 — "규칙을 주지 않는다, 실행체는 잠정으로 물음표 처리"절 |

## 6. 전체 작동 흐름

**문제**
> 6. 전체 작동 흐름
> ● 사용자 입력:
> ● 목표 분석:
> ● Agents 선택:
> ● Skills 실행:

> ● 최종 결과물 생성:

**요구 형식**: 항목 6개 채우기

**앞 문제와의 연결**: 3~5번 답을 시간 순서로 다시 배열한 것이다.

### 답변

- **사용자 입력**: 기업명(원어) + 국가(일본) + 공개 페이지 URL 1개 이상.
- **목표 분석**: 이 기업이 타겟 조건 4종을 전부 충족하는 후보인지를 판정하는 것임을 확인한다.
- **Agents 선택**: 하지 않는다 — 4번 답대로 이 하네스에는 별도 서브에이전트가 없고, 아래 Skill이 그 역할을 겸한다.
- **Skills 실행**: "일본 기업 관찰·판정" 절차를 호출해 관찰층을 채우고 규칙층을 계산한다.
- **결과 검증**: 나온 파일을 3번 답의 성공 기준 열 개 항목으로 자체 점검한다. 걸리는 항목이 있으면 그 자리에서 고쳐 다시 채운다 — 걸린 채로 내지 않는다.
- **최종 결과물 생성**: 기업 1곳 = 파일 1개로 저장한다. 다음 후보가 들어오면 같은 흐름을 처음부터 반복한다(독립 컨텍스트라 앞 기업을 보며 받은 인상이 새어 들지 않는다).

|---|---|
| 흐름 6단계 전체 | 3~5번 답변을 그대로 시간 순서로 재배열 |

## 7. 최종 결과물 & 검증 기준

**문제**
> 7. 최종 결과물 & 검증 기준
> ● 결과물 형식:
> ● 분량:
> ● 반드시 포함할 내용:
> ● 제외할 내용:
> ● 검증 기준:

**요구 형식**: 항목 5개 채우기

**앞 문제와의 연결**: 3번의 출력·성공 기준을 결과물 관점에서 다시 정리한다.

### 답변

**결과물 형식**: 기업 1곳 = 파일 1개. 관찰한 사실(관찰층)과 그 사실로 낸 결론(규칙층)을 같은 파일 안에서 시각적으로 갈라 적는다.

**분량**: 확정된 상한은 없다 — 한 번에 몇 건까지 만들어도 되는지는 회사의 월 제작 캐파(아직 회사에 확인하지 못함)에 달려 있어서, 그 값이 오기 전까지 상한을 정하면 근거 없는 숫자가 된다. 다만 절차 자체가 실제로 도는지는 이미 세 곳을 대상으로 실측해 봤다 — 8번 답 참고.

**반드시 포함할 내용**: 관찰 항목 아홉 개가 값+근거 또는 물음표+사유로 채워진 것, 결론(포함/제외/판정 불가)과 그 사유, 수집일과 수집 주체, 일본어 원어 표기.

**제외할 내용**: 개인 이름·개인 SNS 계정·개인 직통 연락처(법인 공개 창구만 기록한다).

**검증 기준**: 3번 답의 성공 기준 열 개 항목과 같다 — 산출물 1건마다 그 열 개를 확인하고, 절차 자체를 점검할 때는 같은 기업을 두 번 돌려도 결론이 같은지를 본다.

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| 결과물 형식·포함/제외 내용 | 기업 발굴 기능의 설계서 — 출력 형식·제약 절 |
| 분량 상한이 월 제작 캐파에 매여 있다 | 미결정·리스크 목록 — "확인 후 채울 것"으로 등록된 미확인 값 |
| 실제로 세 곳을 실측했다는 사실 | 아래 8번 답 |

### 미확인

- 목록 규모의 상한(월 제작 캐파)과 하한(최소 수주 금액)은 기업에 물어야 나온다.

## 8. 실행 결과

**문제**
> 8. 실행 결과
> ● 실행 횟수:
> ● 확인한 오류:
> ● 수정한 내용:
> ● 남은 보완점:

**요구 형식**: 항목 4개 채우기

**앞 문제와의 연결**: 5번의 Skill을 실제로 돌려본 결과를 옮긴다.

### 답변

**실행 횟수**: 실제 일본 기업 3곳(패션 도매·소매 3곳, 전부 실재 URL)을 대상으로 절차를 그대로 돌렸다. 원래 목표는 5곳이었으나 시간 제약으로 3곳만 마쳤다.

| 곳 | 페이지 열람 횟수 | 소요 시간 | 비고 |
|---|---|---|---|
| 1곳 | 2회 | 9분 4초 | 첫 실행 — 절차 문서를 처음부터 정독하고 시작함(콜드 스타트) |
| 2곳 | 2회 | 4분 0초 | 절차 문서를 이미 파악한 상태에서 시작함(웜 스타트) |
| 3곳 | 4회 | 4분 43초 | 회사 규모 항목(자본금·종업원수)까지 확인하려 하위 페이지를 더 열어 요청 수가 늘어남 |

**확인한 오류**: 절차 자체의 결함은 아니지만, 설계 가정과 다른 관측이 하나 나왔다 — 판정 대상으로 삼은 "한국 진출을 원하는 신호" 네 가지가 세 곳 모두에서 하나도 관찰되지 않았다(0/3). 이 조건을 그대로 필수 조건으로 두면, 통과하는 후보 자체가 거의 안 나올 위험이 있다는 뜻이다.

**수정한 내용**: 표본이 세 곳뿐이라 이번 관측만으로 판정 기준 카드를 바로 고치지는 않았다. 대신 "이 조건을 필수에서 빼고 참고 항목으로 낮출지"의 판단을, 회사에 직접 확인하는 절차로 넘겼다 — 관찰이 안 되는 것을 필수 조건으로 계속 두면 전부 판정 불가로 몰리기 때문이다.

**남은 보완점**:
1. 목표 5곳 중 2곳을 아직 못 봤다.
2. 판정 기준 카드가 아직 실사용 경험이 적어(3곳) 애매한 경계가 더 있을 수 있다 — 처음부터 완벽한 기준을 만들어 두기보다, 앞으로 후보를 계속 판정하면서 애매한 경계를 만날 때마다 그 자리에서 기준 카드를 고쳐나가는 방식으로 다듬을 것이다.

*결과물 분량 상한(월 제작 캐파)은 여기 다시 올리지 않는다 — 7번 답에서 이미 "값이 없어도 지금 이 판정 작업 자체는 막히지 않는다"고 정리했고, 여기서 또 "남은 문제"로 올리면 같은 문서 안에서 서로 다른 말을 하는 것이 된다.*

### 근거

| 주장 | 무엇에서 나왔는가 |
|---|---|
| 실행 횟수·페이지 열람 횟수·소요 시간 | 일본 기업 3곳 실측 기록 (2026-07-31) |
| "한국 진출 희망" 신호 0/3 관측 | 같은 실측 기록 |
| 표본 부족으로 카드를 바로 고치지 않고 기업 확인 절차로 넘겼다는 판단 | 도입 설계 문서의 가정 명시 절 + 판정 기준 카드의 "관찰률 0이면 내려간다" 절 |
| 목표 미달성(5곳 중 2곳)과 기준 카드를 실사용하며 다듬는다는 방침 | 실측 기록 + 판정 기준 카드 자신의 성격 규정("사람이 읽고 고치는 기준", 실제로 판정해 보고 애매했던 문장을 그 자리에서 고친다) |
