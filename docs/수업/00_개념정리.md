## 1. 전제 — LLM은 무엇을 하는 기계인가

| 항목 | 내용 |
|---|---|
| 하는 일 | 지금까지 나온 단어들을 보고 **다음에 올 가장 그럴듯한 단어를 고르는 것**. 사실을 조회하는 기계가 아니다 |
| 그럴듯한 것(plausible) | 자리와 맥락에 맞아 보이는 출력. 사실이라는 보장도, 논리적으로 옳다는 보장도 없다 |
| 검증된 것(verified) | 그 출력이 신뢰할 수 있는 자료와 일치하는지 확인했거나, 사람이 미리 만든 논리적 점검 항목을 통과한 것 |
| Temperature | 높이면 확률이 낮은 단어까지 고르므로 다양·창의적이 되지만 **틀릴 가능성도 같이 올라간다** |

**Hallucination이 생기는 이유는 이 전제에서 바로 나온다.** LLM은 사실 검증기가 아니라 그럴듯한 답을 만드는 기계이므로, **형식은 완벽하고 내용은 틀린** 출력이 자연스럽게 나온다(존재하지 않는 논문의 제목·저자·식별번호를 정확한 서식으로 적어내는 것이 전형).

→ 그래서 **plausible과 verified를 가르는 장치를 사람이 밖에서 만들어 붙여야 한다.** 이것이 하네스가 필요한 근본 이유다.

## 2. 통제할 수 있는 레버는 둘 — 모델과 입력

- 모델을 더 비싼 것으로 바꾸는 것은 레버지만 우리가 만들 수 있는 게 아니다.
- **입력(무엇을 어떤 구조로 주는가)은 우리가 만든다.** 그리고 비싼 모델을 써도 출력 품질은 결국 입력이 결정한다.
- 따라서 개선 노력은 **입력 쪽**에 넣는다.

## 3. 세 가지 활용 방식 — Chatbot / Workflow / Agent

| 구분 | Chatbot | Workflow | Agent |
|---|---|---|---|
| 흐름을 누가 정하는가 | 사람이 그때그때 | **사람이 미리 설계** | AI가 스스로 판단 |
| 도구 사용 | 없음 | 미리 정해둔 것만 | 필요에 따라 선택 |
| 오류가 나면 | 사람이 다시 물어본다 | **파이프라인이 멈춘다** | 스스로 재시도할 수 있다 |
| 맞는 작업 | 일회성 질문·답변 | **경로를 예상할 수 있는** 복잡한 작업 | 경로를 예상하기 **어려운** 복잡한 작업 |

**셋 중 무엇으로 만들 것인지를 먼저 정해야 오류 처리 설계가 결정된다.** 같은 시스템을 Workflow로 보면 실패 시 중단이고 Agent로 보면 재시도인데, 이걸 정하지 않으면 실패 경로가 설계에서 빠진다.

## 4. 하네스 엔지니어링의 정의와 세 가지 붕괴 지점

**정의**: AI가 원하는 결과를 낼 확률을 높이도록 **입력·구조·검증을 설계하는 행위.** 프롬프트를 원하는 답이 나올 때까지 고쳐보는 것(Trial & Error)과 다르다 — 목표·절차·검증 기준을 **먼저** 정하고 같은 절차를 반복해 **일관된** 결과를 얻는 쪽이다.

**Breaking Points — 하네스가 없으면 무너지는 세 지점**

| 붕괴 지점 | 무슨 일이 일어나는가 | 무엇으로 막는가 |
|---|---|---|
| **막연한 요청** | 목표가 불명확하니 결과도 불명확해진다. 의도와 다른 일반적인 답이 나온다 | **Spec** — 목표와 성공 기준을 명확히 적는다 |
| **단일 에이전트 과부하** | 하나에 너무 많은 맥락이 들어가면 품질이 떨어지고 조건이 누락된다 | **Subagent** — 작업을 단계로 쪼개 독립 단위로 만든다 |
| **검증 없는 실행** | 결과가 맞는지 확인하는 단계가 없어 오류가 그대로 통과한다 | **검증 단계** — 파이프라인 마지막에 두고 완료 전 반드시 거친다 |

## 5. 하네스 6요소

| 요소 | 무엇인가 |
|---|---|
| **Spec** | 목표·범위·성공 기준. 모든 설계의 출발점 |
| **Skill** | 반복 작업의 절차 카드 |
| **Subagent** | 단계별 독립 실행 단위 |
| **Workflow** | 실행 순서와 데이터 흐름 |
| **Hook** | 자동 실행 트리거 |
| **Checklist** | 완료의 기준 |

## 6. Build Order — 만드는 순서

```
① Spec → ② Skill → ③ Subagent → ④ Workflow → ⑤ Hook → ⑥ Checklist
```

각 단계는 다음 단계에 **재료를 넘긴다.** Spec은 Skill에 절차를 짜는 기준(무엇을 어디까지, 언제 완료인지)을 넘기고, Subagent는 Workflow에 **실행 단위**를 넘긴다. 순서를 지키는 이유는 뒤 단계가 앞 단계의 산출물 없이는 정해지지 않기 때문이다 — 성공 기준이 없으면 Checklist를 쓸 수 없고, 실행 단위가 없으면 실행 순서를 그릴 수 없다.

**뒤에서부터 만들면 무엇이 잘못되는가**: Workflow·Hook부터 만들면 "돌아가기는 하는데 무엇이 완료인지 아무도 모르는" 시스템이 된다. 판정 기준 없이 자동 실행만 붙은 상태이므로 Breaking Point 1(막연한 요청)과 3(검증 없는 실행)을 동시에 안게 된다.

## 7. 요소별 세부 규칙

### 7-1. Spec — 6요소, 성공 기준을 가장 먼저 쓴다

| 요소 | 답해야 하는 질문 |
|---|---|
| 목표 | 무엇을 만드는가 |
| 맥락 | 왜 이 작업이 필요한가 |
| 범위 | 어디까지 포함이고 어디부터 제외인가 |
| 제약 | 지켜야 할 조건은 무엇인가 |
| 출력 형식 | 어떤 형태로 나와야 하는가 |
| **성공 기준** | 언제 "완료"인가 — **예/아니오로 판단 가능하게** |

**성공 기준을 가장 먼저 쓰는 이유**: 성공 기준이 구체적이어야 목표를 정의할 수 있고, 목표가 정의돼야 결과를 기준과 대조해 검증할 수 있다. 순서를 뒤집으면 만든 다음에 기준을 만들게 되고, 그러면 기준이 결과에 맞춰진다.

**"예/아니오로 판단 가능하게"가 요구하는 것**: 세거나 대조해서 답이 갈리는 형태여야 한다. "품질이 좋은가"는 판단 불가이고, "다섯 문장인가 / 근거를 원문에서 확인할 수 있는가"는 판단 가능하다.

### 7-2. Skill — 언제 불러오고 무엇을 하는가

| 구성 | 역할 |
|---|---|
| Frontmatter (전면 메타데이터) | 이 Skill을 **언제 불러와야 하는가**를 정의 |
| Instructions (본문 실행 지침) | 실제로 따라가는 **실행 순서** |

**`description`의 두 역할** — ① **자동 로딩 트리거**: 어느 Skill을 쓸지 에이전트가 스스로 읽고 판단하는 근거가 된다. ② **책임 범위 선언**: 무엇을 담당하는지 못박아 Skill 사이의 충돌을 줄인다.

**단일 책임 원칙**: 하나의 Skill은 하나의 상황을 담당한다. "A를 작성하거나 기존 A를 검토할 때 쓴다"처럼 **서로 다른 상황을 or로 묶으면** 트리거가 흐려지고 책임이 겹친다. "A를 새로 작성해야 할 때 쓴다"가 옳은 형태다.
※ 순차적으로 이어지는 절차(먼저 X하고 그 결과로 Y한다)를 하나의 Skill에 담는 것은 or로 묶은 것과 다르다 — 상황이 하나이기 때문이다.

### 7-3. Subagent — Context Rot과 네 개의 경계

**Context Rot**: AI는 Context Window라는 한정된 공간에서 정보를 처리하므로, 맥락이 길어지면 **앞에서 정한 것이 뒤에서 밀려난다.** 대표 증상은 초반에 정한 성공 기준을 확인하지 않고 "완료"라고 보고하는 것. 해결 구조는 작업을 나눠 **Subagent마다 별도의 Context Window**를 쓰게 하는 것이다.

**Subagent의 네 경계** — 이 넷이 정해지지 않은 것은 Subagent가 아니다.

| 경계 | 내용 |
|---|---|
| 입력 형식 | 무엇을 어떤 형태로 받는가 |
| 출력 형식 | 무엇을 어떤 형태로 내놓는가 |
| 도구 권한 | 어떤 도구까지 쓸 수 있는가 (읽기만 / 쓰기 포함 / 외부 전송 등) |
| 독립 컨텍스트 | 다른 에이전트와 맥락을 공유하지 않는가 |

### 7-4. Workflow — 두 패턴

| 패턴 | 정의 | 쓰는 경우 |
|---|---|---|
| **체이닝** | 앞 Subagent의 출력이 다음 Subagent의 입력이 되는 순차 연결. 입·출력 **파일**로 잇는다 | 앞 단계의 결과를 처리해 다음 단계로 넘겨야 할 때 |
| **조건 분기** | 중간 결과에 따라 이후 실행 경로가 갈리는 구조 | 경로가 갈려야 할 때 (예: 대상이 0건이면 본 작업을 건너뛰고 다른 처리로 간다) |

### 7-5. Hook — 왜 Skill로는 안 되는가

Skill로 대체되지 않는 이유가 둘이다.

1. **에이전트가 건너뛸 수 있다.** Skill은 에이전트가 스스로 판단해 불러오는 것이므로, 필요 없다고 판단하면 실행되지 않는다.
2. **Workflow 밖을 잡지 못한다.** Skill은 결국 대화·Workflow 안에서 동작하므로, 그 밖에서 발생하는 사건은 걸리지 않는다.

Hook은 **사건(시각·업로드·상태 변화)에 묶여 강제로 실행**되므로 이 두 구멍을 막는다.

### 7-6. Checklist — 성공 기준의 실행 가능한 버전

Checklist는 단순한 확인 목록이 아니라 **Spec의 성공 기준을 실제로 세고 대조할 수 있게 바꿔 놓은 것**이다. 성공 기준이 "근거가 원문에 있는가"라면 Checklist는 "각 항목을 원문과 대조했는가"가 된다. 그래서 Checklist는 Spec 없이 쓸 수 없고, 미충족 항목을 찾아내 수정으로 되돌리는 입력이 된다.

## 8. 검수자 마인드셋 세 원칙

| 원칙 | 내용 |
|---|---|
| ① "맞겠지"가 아니라 "확인해야지" | LLM의 답은 정답을 보증하지 않으므로 사람이 검증한다 |
| ② 성공 기준을 미리 정한다 | 목표가 확실하지 않으면 과정이 좋아도 원하지 않는 결과가 나온다 |
| ③ 검수 단계를 자동화한다 | 생성 속도를 사람이 따라갈 수 없으므로 검수도 속도를 맞춰야 한다 |

**LLM-as-a-Judge**: 한 에이전트의 산출물을 **다른 에이전트가 기준에 따라 평가**하게 하는 패턴. ③을 구현하는 대표 수단이다(예: 조사 에이전트의 결과를 다른 에이전트가 출처 신뢰도 기준으로 검사).

## 9. Trial & Error와의 차이 — 한 줄 요약

| | Trial & Error | Harness Engineering |
|---|---|---|
| 하는 일 | 원하는 결과가 나올 때까지 프롬프트를 고쳐 반복 | 목표·절차·검증 기준을 먼저 정하고 같은 절차를 반복 |
| 남는 것 | 그때 통한 프롬프트 하나 | 다음에도 같은 결과를 내는 **구조** |
