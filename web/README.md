# web/ — 대시보드 구현체

`docs/35_웹_대시보드_설계.md`(설계)를 실제로 구현한 것. 여기는 구현 결정과 실행 방법만 담고, 화면 구조·근거는 `docs/35`를 본다(중복 안 함).

## 스택 (2026-08-10 결정)

- **Node.js가 이 개발 환경에 설치돼 있지 않아** `docs/35` 6절이 예로 든 것과 다르게 **Python(Starlette + Uvicorn + Jinja2 + markdown-it-py)**로 만들었다 — 전부 이미 설치돼 있어 추가 설치 없이 바로 됨. `docs/35`의 "가볍게 간다" 원칙(DB 없이 파일 직접 읽기, 캐싱 없음)은 언어와 무관하게 그대로 지켰다.
- 프런트는 서버 렌더링(Jinja2 템플릿) + 최소 vanilla JS(승인 버튼 AJAX, G12 채팅창) — SPA 빌드 파이프라인 없음.

## 데이터 소스

- **운영 기본값**: `specs/`(저장소 루트) — `docs/35`가 지정한 정본.
- **자동 테스트용**: `web/test-fixtures/`(이 폴더 전용, 실제 `specs/`를 절대 건드리지 않는다). 환경변수 `DASHBOARD_DATA_ROOT`로 전환.

## 실행

```
DASHBOARD_DATA_ROOT=<repo>/specs python web/app.py
```

## 승인 액션(A안) 구현

`docs/35` 4-2절대로 — 승인 버튼 클릭 시 서버가 파일에 「승인」을 쓰는 것과 발송 트리거를 한 요청 안에서 같이 처리한다. 발송 트리거는 `DISPATCH_MODE` 환경변수로 `mock`(파일 로그만 남김, 기본값·테스트용)과 `real`(`claude -p "/g5-제안메일제작발송 발송 ..."` 실제 호출)을 가른다 — 자동 테스트가 매번 실제 Claude Code 세션을 재귀 호출하면 느리고 비용도 들고 권한 프롬프트에 걸릴 수 있어서다.

## 테스트 (2026-08-11)

`web/test_playwright.py` — Playwright로 실제 브라우저를 띄워 화면 11개 전부 로드·콘솔 에러 없음을 확인하고, 승인 대기함은 **실제로 버튼을 클릭**해 파일 기록·발송 로그까지 검증하며, G12 챗봇도 실제로 질문을 입력해 답변을 확인한다. `python web/test_playwright.py` (서버가 `web/test-fixtures`를 가리키며 떠 있어야 한다).

**참고**: 이 세션엔 Playwright MCP가 연결돼 있지 않아 Playwright 파이썬 라이브러리를 직접 설치해 썼다 — 실제 브라우저(Chromium)로 조작한다는 목적은 동일하다.

테스트 중 발견해 고친 것:
- 후보 목록의 "후보 판정" 값이 안 뽑히던 정규식 버그
- 승인 대기함의 메일 제목이 안 뽑히던 정규식 버그(발송대기 파일은 "일본어 제목"+"件名:" 형식, 발송기록 파일은 "제목" 형식으로 서로 다름)
- 표 안의 `**굵게**` 마크다운이 그대로 별표로 보이던 것 → 표 렌더링 시 제거
- 상세보기(원문) 화면에서 마크다운 표가 안 그려지던 것 → `MarkdownIt` 프리셋을 표 지원이 없는 `commonmark`에서 `gfm-like`로 전환(linkify는 미설치라 비활성화)
- 세그먼트 화면에서 "세그 ID" 같은 좁은 헤더가 세로로 한 글자씩 줄바꿈되던 레이아웃 버그 → 헤더 `white-space: nowrap`

`specs/`(실 데이터, 대부분 화면이 비어 있음 — 실제 파이프라인이 그만큼만 진행됐다는 뜻)와 `web/test-fixtures/`(합성 데이터로 전 화면 채움) 양쪽에 대해 전부 200 응답 확인.
