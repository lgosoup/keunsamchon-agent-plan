# web/ — 대시보드 구현체

`docs/35_웹_대시보드_설계.md`(설계)를 실제로 구현한 것. 여기는 구현 결정과 실행 방법만 담고, 화면 구조·근거는 `docs/35`를 본다(중복 안 함).

## 스택 (2026-08-10 결정)

- **Node.js가 이 개발 환경에 설치돼 있지 않아** `docs/35` 6절이 예로 든 것과 다르게 **Python(Starlette + Uvicorn + Jinja2 + markdown-it-py)**로 만들었다 — 전부 이미 설치돼 있어 추가 설치 없이 바로 됨. `docs/35`의 "가볍게 간다" 원칙(DB 없이 파일 직접 읽기, 캐싱 없음)은 언어와 무관하게 그대로 지켰다.
- 프런트는 서버 렌더링(Jinja2 템플릿) + 최소 vanilla JS(승인 버튼 AJAX, G12 채팅창) — SPA 빌드 파이프라인 없음.

## 데이터 소스

- **운영 기본값**: `specs/`(저장소 루트) — `docs/35`가 지정한 정본.
- **자동 테스트용**: `web/test-fixtures/`(이 폴더 전용, 실제 `specs/`를 절대 건드리지 않는다). 환경변수 `DASHBOARD_DATA_ROOT`로 전환.

## 실행

```
DASHBOARD_DATA_ROOT=<repo>/specs python web/app.py
```

## 홈 하단 — 성과 섹션 (2026-08-13 추가)

`docs/35` 2-1절 — "할 일" 카드(위) 옆에 "지금까지 만든 것"을 KPI 타일 4개 + 파이프라인 막대(퍼널) + 연락처 구성 막대로 보여준다. `parsers.pipeline_stats()`가 계산하고, 색은 기존 상태 팔레트(good/warning/serious)를 그대로 재사용했다(`dataviz` 스킬 — 이미 검증된 팔레트 재사용).

**실 데이터(`specs/`)로 이 기능을 만들다가 기존 `parse_contacts()`·`parse_candidates()`의 실물 파싱 버그 4건을 발견해 같이 고쳤다** — `web/test-fixtures`를 기준으로 짠 정규식이 실제 스킬 산출물의 표기 관례와 갈려 있었다(발송대기·집계 파서가 이미 겪은 것과 같은 종류의 드리프트):

- `parse_contacts()` 기업 식별자 — 헤딩이 "id 먼저"(테스트픽스처 관례)가 아니라 "연락처 확보 — id"(id가 뒤, 실물 22건 중 20건)라 전부 "연락처"로 잘못 읽혔다 → 본문의 `**기업 식별자**` 필드로 조인하도록 변경(`_sent_company_ids`와 같은 원칙)
- `parse_contacts()` 상태 — 실물은 `## 상태: [확보]`(볼드 없음)인데 정규식이 `**[확보]**`(볼드)만 받아 20/22건이 "미상"으로 샜다 → 볼드 유무 모두 허용
- `parse_contacts()` 등급·연락처 값 — 실물은 목록 형식(`- **유효 등급**: 일반`)인데 정규식이 표 형식(`| **유효 등급** | **일반** |`)만 받았다 → 두 형식 다 허용
- `parse_candidates()` — `candidates/후보목록.md`에 낀 "## 종합 — ..." 요약 섹션을 실제 후보처럼 세어 총 조사 건수가 2건 많게 잡혔다 → `후보 판정:` 줄이 없는 섹션은 건너뛴다

고친 뒤 `/contacts` 화면 실물 22건 전부 기업 식별자·상태·등급이 정상 표시됨을 확인(Playwright 스크린샷, 라이트·다크 양쪽).
