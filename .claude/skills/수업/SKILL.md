# 수업 — 하네스 엔지니어링 문제를 이 과제로 답한다

## 이 스킬이 하는 일

수업에서 배운 하네스 엔지니어링 개념을 문제 형태로 받아, **일반론을 설명하지 않고 이 저장소의 실물로 답한다.** 산출물은 `docs/수업/<일차>.md` 한 파일이며, 여기에 그날의 문제와 답변이 순서대로 쌓인다.

**재료는 이 저장소지만 독자는 이 저장소를 모른다** — 수업 제출물이므로 파일 경로·문서 번호 없이, 그 자체로 읽히게 쓴다 (절대 규칙 5).

이 스킬의 목적은 학습 기록이 아니다. **수업 개념을 이 과제의 하네스(`CLAUDE.md`·`docs/` 체계·서브에이전트·스킬·게이트)에 실제로 착지시키는 것**이 목적이고, 문제-답변 파일은 그 착지 과정의 기록이다. 답만 쓰고 저장소가 그대로면 이 스킬은 절반만 실행된 것이다.

## 인자 해석

```
/수업 3 "1. 컨텍스트 윈도우를 어떻게 나눌 것인가" "2. 1번의 분할을 검증하는 방법은"
```

| 인자 | 의미 | 처리 |
|---|---|---|
| 첫 번째 | **일차(index)** | 숫자면 `docs/수업/03일차.md`(2자리 패딩), 날짜(`2026-07-29`)면 `docs/수업/2026-07-29.md` |
| 두 번째 이후 | **문제 하나씩** | 따옴표 하나 = 문제 하나. 문제 번호는 문제 내용 안에 들어 있으므로 **그 번호를 그대로 쓴다** (임의로 다시 매기지 않는다) |

- 일차가 같으면 **같은 파일에 이어 붙인다.** 파일이 이미 있으면 덮어쓰지 않고 append 한다.
- 인자가 비었으면 사용자에게 일차와 문제를 묻는다. 추측해서 만들지 않는다.
- 문제 안에 번호가 없으면 주어진 순서대로 번호를 붙이고, 파일에 "번호는 호출 순서 기준"이라고 적는다.

## 절대 규칙 — 이걸 어기면 답이 아니라 감상문이 된다

### 1. 재료는 이 저장소뿐이다

**답변에 쓸 수 있는 것**: `CLAUDE.md`, `docs/`, `reference/`, `archive/`, `.claude/`(에이전트·스킬 정의), `debate/`(있을 때), git 히스토리.

**쓸 수 없는 것**: 웹 검색, 외부 사례, 다른 회사 예시, 교과서적 정의를 그대로 옮긴 서술.

문제가 "○○ 개념을 설명하라"고 요구하더라도 **개념 설명은 한 문장으로 끝내고 곧바로 이 과제의 실물로 넘어간다.** "컨텍스트 엔지니어링이란 …입니다" 세 문단은 이 스킬의 실패 형태다. 올바른 형태는 "이 저장소에서 그것에 해당하는 것은 `docs/`의 00/10/30/90 분리이고, 그렇게 나눈 이유는 …"이다.

### 2. 개념은 반드시 이 저장소의 실물에 착지시킨다

문제에 나온 하네스 개념을 아래 표로 먼저 번역하고 답을 쓴다. 표에 없는 개념이면 **대응하는 실물이 이 저장소에 있는지부터 찾고, 없으면 "없다"가 곧 답의 일부다** (그리고 그것이 4단계의 반영 후보가 된다).

**개념 정의는 `docs/수업/00_개념정리.md`에서 가져온다** — 매 일차 정의를 다시 쓰지 않는다.

⚠ **하네스가 둘이다.** **A = 기획 하네스**(이 저장소를 돌려 기획을 만드는 장치), **B = 제품 하네스**(과제 산출물로 만들 장치). 개념 하나가 양쪽에 다르게 착지하는 경우가 많으므로 **어느 쪽인지 밝히고 답한다.** 한쪽만 답하면 반쪽 답이다 (`CLAUDE.md` 7절).

|---|---|---|

### 3. 문제가 요구한 형식을 그대로 따른다

문제 문장에서 형식 지시를 먼저 추출해 답변 앞에 `**요구 형식**:`으로 명시하고, 그 형식으로만 답한다.

| 문제가 이렇게 쓰여 있으면 | 이렇게 답한다 |
|---|---|
| "표로 정리하라" | 표. 열 이름까지 문제가 정했으면 그대로 |
| "3문장으로" | 정확히 3문장. 넘기지 않는다 |
| "다이어그램으로" | 코드블록 안의 텍스트 다이어그램 |
| "예시를 들어" | 이 과제의 실제 항목으로 든 예시 (가공 사례 금지) |
| 형식 지시가 없음 | 근거를 붙일 수 있는 최소 형식 — 결론 문장 + 근거 표 |

형식 지시와 내용 지시가 충돌하면 **형식을 지키고, 지키느라 뺀 내용은 답변 아래 "형식상 생략" 한 줄로 남긴다.**

### 4. 2번 문제부터는 앞 답변이 전제다

- 같은 일차의 앞 문제 답변을 **읽고 나서** 답한다. 앞 답변과 모순되면 둘 중 하나가 틀린 것이므로, 뒤 답변에서 **앞 답변을 수정하고 수정 사실을 적는다** (앞 답을 남긴 채 모순된 새 답을 쌓지 않는다).
- 답변에 `**앞 문제와의 연결**` 항목을 두고 "몇 번의 무엇을 전제로 썼는지" 한 줄로 적는다.
- **이전 일차 파일도 읽는다.** `docs/수업/` 아래 앞선 일차가 있으면 전부 훑고, 이번 답이 이전 일차의 결론을 뒤집으면 그 파일에 "N일차 X번에서 수정됨" 표시를 남긴다.

### 5. 답변은 이 저장소를 모르는 사람이 읽는다

**재료는 이 저장소지만, 독자는 이 저장소를 본 적이 없다.** 수업 제출물이므로 강사·다른 수강생이 읽는다. 재료로 쓴 것을 그대로 인용 표기하면 답변이 우리끼리만 읽히는 메모가 된다.

| 쓰지 않는다 | 대신 이렇게 |
|---|---|
| `docs/00_과제_정의.md` 2절 | "기업과제 원문이 요구한 3가지" |
| `30` ④ / `30` ⑤ | "해결 설계안의 기업 발굴 단계" / "무엇을 제안할지 정하는 매칭 단계" |
| `12` Q1 / N2 / N7 | **질문 내용을 그대로 편다** — "미팅에서 물을 질문 — '해외에서 파는 것이 AI 영상·이미지 제작 서비스 단독인가, 동대문 B2B 앱도 포함인가'" |
| `90` 리스크 7 | "리스크 목록 — 공개 정보로는 의사결정권자 연락처 확보가 어렵다" |
| `11_대안탐색_비교.md` | "데이터 소스 대안 비교 조사 (2026-07-29)" |
| Clo.D / AI-Studio를 설명 없이 | 처음 나올 때 한 줄로 무엇인지 — "동대문 B2B 거래 앱", "촬영 없이 AI로 제품 이미지·영상을 만드는 서비스" |
| 브리프, 축2, 신호 4종을 예고 없이 | **0절 배경 블록에서 먼저 정의**하고 그 뒤로는 그 이름을 쓴다 |

- **파일 경로와 문서 번호는 답변 본문·근거 표·미확인 절 어디에도 쓰지 않는다.** 근거 표의 열 이름은 `무엇에서 나왔는가`이며, "기업 조사 — 누적 투자 4억 원대에서 추론"처럼 **무엇을 조사해서 나온 것인지**를 적는다.
- **예외는 맨 아래 내부 기록 절 하나뿐이다.** 거기서만 경로를 쓰고, 절 제목에 `(내부 기록)`을 붙여 독자가 건너뛸 수 있게 한다.
- **0절 배경 블록은 매 일차 파일의 맨 앞에 둔다.** 기업과제 원문 한 문장, 3대 요구, 회사가 파는 것, 그날 답변에서 반복해 쓸 용어를 담는다. 같은 내용이 일차마다 반복돼도 잘라내지 않는다 — 각 파일이 단독으로 읽혀야 한다.

### 6. 모르는 것은 모른다고 쓴다

저장소 안의 재료로 답이 안 나오는 문제는 지어내지 않는다. `(미확인)`으로 표시하고 **무엇을 확인하면 답이 나오는지**를 적는다. 그 확인처가 기업이면 `docs/12_미팅_질문지.md`에 질문으로 추가할 후보로 올린다 (4단계).

## 실행 절차

### 0단계 — 파싱과 재료 확보

1. 인자에서 일차와 문제 목록을 뽑는다. 대상 파일 경로를 확정한다.
2. `docs/수업/` 디렉터리가 없으면 만든다. 대상 파일이 이미 있으면 읽는다 (이어쓰기 위치 확인).
3. `docs/수업/` 아래 이전 일차 파일을 전부 읽는다.
4. **항상 읽는 것**: `CLAUDE.md`(특히 7절 A/B 구분), `docs/수업/00_개념정리.md`, `docs/00_과제_정의.md`, `docs/90_미결정과_리스크.md`.
   - **개념 정의를 답변에서 다시 만들지 않는다.** `00_개념정리.md`에 있으면 그것을 쓰고, 없으면 그 개념을 이 파일에 **추가하는 것도 4단계 반영 후보다.**
5. 문제 내용에 따라 2절 매핑표를 보고 추가로 읽을 파일을 정한다. 회사 사실이 필요하면 **재조사하지 않고 `docs/10_기업조사.md`에서 가져온다** (`CLAUDE.md` 4절).

### 1단계 — 문제별로 답을 만든다

문제 하나씩, 번호 순서대로 처리한다. 병렬로 처리하지 않는다 — 4번 규칙(앞 답변이 전제) 때문이다.

각 문제에서:

1. **요구 형식 추출** — 3번 규칙 표로 판정.
2. **개념 착지** — 2번 규칙 표로 번역. 대응 실물이 없으면 그 사실을 기록.
3. **사고** — 설계·판단·비교가 걸린 문제는 `mcp__sequential-thinking__sequentialthinking`으로 단계를 나눠 생각한다 (`CLAUDE.md` 0절). 단순 조회·요약 문제는 쓰지 않는다.
4. **반례 세우기** — `CLAUDE.md` 0절 원칙대로, 낸 답을 스스로 한 번 반박해 보고 살아남는지 확인한 뒤 쓴다. 반례가 답을 무너뜨리면 답을 바꾼다.
5. **근거 표** — 답의 각 주장이 어느 파일 어느 절에서 나왔는지 남긴다. 근거를 못 붙이는 문장은 지운다.

### 2단계 — 파일에 쓴다

`docs/수업/<일차>.md`에 아래 형식으로 쓴다. 파일이 이미 있으면 헤더는 두고 문제 절만 이어 붙인다.

```markdown
# 수업 <N>일차 — 하네스 엔지니어링

> **재료 제약**: 이 문서의 모든 답변은 우리 팀이 맡은 기업과제와 그동안의 조사·설계 기록만으로 작성했다. 외부 자료·다른 회사 사례·교과서 정의는 재료로 쓰지 않았다.
> 작성 <YYYY-MM-DD>

## 0. 배경 — 이 답변들이 무엇에 대한 것인가 (처음 보는 사람용)

**맡은 기업과제**: 주식회사 큰삼촌컴퍼니 — *"진출 대상 국가에 적합한 잠재고객을 자동으로 탐색·목록화하고, 고객 특성에 맞춘 제안 메일을 반자동으로 작성·발송하는 AI 에이전트를 개발한다."*

<과제 원문이 요구한 3가지 표 — ① 탐색·목록화 ② 고객 특성 맞춤 ③ 반자동>
<회사가 파는 것 두 가지 — Clo.D(동대문 B2B 거래 앱) / Clo.D AI-Studio(촬영 없이 AI로 제품 이미지·영상 제작)>
<그날 답변에서 반복해 쓸 용어 — 예: 판별 신호 4종이 무엇인지>

※ 그날 문제가 다루지 않는 항목은 넣지 않는다. 배경은 **그날 답변을 읽는 데 필요한 것만**.
```

### 3단계 — 반영 후보를 뽑는다

답변을 다 쓴 뒤, **이번 답이 저장소를 실제로 바꿔야 한다고 말하고 있는 부분**을 찾는다. 이 단계를 건너뛰면 이 스킬은 필기 도구로 전락한다.

반영 후보의 형태는 셋뿐이다.

| 유형 | 반영 위치 | 예 |
|---|---|---|
| **하네스 자체를 고침** | `CLAUDE.md`, `.claude/agents/`, `.claude/skills/`, 디렉터리 구조 | 답변이 "지금 컨텍스트 분할에 X가 빠져 있다"로 귀결됨 |
| **기획을 고침** | `docs/30`·`01`·`02`, 미결정은 `90`에서 제거 | 답변이 파이프라인 단계나 판별 기준의 결함을 짚음 |
| **확인할 것이 늘어남** | `docs/12_미팅_질문지.md` | 답이 `(미확인)`에 걸려 멈춤 |

각 후보를 **한 줄 제안 + 그렇게 바꿔야 하는 이유**로 정리해 사용자에게 제시한다.

### 4단계 — 승인받고 반영한다

- **승인 전에 `docs/` 본문과 `CLAUDE.md`를 고치지 않는다.** (`plan-debate` 6단계와 같은 규칙)
- 승인된 것만 반영하고, 반영할 때마다:
  1. 해당 문서를 고친다
  2. 결정이 확정된 항목은 `docs/90_미결정과_리스크.md`에서 제거한다 (`CLAUDE.md` 5절)
  3. `docs/91_진행로그.md`에 **무엇이 왜 바뀌었는지** 한 줄 남긴다 — "수업 N일차 X번 답변에 따라 …"
  4. 2단계 파일 맨 아래 반영 표에 행을 추가한다
- 승인되지 않은 후보는 버리지 말고 그 표에 `보류`로 남긴다.

### 5단계 — 보고

사용자에게 짧게: 답한 문제 수 / 저장 위치 / **반영한 것과 보류한 것** / 남은 `(미확인)`. 답변 전문을 대화에 다시 붙여넣지 않는다 — 파일에 있다.
