# .claude — 실행체 (하네스 A + 하네스 B)

**이 저장소를 돌려 기획을 만드는 장치**(하네스 A)와 **기업과제 산출물로 만들 장치**(하네스 B)의 실행체가 함께 있다. 둘은 다른 것이며 섞어 말하면 공백 진단이 어긋난다 (`../CLAUDE.md` 7절) — 아래 표에서 하네스 B는 그렇게 표시해 뒀다(`g1-기업판정`, `g7-*`).

판단 기준은 `../CLAUDE.md`, 진행 순서·게이트는 `../docs/01_진행계획.md`에 있고, **이 디렉터리는 그 기준을 실제로 실행하는 몸통**이다.
Build Order(① Spec → ② Skill → ③ Subagent → ④ Workflow → ⑤ Hook → ⑥ Checklist)에서 하네스 A는 **⑤ Hook만 비어 있다** — 5절의 *"게이트 전에 `project-critic`으로 검토한다"*가 스스로 건너뛸 수 있는 형태로 남아 있다는 뜻이다 (`../docs/90_미결정과_리스크.md` 리스크 18).

## agents/ — 서브에이전트 8종

독립 컨텍스트로 돌고, **도구 권한이 각자 다르다.** 권한 차이는 실수가 아니라 설계다.

| 파일 | 어떤 사람인가 | 언제 부르는가 | 도구 |
|---|---|---|---|
| `planner-field.md` | **현장 귀납형** — 직접 리스트업·콜드메일을 해보다 기획자가 됨. 사례를 만들고 거기서 기준을 끌어올린다 | 판별 기준·임계값을 실제 사례로 검증할 때 | Read/Grep/Glob/Write + WebSearch/WebFetch |
| `planner-frame.md` | **문제 재정의형** — "잘 만들었는데 안 쓰인" 원인이 요구사항 문장 자체였음을 겪음. 브리프 뒤의 진짜 문제를 판다 | 문제 가설 경쟁·기준 체계 설계 | 위와 같음 |
| `planner-counterpart.md` | **수신자 역산형** — 제안 메일을 지우던 쪽에 있다 넘어옴. 답장이 나오는 조건에서 거꾸로 설계한다 | 메일 문안·톤·반응 설계 | 위와 같음 |
| `function-decomposer.md` | **폭포수 기능 분해 설계자** — 기능 경계를 잘못 그어 프로젝트를 다시 짜본 사람. 경계를 먼저 확정한다 | 확정된 플로우를 큰 기능 단위로 쪼개고 입출력 연결을 확정할 때. **사람/AI 분담·임계값·구현 방식은 다루지 않는다**(뒤 단계) | Read/Grep/Glob/**Write** (웹 없음 — 조사가 아니라 분해가 일이다) |
| `project-critic.md` | **적대적 검토자 — 프로젝트 전체** | 문서를 크게 고친 뒤, 단계 게이트 통과 전, 미팅·발표·제출 전 (`../CLAUDE.md` 5절) | Read/Grep/Glob + 웹. **Write 없음 — 지적만 하고 고치지 않는다** |
| `change-reviewer.md` | **적대적 검토자 — 변경 1건만.** `project-critic`과 트리거·범위가 다르다 — 전체 감사가 아니라 **방금 고친 변경**이 의도대로 반영됐는지, 다른 문서와 모순·부작용을 만들었는지만 좁게 본다 | 문서·Spec·기준 카드·Skill을 고친 직후, 그 파급 범위만 빠르게 확인할 때 | Read/Grep/Glob (웹 없음 — 내부 정합성만 본다). **Write 없음** |
| `g7-회신해석.md` | **하네스 B — G7의 해석 단위 T.** 일본어 회신 1통을 원문 보존한 채 해석하고 8분류·수신 거부·자동응답을 판정해 레코드를 만든다. **자기 번역을 검증하지 않는다** | `g7-회신처리` 스킬이 호출한다 (1단계, 재번역 시 2회차) | Read/Write/Edit (**웹 없음, 발신 도구 없음** — 답장 권한을 권한 층에서 없앤다) |
| `g7-번역검증.md` | **하네스 B — G7의 검증 단위 V.** 일본어 원문과 한국어 해석 **둘만** 받아 번역 검증 3층을 대조한다. 분류 결과·판단 과정을 받지 않는다 — 결론을 먼저 보면 번역을 결론에 맞춰 읽는다 | `g7-회신처리` 스킬이 호출한다 (5단계) | **Read만** (Write 없음 — 검증층에 옮겨 적는 것은 스킬의 일이고, 번역을 고치면 검증자가 번역자가 된다) |

- 앞 세 개(`planner-*`)는 **분업이 아니라 성향 분할**이다. 셋 다 같은 쟁점에 완결된 안을 내고, **답이 갈리는 것이 목적**이다. 묶어 돌리는 절차가 `skills/plan-debate`다.
- `planner-*`·`project-critic`·`function-decomposer` 5종은 모델이 `opus`로 고정돼 있다 — 판단이 갈리는 일을 맡기는 자리라 값을 아끼지 않는다. **`change-reviewer`와 `g7-*` 2종은 모델을 고정하지 않는다**(세션 모델 상속) — 반복 호출되는 좁은 실행 단위라 매번 opus를 쓰면 비용만 늘고, 검토 중 실제로 깊은 추론이 필요하다고 판단되는 좁은 지점만 호출하는 쪽이 별도로 opus 서브에이전트에 넘긴다(`CLAUDE.md` 5절). G7의 오역 방지는 모델 등급이 아니라 **T/V 분리와 역번역 대조**가 담당한다 — 근거는 `../docs/33_설계근거.md` D19.

## skills/ — 절차 카드 4종

**"매번 같은 절차로 하고 있다"**는 지점을 고정한 것이다. 즉흥으로 처리하면 결과가 매번 달라지는 작업만 여기 들어온다.

| 디렉터리 | 하는 일 | 호출 | 산출물 |
|---|---|---|---|
| `plan-debate/SKILL.md` | 세 기획자를 **블라인드**로 각자 조사·집필시킨 뒤 정(定)-반(反)-합(合)을 여러 차례 돌려 하나로 수렴시킨다. 결론뿐 아니라 **어떻게 그 결론에 도달했는지의 기록**이 산출물 — 심사가 요구하는 대안 비교·검증 자료 그 자체다 | `/plan-debate <쟁점>` | 합의안 + 토론 기록 + 결정대장 |
| `수업/SKILL.md` | 수업(하네스 엔지니어링) 문제를 **일반론이 아니라 이 저장소의 실물로** 답한다. 독자는 이 저장소를 모르므로 파일 경로·문서 번호 없이 쓴다 | `/수업 <일차> "1. 문제" "2. 문제" …` | `../docs/수업/<일차>.md`에 append |
| `g1-기업판정/SKILL.md` | **하네스 B(제품 하네스)의 실행체.** 일본 기업 1곳의 공개 페이지를 읽어 `../specs/G1_대상기업발굴.md`·`../기준/G1_기업판정기준.md`를 그대로 실행하고 후보 판정 파일 1개를 낸다. 판정 기준 카드가 규칙을 안 정한 경계(커머스 O4 등)는 카드 지시대로 `?`+사유로 잠정 처리하고, 스스로 규칙을 만들지 않는다 | `/g1-기업판정 "기업명" <URL 1개 이상>` | `candidates/{기업식별자}.md` |
| `g7-회신처리/SKILL.md` | **하네스 B(제품 하네스)의 실행체.** 일본어 회신 1통을 `../specs/G7_회신해석정리.md`·`../기준/G7_회신판정기준.md`대로 처리한다. G1과 달리 **실행 단위가 둘(해석 T / 검증 V)이라 서브에이전트 2종을 순서대로 호출하는 Workflow**이며, T의 산출물에서 **원문과 해석만 뽑아** V에게 넘겨 검증자가 분류 결과를 보지 못하게 막는다. 검증 불일치·판독 불가·검증층 미충족 3종의 분기가 실행 절차에 박혀 있다 | `/g7-회신처리 <회신 원문 붙여넣기>` | `replies/{수신일시}-{식별자}.md` + 수신 거부면 `발송금지.md` 1행 |

- **`plan-debate`는 한 번 쓰고 끝내는 스킬이 아니다.** 판단이 갈리는 쟁점이 나올 때마다 쟁점 하나 단위로 반복 호출한다.
- **`수업`은 답만 쓰면 절반만 실행된 것이다.** 그 결론이 프로젝트를 바꾸려면 `../docs/30`·`90`·`91`에 반영돼야 유효하다.
- **`g1-기업판정`·`g7-회신처리`와 `g7-*` 서브에이전트 2종은 하네스 A가 아니라 B다.** 나머지와 달리 이 저장소를 기획하는 도구가 아니라 **기업과제 산출물(제품 하네스)의 실행체**이며, `../CLAUDE.md` 7절 Build Order 대조표의 ②③④를 채운다. **G1은 실행 단위가 1개라 스킬 하나로 끝나고, G7은 실행 단위가 T·V 둘이라 스킬 1 + 서브에이전트 2**다 — 실행 단위 수가 곧 파일 수를 결정한다.

## settings.local.json — 유일한 미커밋 파일

비밀은 아니지만 **사람마다 다르게 두는 개인 권한 설정**이라 공유하지 않는다. `.gitignore`에 등재돼 있고, 이 디렉터리에서 커밋되지 않는 것은 이 파일뿐이다 (`../CLAUDE.md` 6절 공개 범위).

## 여기에 무엇을 추가할 때의 규칙

- **만들기로 결심하기 *전에* 먼저 찾는다.** ① 세션에 이미 뜬 목록 → ② `ls ~/.claude/plugins/marketplaces/*/plugins/`(공식 마켓플레이스가 로컬에 클론돼 있다) → ③ 웹 검색. **"이런 스킬이 있으면 좋겠다"는 생각이 든 시점이 곧 ②를 실행할 시점이다** (`../CLAUDE.md` 0절).
- **만들기 전 두 가지를 확인한다.** (a) 그 절차가 두 번 이상 반복되는가 (b) 사람이 매번 같은 판단을 내리는가. 둘 다 아니면 Skill이 아니라 한 번 하는 작업이다.
- **Build Order를 지킨다 — Skill은 ① Spec 다음이다.** 성공 기준 없이 절차 카드를 먼저 쓰면 "무엇이 완료인지 모르는 절차"가 된다.
- **왜 필요했는지를 `../docs/91_진행로그.md`에 한 줄 남긴다.** 이유가 없으면 나중에 지울지 판단할 수 없다.
- **저장 위치**: 프로젝트 공용은 여기(커밋 대상), 개인 전용은 `~/.claude/skills/`. 자격 증명·개인 경로는 본문에 쓰지 않고 환경변수로 참조한다 (`../CLAUDE.md` 6절).
