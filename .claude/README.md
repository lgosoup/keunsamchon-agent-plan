# .claude — 실행체 (하네스 A + 하네스 B)

**이 저장소를 돌려 기획을 만드는 장치**(하네스 A)와 **기업과제 산출물로 만들 장치**(하네스 B)의 실행체가 함께 있다. 둘은 다른 것이며 섞어 말하면 공백 진단이 어긋난다 (`../CLAUDE.md` 7절) — 아래 표에서 하네스 B는 그렇게 표시해 뒀다(`g1-기업판정`, `g2-세그먼트화`, `g4-연락처확보`, `g5-*`, `g6-발송결과판정`, `g7-*`, `run-orchestrator`, 그리고 검토 미통과로 `skills/_검증중/`에 있는 `g3-적합도평가`).

**⚠ `harness-builder`·`build-orchestrator`와 `run-orchestrator`는 이름이 비슷하지만 반대편이다.** 앞 둘은 **하네스 A** — 하네스 B의 실행체를 *만드는* 도구다. `run-orchestrator`는 **하네스 B 자신의 일부** — 만들어진 실행체를 *돌리는* 배선이며 제출물에 들어간다.

판단 기준은 `../CLAUDE.md`, 진행 순서·게이트는 `../docs/01_진행계획.md`에 있고, **이 디렉터리는 그 기준을 실제로 실행하는 몸통**이다.
Build Order(① Spec → ② Skill → ③ Subagent → ④ Workflow → ⑤ Hook → ⑥ Checklist)에서 하네스 A는 **⑤ Hook만 비어 있다** — 5절의 *"게이트 전에 `project-critic`으로 검토한다"*가 스스로 건너뛸 수 있는 형태로 남아 있다는 뜻이다 (`../docs/90_미결정과_리스크.md` 리스크 18).

### 모델을 고정하는 자리와 고정하지 않는 자리

가르는 기준은 하나 — **매 호출마다 새로 내리는 판단이 그 에이전트 존재 이유의 얼마를 차지하는가.**

| 모델 | 누구 | 왜 |
|---|---|---|
| **`opus` 고정** | `planner-*` 3종 · `project-critic` · `function-decomposer` · **`grading-critic`** · **`harness-builder`** | 판단이 갈리는 일을 맡기는 자리라 값을 아끼지 않는다. `grading-critic`은 `project-critic`과 같은 계열(적대적 해석 — 배점표 문장을 우리 산출물에 적용하는 것 자체가 해석이다). `harness-builder`는 **매 호출이 서로 다른 기능**이고 「실행 단위를 몇 개로 가를지 · 기존 실행체를 재사용할지」가 곧 그 에이전트의 존재 이유다 — `change-reviewer`의 좁은 대조가 아니라 `project-critic` 쪽에 가깝고, 이 저장소는 판단이 갈리는 지점을 이미 opus에 좁혀 물어 온 전례가 있다(`../docs/33_설계근거.md` D13) |
| **고정하지 않음** (세션 모델 상속) | `change-reviewer` · `g5-*` 2종 · `g7-*` 2종 · **`build-orchestrator`** · **`run-orchestrator`** | 반복 호출되는 좁은 실행·검토 단위라 매번 opus를 쓰면 비용만 늘고, 깊은 추론이 필요한 좁은 지점만 별도로 opus에 넘긴다(`../CLAUDE.md` 5절). `build-orchestrator`는 정본 표에서 순서를 세우고 파일 존재를 확인하고 고정된 라우팅 규칙을 따르는 일이라 새 판단이 얇다(깊은 판단은 `harness-builder`가 이미 opus로 갖고 있다). `run-orchestrator`는 **필요한 것이 더 똑똑한 판단이 아니라 고지식한 절차 준수**다 — 등급을 올리면 *"타임아웃이면 알아서 승인하면 되겠지"* 같은 자율적 우회 유혹만 커진다 |

- **`grading-critic`은 호출자에 따라 등급이 갈린다.** 프론트매터 고정은 `opus`고 사용자 단독 호출·`build-orchestrator`의 **전체 5항목 최종 판정**은 그대로 opus로 돈다. 단 `harness-builder`가 기능 하나·세 항목만 보는 **중간 판정**으로 부를 때는 Agent 호출의 `model` 파라미터로 `sonnet`을 지정해 프론트매터를 덮어쓴다 — 같은 배점표를 두 번(중간·최종) 다른 깊이로 보는 구조이고, 최종이 다시 opus로 전체를 훑으므로 중간 단계의 판단 비중은 상대적으로 낮다(2026-08-05, 사용자 지시 — 개별 검토 비용 절감). **등급을 낮췄다고 검토 자체를 건너뛰지 않는다** — `change-reviewer`→`grading-critic` 게이트 순서(`.claude/agents/harness-builder.md` 5번)는 그대로 유지된다.
- **낮은 등급으로 고정하지도 않았다.** `build-orchestrator`는 호출 빈도가 낮아(빌드 1회차에 한 번) 아낄 비용 자체가 없고, `run-orchestrator`는 배선 누락 하나가 곧 위법 발송 경로(수신 거부 되돌림)라 값을 아낄 자리가 아니다. 과거 미션 답안(`../포멧/6강_basic mission_answer_sheet.zip`)의 오케스트레이터가 `claude-haiku-4-5`로 낮춰 잡혀 있지만, 그것은 고정된 3스텝을 순서대로 부르는 일만 했고 우리 둘은 **실패 원인을 진단해 어디로 되돌릴지 가르는 일**을 함께 갖는다.
- **`g5-*` 2종도 고정하지 않는다 — G7과 같은 이유다.** 둘 다 정본 문서가 정한 것을 그대로 대조·집필하는 좁은 단위이고, 문안 1건마다 반복 호출된다. **오역을 막는 것은 등급이 아니라 방향이 맞는 카드 행 + T/V 분리 + 역번역 대조**이며, `g5-문안제작`의 사례·가격 인용 방지도 등급이 아니라 **입력 블록 경계**가 한다(아래 항목과 같은 원칙).
- **모델 등급을 안전장치로 쓰지 않는다.** G5·G7의 오역 방지는 등급이 아니라 **T/V 분리와 역번역 대조**가 담당하고(D19), G5의 반자동 보장은 등급이 아니라 **승인 정지점에서 종료**가 담당하며(대기 루프가 없으니 자동 재개는 **불가능**이다 — 여기까지가 구조다. 반면 *"승인란을 스스로 채우지 않는다"*는 `disallowed-tools`가 경로 단위가 아니고 발송 모드가 `발송기록/`을 쓰려면 Write가 살아 있어야 해서 **지침으로만 막는 금지**다. 둘을 한 단어로 뭉쳐 말하지 않는다 — *"어떻게 못 채우게 했나"*에 답이 달라진다), `run-orchestrator`의 정지점은 등급이 아니라 **정지점에서 종료 + 발송 권한 없음**이 담당한다. 등급을 안전장치로 삼는 순간 "그래서 그 구조가 왜 필요한가"에 답할 수 없게 된다. 근거는 `../docs/33_설계근거.md` **D19**·**D23**.

  1. **검증자가 결론을 보면 안 된다** → 검증 단위를 뗀다(G7의 V, G5의 V).
  2. **다시 만드는 쪽이 앞 회차 자기 산출물을 보면 안 된다** → 생성 단위를 뗀다(G7의 T, G5의 D). 재번역 지시를 내리는 자리가 곧 1회차 번역을 들고 있는 자리면 *"1회차는 주지 않는다"*가 물리적으로 성립하지 않는다.
  **G5가 셋이 된 것은 1과 2가 동시에 걸렸기 때문이다.** Spec 「독립 컨텍스트」가 세그먼트 1개를 제작의 1단위로 못박은 것, 그리고 *"게이트를 통과시키는 쪽이 문안을 만든 쪽이면 게이트가 아니다"*(`skills/g5-제안메일제작발송/SKILL.md`)도 같은 2의 방향이다 — **자기 산출물을 심사하는 자리와 만드는 자리를 겹치지 않게 두는 것**이 셋의 공통 뿌리다.
- **두 질문 어디에도 안 걸리면 파일만 늘어난다.** 컨텍스트 단위가 기능 안에서 갈리는 것(G3의 채점 1곳 ↔ 정렬 전체, G5의 제작 ↔ 발송)은 그 질문에 해당하지 않는다 — **모드를 나눠 호출하면 같은 스킬 하나로 지켜진다.**
- **질문 ②를 Spec 문구로 판정하지 않는다** (2026-08-06 G6에서 명시). 4경계 「도구 권한」 칸의 ***"…읽기 + 결과 파일 쓰기까지만"*** 과 ***"메일 발송 권한 없음"*** 은 **거의 모든 Spec이 쓰는 상용구**다(예외는 G5 하나 — 유일하게 발송 권한을 남긴 기능이다). 그 문구만으로 허용 목록(서브에이전트)이 필요하다고 읽으면 전 기능이 서브에이전트가 된다. 실제로 G1·G2·G3·G4·G7 다섯이 같은 문구를 **거부 목록(`disallowed-tools`)으로** 처리했다. **가르는 것은 문구가 아니라 「닫아야 할 대상을 지금 이름으로 다 열거할 수 있는가」**다 — 위 두 질문 표(:79)의 문언 그대로이며, **대상이 도구명이든 아니든 열거 가능성으로 가른다.** **경로 단위 제약은 그중에서도 별개 축으로 보인다** — `disallowed-tools`도 서브에이전트 `tools:`도 경로를 표현하지 못해 **어느 쪽을 골라도 안 닫히고**, 그래서 실행 구조나 지침으로 막는다(G6의 *"회신 열람 없음"*이 그 자리다). **:79와 `../docs/33_설계근거.md` D23이 허용 목록 후보로 지목해 둔 G11의 *"G2·G3 쓰기 불가"*가 바로 이 축이라, 그 지목이 유효한지가 갈린다**(그 기능도 「결과 파일 쓰기」가 필요해 `tools:`에서 Write를 뺄 수 없다). **여기서 확정하지 않고** `../docs/90_미결정과_리스크.md` 3절 G6에 올렸다 — 예시 하나의 분류가 아니라 두 질문의 적용 범위가 걸린 자리라 정본(`agents/harness-builder.md` 표)까지 함께 봐야 한다. 그리고 이 판정에는 유효기간이 있다: **메일 시스템 MCP가 실제로 연결되면 거부 목록은 그 서버의 새 도구(발송 포함)를 기본 허용한다.** G6은 바운스 조회 때문에 그 MCP를 **일부만** 필요로 하는 유일한 기능이라 그때 재판정 대상이며, `../docs/90_미결정과_리스크.md` 3절 G6에 올려 두었다.
- **스킬에는 모델 고정이 없다** (개수는 여기서도 세지 않는다 — 위 두 절 제목이 정본이고, 확정분과 검증 중인 것을 각자 다른 기준으로 세다가 같은 숫자가 되는 자리였다). 위 「모델을 고정하는 자리와 고정하지 않는 자리」는 서브에이전트에만 적용된다 — 스킬은 세션 컨텍스트에서 돌아 별도 모델 배정 지점이 아니기 때문이다. **`g2-세그먼트화`·`g3-적합도평가`·`g4-연락처확보` 셋은 서브에이전트를 만들지 않아 모델 배정 판단 자체가 발생하지 않았고, `g5-제안메일제작발송`에서 처음으로 다시 발생했다**(`../docs/33_설계근거.md` D23의 「뒤집힐 조건 ①」이 지켜보던 **수렴 3건 연속이 G5에서 깨졌다** — 「전부 스킬 하나로 수렴하면 `harness-builder`의 opus 고정을 내린다」는 조건은 이로써 발동하지 않는다).

## Skill이 조건 값을 다루는 방법 — 참조하지, 옮겨 적지 않는다

**Skill 본문(SKILL.md)에는 판정 문장·조건 값·임계값을 직접 쓰지 않는다.** 그런 값이 필요하면 먼저(또는 동시에) `../기준/<기능코드>_*.md`에 만들고, Skill 본문은 "이 파일을 참조한다"는 문장으로 대신한다 — `g1-기업판정/SKILL.md`가 이미 그 형태다("이 스킬은 정본 두 문서를 그대로 실행하는 호출 계약이다... 이 스킬 본문과 두 문서가 어긋나면 문서가 이긴다").

- **참조는 파일 단위다, 절 단위로 쪼개 앵커를 걸지 않는다.** `기준/` 카드는 "매 실행마다 전체를 다시 읽는다"가 원칙이라(`g1-기업판정` 패턴) — 절 하나만 콕 집어 참조하면 그 카드의 다른 절이 바뀐 걸 실행체가 놓칠 위험이 생긴다.
- **이미 만들어진 스킬도 예외가 아니다.** `g1-기업판정`·`g2-세그먼트화`·`g4-연락처확보`·`g7-회신처리`(그리고 검증 중인 `g3-적합도평가`)의 조건이 바뀌면 스킬 본문이 아니라 대응하는 `기준/` 카드를 고친다 — 새로 만드는 스킬만의 규칙이 아니라 스킬 전체의 규칙이다.
- **아직 `기준/` 카드가 없는 기능**(G5·G9·G10처럼 `specs/README.md` 파일 표에 "별도 기준 카드 없음, 다른 카드 재사용"이라고 적힌 것)은 그 스킬을 만들 때 **재사용 대상 카드를** 참조 문구에 명시한다. **그 표가 절 번호까지 적어 둔 기능도 있고 카드 이름만 적어 둔 기능도 있다**(G5는 "`기준/G7` 3절", G9·G10은 카드 이름만) — **없는 절 번호를 만들어 붙이지 않는다.** 참조 단위가 파일 전체라는 위 원칙과 부딪히지 않는 이유는, 절 번호가 적힌 경우도 *"카드 전체를 읽고 그중 이 절이 이 기능의 자리"*라는 안내이지 부분 참조 허가가 아니기 때문이다.
- **어디까지가 "조건"이고 어디까지가 "절차"인지는 `../CLAUDE.md` 5절의 판별법을 그대로 쓴다.** 지우면 출력이 바뀌면 조건(`기준/`로 보낸다), 과정만 바뀌면 절차(Skill 본문에 남긴다).
- 근거는 `../docs/33_설계근거.md` **D21**.

## settings.local.json — 유일한 미커밋 파일

비밀은 아니지만 **사람마다 다르게 두는 개인 권한 설정**이라 공유하지 않는다. `.gitignore`에 등재돼 있고, 이 디렉터리에서 커밋되지 않는 것은 이 파일뿐이다 (`../CLAUDE.md` 6절 공개 범위).

## 여기에 무엇을 추가할 때의 규칙

- **만들기로 결심하기 *전에* 먼저 찾는다.** ① 세션에 이미 뜬 목록 → ② `ls ~/.claude/plugins/marketplaces/*/plugins/`(공식 마켓플레이스가 로컬에 클론돼 있다) → ③ 웹 검색. **"이런 스킬이 있으면 좋겠다"는 생각이 든 시점이 곧 ②를 실행할 시점이다** (`../CLAUDE.md` 0절).
- **만들기 전 두 가지를 확인한다.** (a) 그 절차가 두 번 이상 반복되는가 (b) 사람이 매번 같은 판단을 내리는가. 둘 다 아니면 Skill이 아니라 한 번 하는 작업이다.
- **Build Order를 지킨다 — Skill은 ① Spec 다음이다.** 성공 기준 없이 절차 카드를 먼저 쓰면 "무엇이 완료인지 모르는 절차"가 된다.
- **왜 필요했는지를 `../docs/91_진행로그.md`에 한 줄 남긴다.** 이유가 없으면 나중에 지울지 판단할 수 없다.
- **저장 위치**: 프로젝트 공용은 여기(커밋 대상), 개인 전용은 `~/.claude/skills/`. 자격 증명·개인 경로는 본문에 쓰지 않고 환경변수로 참조한다 (`../CLAUDE.md` 6절).
