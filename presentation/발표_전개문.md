## S1. 문제
- 큰삼촌컴퍼니 해외진출 시도, 매번 협력사 개인 경험에서 멈춤
- 근거: 2026-07-30 설명회 실패사례 4건(협력사 경험영역 한정 / 플랫폼 과다로 전수탐색 불가 / SNS 다량영업→계정정지 1주 / 연락처 미갱신→도달실패)

## S2. 병목 확정
- 4사례 공통점 = "기업을 못 찾는 것"이 아니라 "누구를 접촉할지 판별기준이 없는 것"
- 근거: Qoo10·라쿠텐에서 이미 수백 개 판매자 리스트 확보 경험 있음("검증을 거치지 않았다"는 것까지 기업이 직접 말함) → 후보 부재가 아님

## S3. 근본원인 + 해결원리 (통합)
- 근본원인: 해외영업 판단(누구를·무엇을)이 회사 자산이 아니라 협력사 암묵지에 갇혀 있음
- 두 병목: ①기업서치(확정된 사실) ②이메일 제작·발송 — **여기 한 층 더 나눠 말한다**: "자동 발송 자체"는 기업이 이미 확정 요구했다(설명회에서 "자동으로 하고 싶다"고 직접 발언) / "그 병목의 정확한 원인 진단"(미도달이 협력사 병목 재생산 때문인지, 다른 이유인지)만 가설이고 확인 질문 대기 중이다. **"요구는 확정, 원인 진단만 미확인"** — 요구 자체를 가설 취급하지 않는다
- 해결원리: 암묵지 → 명시적 자산화, 재사용(지금)/학습(나중) 2축. 두 병목 다 지금 재사용으로 먼저 푼다

## S7. G5 하나로 관통하는 Build Order 설계 (4장)

> 12개 기능을 다 훑지 않고 G5(제안메일 제작·발송) 하나를 끝까지 열어 채점 3항목(Skill완성도25·Agent·Workflow25·Harness20)을 증명한다. 실물 인용은 전부 `Harness/data/`의 **합성 시나리오 실행 1회분**(ingni-store-com=S1/관심표명, orbis-co-jp=S2/이유있는 거절)에서 가져온다.
>
> **도입 문장(신설)**: "Workflow와 Hook만 있고 검증 단위가 없었다면 어떻게 됐을까 — 번역이 틀려도 그대로 발송됐을 것이다. 이번 실행에서 V(번역검증)가 그 틀을 실제로 잡아냈다(3층 전부 일치, 1회차 통과 — 걸릴 게 없어서 통과했다는 뜻이지, 검증이 없었다는 뜻이 아니다)." → Build Order를 지킨 결과 무엇이 달라졌는지부터 말하고 시작한다.

### S7-A. Skill 완성도 및 자동화 (25점)
- **Spec 카드 + SKILL.md 둘 다 캡처** (v1에서 Spec 카드만 캡처하던 것을 수정 — 배점표 문구가 "SPEC.md와 SKILL.md" 둘을 명시) — Spec은 목표·범위·성공기준, SKILL.md는 오케스트레이션 절차(제작→확장→검증→승인→발송 순서 그 자체)
- **성공기준 표기: 무관용 6종**(승인기록 존재 / 번역검증 3층 일치 / 법정표시 의무 4종 / 레퍼런스·가격 미인용 / 미확인 상업적 약속 없음 / 발송금지 미등재) — v1의 "4종"은 "법정표시 의무 4종"과 전체 무관용 항목 수를 혼동한 오류였다. **6종 전체를 짧게 나열**하고 그 중 "법정표시 4종"은 하나의 항목임을 명시
- Skill이 세그먼트마다 반복 호출되는 자동화 단위임을 실물로: S1(ingni-store-com)·S2(orbis-co-jp) 두 세그먼트에 같은 절차가 반복 적용된 이력
- Subagent 3분리 이유: "자기 번역은 자기가 검증 못 한다" → D(문안제작)/V(번역검증) 분리, "발송권한 쥔 쪽이 승인판단 못한다" → 승인확인 별도
- **재사용 한계(문구 수정)**: v1 "재사용 시도했지만 실패"는 약점으로 읽힐 위험이 있어 수정. → **"V는 G7과 판정 방향이 반대(G7=일→한, G5=한→일)라 무리하게 재사용하면 실행 중 판정기준 문서의 어느 줄을 볼지 갈린다 — 그래서 재사용을 강행하지 않고 별도로 뒀다"**. 성공사례가 아니라 **경계를 지킨 판단**으로 읽히게 프레이밍

### S7-B. Agent·Workflow 실행 완성도 (25점)
- **Agent 역할의 구체성(실물)**: D는 한국어 의도문 한 장 → 일본어 제목·본문을 낸다(실제 예: "INGNI STORE様 掲載アイテム353点のビジュアル制作に関するご提案", 본문에 O6 상품353건·O3 코디사진 인용). V는 그 원문+번역 둘만 받아 3층 대조 → 실제 결과 "3층 전부 일치, 1회차 통과". 승인확인은 승인란만 읽고 승인/거부/미승인만 반환
- **워크플로우 흐름**: D→V→승인확인→발송 체이닝 다이어그램, ingni-store-com이 이 체인을 실제로 완주한 이력
- **설계범위 내 조작(개념 연결 추가)**: 승인게이트=자동재개 없이 종료(타임아웃으로 자동승인 안 됨) — 이건 **"검증 없는 실행"** 붕괴를 막는 장치다(승인 없이 다음 단계로 못 넘어가므로). G6이 회신 내용 자체를 열람하지 않는 것, G10이 재조사 우회를 막으려 Agent 권한까지 함께 차단한 것도 같은 붕괴(검증 없는 실행/우회 경로로 새는 것)를 막는 같은 원칙의 반복 사례라고 슬라이드에서 명시적으로 연결
- **트리거→최종산출물**: H6(제작트리거: 5건누적/7일경과)→U2(승인)→발송기록 (자세한 체인은 S7-D)

### S7-C. Harness 견고성 및 재현성 (20점)
- **반복실행 안정성**: ingni-store-com(S1)과 orbis-co-jp(S2) 두 건을 나란히 — 같은 파일 스키마·같은 절차, 결과만 다름(관심표명 vs 이유있는 거절). "같다"고 말하는 대신 두 건을 눈으로 대조시킨다
- **실패·예외 상황 고려(existence만 — 실행 확인 아님)**: Spec 실패표 4종(번역불일치→재번역1회후 보류 / 발송상한초과→라운드로빈 보류 / 승인거부·무응답→미발송 / 발송금지등재→해당건만 제외) 캡처. **이 4종은 설계돼 있다는 것만 보여준다 — "실물로 실행했다"고 말하지 않는다.** (v1에서 orbis-co-jp의 "거절"을 실패 사례로 인용했던 것은 삭제 — 그건 G7이 회신을 정상적으로 8분류 중 하나로 분류한 성공 경로이지 G5의 실패 분기가 아니다. 배점 문구 자체가 "고려했는가"이지 "전부 실행했는가"가 아니므로 존재 증빙으로 충분)
- **검증기준**: 무관용(법정표시 4종 등 — 위법·비용비대칭, 6종 전체는 S7-A 참조) vs 서식점검(나머지) 등급 구분
- **하네스 폴더만으로 재현 가능 + 외부 의존성 없음**: `Harness/README.md` 자기선언("이 폴더 하나로 완결 — 다른 파일 참조 안 함") + 2026-08-06 실제 점검 이력(root docs/33·34 참조 제거) 캡처. `Harness/data/`·`Harness/criteria/`에 합성 시나리오 실행 1회분이 실제로 쌓여 있는 상태 캡처(README 오기재는 발표 전 정정 완료 — 아래 "정정 이력")

### S7-D. 트리거 → 최종 산출물 체인 (신설)
- H6(제작트리거)→U2(승인)→`발송기록/ingni-store-com-...md`(수신주소+확정문안)→`상태/...md`([회신])→`replies/...md`(해석+분류) — 4개 파일 캡처를 화살표로 연결한 한 장
- "트리거부터 최종 산출물까지 끊기지 않고 이어진다"를 실물 파일로 증명
- **한계를 슬라이드 하단에 작게 명시**: 이 체인은 사람이 각 기능을 순서대로 호출해 만든 결과다 — `run-orchestrator`(전체 자동 배선)는 아직 실행 이력이 없다(`Harness/data/실행상태.md` 부재). "기능 하나하나는 검증됐고, 전체 자동 배선은 다음 단계"라고 정직하게 구분
