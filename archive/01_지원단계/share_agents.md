### feasibility-agent (현실성)

**평가 기준**: 부트캠프 "프로젝트 LAB"은 기간이 짧은 트랙이며 참여는 "2인 1팀 또는 개인 단위"(기업과제 PDF)로 진행된다. 이 규모·기간 대비 계획서가 설계한 기술 스택과 파이프라인 범위가 프로토타입 수준을 넘어서는지를 기준으로 판단했다.

**1지망 — 큰삼촌컴퍼니: 등급 하**

근거: 원 과제는 "고객 특성에 맞춘 제안 메일을 반자동으로 작성·발송하는 AI 에이전트를 개발"(기업과제 PDF)로 범위를 명확히 좁혀 놓았는데, 지원자 계획서는 "잠재고객 탐색, 기업 정보 구조화, 고객 요구 분석, …, 맞춤형 이메일 생성, 발송과 반응 분석으로 이어지는 파이프라인"에 "온톨로지·지식그래프", "MCP 기반 Chrome 연동", "전역 LLM 에이전트", "규칙 기반 검증", "반응 분석" 기반 자기개선 루프까지 전 구성요소를 쌓아 올려 1~2인·단기 트랙이 감당하기엔 스코프가 과도하다.

- 자동/반자동 간극: 원 브리프는 "반자동"만 명시했는데, 계획서는 "각 단계는 자동 실행, 조건부 확인, 항상 확인 방식으로 설정합니다 … 이메일 발송 단계에도 같은 정책을 적용해 자동 발송과 승인 후 발송을 모두 지원합니다"라고 하여 완전 자동 발송 옵션까지 설계 범위에 넣었다. 승인 모드를 함께 제공한다는 점에서 반자동 요건을 위배하진 않지만, "조건과 신뢰도 기준을 충족한 업무는 자동으로 다음 단계까지 진행"처럼 완전자동 경로를 정식 기능으로 설계·구현해야 하는 부담이 원 브리프보다 크다.
- "각 단계마다 사용자 요구사항, 조건들은 각각의 문서로 관리되며, 해당 문서를 llm 참조 함으로서 보다 환각없이 사용자의 요구를 이행할 수 있습니다"는 표현은 문서 참조(RAG류 접근)가 환각을 "줄일" 수는 있어도 "환각 없이"라고 단정할 근거는 없다 — 어려운 문제(LLM 환각 억제)를 이미 해결된 전제로 서술한 대표적 사례.
- "프로젝트 LLM과 MCP 기반 Chrome 연동을 활용해 … 검색 결과와 기업 홈페이지를 순차적으로 탐색해 기업명, 주요 사업, 제공 상품·서비스, 최근 사업 활동, AI 활용 수요와 공식 연락처를 수집합니다"는 국가·언어별로 상이한 실제 해외 기업 웹사이트 구조, 접근 차단, 연락처 정보의 신뢰도 문제를 전제하지 않고 있어, 단기 트랙에서 안정적으로 동작하는 프로토타입으로 구현하기엔 낙관적이다.

리스크/블로커:
1. MCP 기반 Chrome 연동으로 실제 해외 기업 사이트를 순회하며 "공식 연락처"까지 신뢰성 있게 수집하는 기능은 사이트 구조 다양성·언어 처리·접근 차단 이슈로 단기간 내 안정 구현이 어려움.
2. "환각없이 사용자의 요구를 이행할 수 있습니다"는 미해결 기술 난제를 전제한 과확신 표현.
3. 온톨로지·지식그래프, 규칙 기반 검증, 전역 LLM 에이전트, 반응 분석 기반 개선 루프를 모두 포함한 8단계 이상 파이프라인은 1~2인·단기 트랙 규모 대비 구현 범위가 과도함.
4. 원 브리프의 "반자동" 전제 대비, 완전 자동 발송 경로까지 정식 기능으로 설계해 스코프와 오발송 리스크 관리 부담이 늘어남.

**2지망 — 잇뉴: 등급 중**

근거: "주문일, 이용 주기, 주문 횟수와 최근 이용 시점을 기준으로 신규·재이용·이탈 위험 고객을 분류"하는 방식은 RFM류 규칙 기반 분석으로 부트캠프 기간 내 구현 가능한 현실적 범위다. 다만 "고객·주문·품목·지역 간 관계는 온톨로지와 지식그래프 형태로 연결합니다"는 이 규모의 데이터·기간에는 과잉 설계 소지가 있고, 실제 데이터 접근 여부가 확인되지 않은 상태로 "지역별 주문 변화", "물류 인력 배치"를 다루는 것은 서비스가 "제주 본섬 내에서만 운영"(공통 컨텍스트, 웹서치 결과)되는 단일 지역 규모와 맞물려 데이터 세분성이 뒷받침되는지 불확실하다.

리스크/블로커:
1. 실제 주문·회원 데이터 접근 여부가 확인되지 않음 — 목업 데이터로 대체할 경우 "비정형 품목명 … 구조화"의 정확도를 검증하기 어려움.
2. "온톨로지와 지식그래프 형태로 연결"은 이 데이터 규모·기간 대비 관계형 DB로도 충분할 수 있어 과잉 설계 우려.
3. "지역별 주문 변화", "물류 인력 배치와 운영 계획 수립에 분석 결과를 활용"은 제주 단일 지역 서비스 규모 대비 세분화된 지역 데이터가 실제 존재하는지 불확실.
4. "데이터 분석과 머신러닝은 고객 이용 패턴, 이탈 위험과 품목별 수요 변화를 탐지하기 위해 활용합니다"라고 명시했으나, 바로 앞 문단에서 설명한 분류 기준은 규칙 기반(RFM류)으로 충분해 "머신러닝"이 실제로 필요한지, 프로토타입에 어느 수준까지 넣을지 불명확함.

**3지망 — 휴플: 등급 상**

근거: 원 과제가 요구하는 "소개 콘텐츠 제작(디자인 업무)"과 "웹화면 노출(코딩 업무)"의 자동화 범위와 계획서의 "관광상품의 기본 정보와 보유 자료를 입력하면 소개 문구, 주요 일정, 추천 대상, 핵심 관광 요소, 이용 안내와 웹페이지 구성안을 생성"이 거의 그대로 대응되며, 1·2지망과 달리 온톨로지·지식그래프나 실시간 외부 웹 연동 같은 무거운 인프라 전제가 없다. "외부 API 연동이 가능한 경우 지도, 관광지와 이동 관련 정보를 추가로 반영할 수 있습니다"처럼 확장 기능을 조건부("가능한 경우")로 남겨둔 점도 스코프 관리가 상대적으로 신중함을 보여준다.

리스크/블로커:
1. "노코드 웹페이지 템플릿에 자동으로 반영"이 실제 젠트립 CMS·노코드 툴과의 연동을 의미하는지, 자체 제작 템플릿 렌더러를 의미하는지 불명확 — 전자라면 플랫폼 접근권한 확보가 전제되어야 함.
2. "이 내용을 영어 홍보 페이지로 만들어줘"처럼 다국어·다채널 콘텐츠 생성까지 포함되어 검증해야 할 조합이 늘어나 단기 트랙 내 전량 검증에 시간이 부족할 수 있음.
3. "규칙 기반 검증은 일정 순서, 필수 정보 누락, 날짜·가격·인원과 같은 입력값의 불일치를 확인"하려면 관광상품 데이터 스키마가 사전 정의되어야 하는데, 실제 젠트립 데이터 스키마 확보 여부가 확인되지 않음.
4. 세 지망 중 가장 현실적이나, "여행자 유형과 상품 조건에 따라 콘텐츠와 화면 구성이 달라지는" 조건 분기 수를 어디까지 지원할지 범위가 명시되지 않아 구현 중 스코프가 확장될 가능성이 있음.

### specificity-agent (구체성)

**총평(비교)**: 2지망(잇뉴)이 세 지망 중 가장 구체적이다 — 고객 분류 기준(주문일·이용 주기·주문 횟수·최근 이용 시점)과 품목 구조화 스키마(표준 품목명/품목군/세부 유형)처럼 측정 가능한 변수·범주를 제시한다. 1지망(큰삼촌컴퍼니)은 잠재고객 탐색 단계의 수집 항목(기업명, 주요 사업, 제공 상품·서비스, 최근 사업 활동, AI 활용 수요, 공식 연락처)은 구체적으로 나열하지만, 선택사유와 본문 곳곳에서 "AI 오케스트레이션·전역 LLM 에이전트·온톨로지·규칙 기반 검증"을 한 문단에 몰아 쓰면서 정작 각 기법의 데이터 구조·임계값은 설명하지 않아 세 지망 중 용어 의존도가 가장 높다. 3지망(휴플)은 출력 스키마(제목/요약/일정/관광지/이동정보/준비사항/유의사항)와 검증 대상(일정 순서·필수 정보 누락·날짜·가격·인원 불일치)을 구체적으로 나열하지만 서술 분량 자체가 가장 짧아 오케스트레이션·노코드 템플릿 결합의 메커니즘 설명이 가장 피상적이다.

공통적으로 지적할 점: 문서 전체에서 "신뢰도 기준"이라는 표현은 1지망("사용자가 지정한 조건과 신뢰도 기준을 충족한 업무는 자동으로 다음 단계까지 진행합니다")과 2지망("분류 결과에 신뢰도를 부여해 불확실한 항목만 담당자가 확인")에 등장하지만, 문서 전체 어디에도 신뢰도를 어떻게 산출하는지(모델 confidence score, LLM 자기평가, 규칙 기반 점수 등)와 구체적 임계값(예: 80% 이상)이 한 번도 제시되지 않는다. "문서로 관리"(1지망)도 형식·저장 위치·스키마 없이 개념만 언급된다.

#### 1지망 — 큰삼촌컴퍼니: 등급 **중**

근거: 해외 기업 탐색 단계는 파이프라인 순서와 수집 항목을 구체적으로 서술해 절차 자체는 세 지망 중 가장 상세하지만, 배경에서 지적된 핵심 기법(문서 관리, 신뢰도 기준, 온톨로지 관계, 규칙 기반 검증)은 스키마·임계값·예시 규칙 없이 용어만 나열되어 이 부분만 놓고 보면 구체성이 떨어진다.

모호한 구절 인용 및 누락 사항:
1. "각 단계마다 사용자 요구사항, 조건들은 각각의 문서로 관리되며, 해당 문서를 llm 참조 함으로서 보다 환각없이 사용자의 요구를 이행할 수 있습니다." → 빠진 것: (a) 문서 형식(마크다운/JSON/DB 레코드 등) 미정 (b) 저장 위치·저장소 미정 (c) "각각의 문서"가 고객별인지 단계별인지 구조 불명 (d) LLM 참조 방식(RAG 검색? 프롬프트 직접 삽입?) 불명.
2. "사용자가 지정한 조건과 신뢰도 기준을 충족한 업무는 자동으로 다음 단계까지 진행합니다." → 빠진 것: (a) 신뢰도 산출 방법 불명 (b) 구체적 임계값 없음 (c) "조건"의 실제 필드·값 예시 없음.
3. "온톨로지·지식그래프는 국가, 기업, 업종, 유통 채널, 고객 요구, 자사 서비스와 기대 효과의 관계를 구조화하고 고객 요구와 기업 강점의 연결을 유지하기 위해 적용합니다." → 빠진 것: (a) 노드/엣지 타입 정의 없음 (b) 그래프 저장 기술(예: 속성 그래프 DB) 언급 없음 (c) 실제 관계 예시(예: "기업 --취급--> 업종") 없음.
4. "규칙 기반 검증은 사용자 정책과 기업의 영업 기준을 실행 조건으로 적용하고, 부정확한 정보나 민감한 제안이 자동으로 발송되는 위험을 줄이기 위해 사용합니다." → 빠진 것: 실제 규칙(if-then) 예시가 전무함.

#### 2지망 — 잇뉴: 등급 **중**

근거: 고객 분류 기준과 품목 구조화 스키마는 측정 가능한 변수로 제시되어 세 지망 중 상대적으로 가장 구체적이나, 온톨로지 관계·신뢰도 임계값·머신러닝 기법은 여전히 용어 수준에 머문다.

모호한 구절 인용 및 누락 사항:
1. "고객·주문·품목·지역 간 관계는 온톨로지와 지식그래프 형태로 연결합니다." → 빠진 것: (a) 실제 관계(edge) 예시 없음 (b) 그래프 저장·조회 기술 불명 (c) 지식그래프가 분석 로직에서 구체적으로 어떻게 질의되는지 불명.
2. "분류 결과에 신뢰도를 부여해 불확실한 항목만 담당자가 확인할 수 있도록 구성합니다." → 빠진 것: (a) 신뢰도 산출 방식(확률/유사도 점수 등) 불명 (b) "불확실"의 기준값 없음.
3. "데이터 분석과 머신러닝은 고객 이용 패턴, 이탈 위험과 품목별 수요 변화를 탐지하기 위해 활용합니다." → 빠진 것: (a) 모델 종류(분류 모델? 시계열 예측?) 미명시 (b) 학습에 쓰일 피처 목록 불명.
4. "규칙 기반 분류와 기존 품목 정보를 함께 활용해 동일한 품목이 일관된 기준으로 관리되도록 합니다." → 빠진 것: 규칙의 실제 내용(문자열 유사도 임계값? 매핑 테이블?) 없음.

#### 3지망 — 휴플: 등급 **하**

근거: 출력 스키마와 검증 대상 항목은 구체적으로 나열되지만, 세 지망 중 서술 분량이 가장 짧고 AI 오케스트레이션·노코드 템플릿 결합의 실행 메커니즘 설명이 가장 피상적이어서 상대적으로 가장 얕다.

모호한 구절 인용 및 누락 사항:
1. "AI 오케스트레이션은 상품 정보 분석, 콘텐츠 생성, 검증, 이미지·구성 요소 선택과 웹페이지 제작 단계를 연결하기 위해 활용합니다." → 빠진 것: (a) 오케스트레이션 도구/프레임워크 미명시 (b) 단계 간 상태 전이 조건 없음 (c) 재시도·실패 처리 로직 없음.
2. "조건을 충족한 콘텐츠는 노코드 웹페이지 템플릿에 자동으로 반영합니다." → 빠진 것: (a) 어떤 노코드 플랫폼/템플릿 엔진인지 불명 (b) 구조화 필드-화면 컴포넌트 매핑 방식 불명 (c) "조건을 충족"의 판정 기준(검증 규칙 몇 개 통과 시 등) 불명.
3. "검증이 필요한 항목은 담당자에게 표시하고" → 빠진 것: 표시 방식(어느 화면/알림 채널)과 우선순위 기준이 없음.

### differentiation-agent (차별성)

**총평(공통 패턴)**: 1~3지망 모두 "전역 LLM 에이전트 + 단계별 파이프라인 + 온톨로지·지식그래프 + 규칙 기반 검증 + AI 오케스트레이션"이라는 동일한 아키텍처 틀에 도메인 명사(해외영업/고객주문/관광콘텐츠)만 바꿔 끼운 구조다. 세 지망의 "수행 아이디어" 문단을 나란히 보면 구성 요소 목록과 문장 패턴이 사실상 동형(isomorphic)이며, 각 기업의 실제 사업 특수성에서 "이 회사이기 때문에 이런 설계가 필요하다"는 역방향 추론이 거의 없다. 차별성 주장은 "~를 통해 차별성을 확보할 수 있습니다"라는 결론 문장에 의존할 뿐, 그 앞에 제시된 기능(자연어 파이프라인 조회, 조건별 콘텐츠 변형, 온톨로지 연결)은 유사한 과제라면 누구나 1차로 떠올릴 법한 범용 설계에 가깝다. 전반적으로 회의적 평가가 필요하다.

**1지망(큰삼촌컴퍼니) — 등급: 하**
- 근거: "사용자가 자연어로 전체 영업 파이프라인을 확인·조정"하는 기능은 리드 탐색→이메일 발송으로 이어지는 어떤 AI 에이전트 과제에도 붙일 수 있는 범용 대화형 UX 패턴이며, Clo.D의 실제 강점(동대문 B2B ERP 디지털화, AI 가상 피팅·비주얼 콘텐츠 대행, 1/3 비용·1~2주 제작)과 구체적으로 맞물리는 설계는 "일본 패션 브랜드 중 AI 모델컷 수요가 높은 기업만 다시 찾아줘"라는 예시 질의 한 줄뿐이다. 나머지 본문은 "Clo.D·Clo.D AI-Studio의 강점 연결"이라는 문구만 5회 이상 반복할 뿐, 어떤 강점을 어떤 해외 고객 세그먼트·업종에 어떻게 매핑하는 로직인지(예: 자체 촬영 스튜디오가 없는 해외 SME는 AI-Studio 제안, 사입 물량이 큰 도매상은 Clo.D ERP 연동 제안 등) 구체적 규칙이 없다.
- 보강 필요:
  1. Clo.D(ERP)와 Clo.D AI-Studio(비주얼 콘텐츠) 각각의 강점을 어떤 해외 고객 특성(업종/규모/현재 촬영 방식 등)과 매칭하는지 명시적 규칙/스코어링 로직 설계
  2. "자연어 파이프라인 조정"이 이 브리프에서만 가능한 이유(예: 원 과제가 요구한 "반자동화" 정책과 결합해 이 회사 영업 프로세스에 맞춘 특수 승인 기준 등) 제시
  3. 경쟁 가능한 일반적 대안(예: 단순 크롤링+템플릿 이메일 툴)과 비교해 무엇이 실질적으로 더 나은지 근거
  4. 온톨로지·지식그래프가 실제로 어떤 질의/추천을 가능하게 하는지 구체 예시(현재는 "관계 구조화"라는 선언뿐)

**2지망(잇뉴) — 등급: 하**
- 근거: 신규/재이용/이탈 분류(주문일·주기·횟수·최근 이용 기준)와 대시보드·월간 보고서 자동화는 표준 RFM 기반 BI 파이프라인과 구조적으로 동일하며, "온톨로지·지식그래프"는 고객-주문-품목-지역 관계를 "구조화"한다고만 서술될 뿐 관계형 DB의 JOIN/GROUP BY로 동일하게 구현 가능한 수준을 넘어서는 그래프 특유의 질의(다중 홉 추론, 연결 패턴 탐지 등)나 알고리즘이 제시되지 않아 사실상 이름만 바꾼 데이터 모델링에 가깝다. 게다가 '얼른'은 제주 단일 지역 서비스라 "지역별 주문 변화" 차원의 부가가치도 제한적이다.
- 보강 필요:
  1. 온톨로지/지식그래프가 아니면 불가능하거나 현저히 어려운 구체적 분석 사례 1개 이상 제시(예: 다중 홉 관계 기반 이탈 전조 탐지)
  2. 표준 관계형 스키마 + 규칙 기반 분류 대비 그래프 모델의 실익(성능, 유연성 등) 비교
  3. 제주 단일 지역이라는 실제 사업 규모에 맞춘 차별화 지점 재정의(지역 차원 대신 무엇이 더 의미 있는지)
  4. "비정형 품목명 LLM 표준화"가 이 회사 데이터의 특수성(취급 품목의 다양성/오탈자 패턴 등)과 어떻게 연결되는지 근거

근거: 1차에서 지적한 "물류 인력 배치" 표현은 기업 활용 제안에서 "이탈 관리·수요 파악에 분석 결과를 활용할 수 있습니다"로 교체되어 완전히 사라졌고, "머신러닝" 서술도 "데이터 분석과 규칙 기반 분류는 고객 이용 패턴과 이탈 위험을 탐지하는 데 활용"으로 바뀌어 불필요한 ML 요구가 제거됐다. 온톨로지 적용 범위도 "고객·주문·품목·지역 관계는 관계형 데이터로 대부분 충분하지만... 다중 관계를 동시에 추적해야 하는 분석에 한해 지식그래프를 적용합니다"로 좁혀졌다. 그러나 월간 리포트 로직을 구체화하면서 "이상치로 감지된 품목·고객군"이라는 이상치 탐지 요구가 새로 생겨, 등급을 끌어올릴 만큼의 순감소는 아니라고 판단해 등급은 "중"으로 유지했다.

여전히 남은/새로 생긴 리스크:
1. (신규) 월간 리포트 로직이 "(3) 이상치로 감지된 품목·고객군을 LLM이 3줄 요약 + 원인 후보로 정리"까지 포함하도록 구체화되면서, 원래 한 문장이던 리포트 자동화에 이상치 탐지(임계값·알고리즘 설계)라는 새 구현 난이도가 추가됐다.
2. (형태 변경) "특정 상권 + 특정 품목군 조합" 분석으로 좁힌 것은 개선이지만, '얼른'이 제주 본섬 단일 지역 서비스라는 점을 고려할 때 "상권" 단위로 세분화할 데이터가 실제로 존재하는지는 여전히 확인되지 않아, 1차 지적("지역별 세분화가 서비스 규모와 맞는지")이 완전히 해소된 것은 아니다.
3. (잔존) 실제 주문·회원 데이터 접근 여부는 수정안에서도 언급되지 않아 그대로 남아 있다.

**3지망 — 휴플: 1차 등급 상 → 2차 등급 상 (유지)**

근거: 원래도 세 지망 중 가장 스코프가 안정적이었고, 수정안은 출력 스키마를 "제목, 요약, 일정, 관광지, 이동 정보, 준비사항과 유의사항"으로 구체화하고 "검증 실패 시 해당 항목만 담당자 확인 후 재생성을 요청하는 재시도 로직"을 추가해 오케스트레이션 메커니즘을 명확히 했다 — 이 재시도 로직은 일반적인 실패-재처리 패턴이라 스코프를 크게 늘리지 않는다. 다만 신규 추가된 "젠트립이 보유한 기존 여행지 정보(1,400여 개)를 참조 데이터로 활용"은 지원자가 실제로 그 내부 데이터에 접근할 수 있는지가 계획서에 확인되지 않은 채 전제되고 있어, 1차엔 없던 데이터 접근성 리스크를 새로 만든다.

여전히 남은/새로 생긴 리스크:
1. (신규) "젠트립이 보유한 기존 여행지 정보(1,400여 개)를 참조 데이터로 활용"하려면 해당 내부 데이터베이스에 대한 실제 접근권한이 전제되어야 하는데, 접근 가능 여부가 계획서 어디에도 명시되지 않았다.
2. (잔존, 1차와 동일) "검증을 통과한 콘텐츠만 노코드 웹페이지 템플릿에 자동 반영"이 실제 젠트립 CMS·노코드 툴과의 연동을 의미하는지, 자체 렌더러를 의미하는지는 수정안에서도 명확해지지 않았다.
3. (신규/확대) 기업 활용 제안에서 "홈페이지·SNS·제휴사 안내 자료"로 활용 채널이 구체적으로 늘어나, 다채널·다버전 콘텐츠를 단기 트랙 내에서 전량 검증해야 하는 부담이 오히려 커졌다.

### specificity-agent (구체성) — 2차

**총평(비교, 1차 대비)**: 세 지망 모두 1차에서 지적한 "용어만 나열, 메커니즘·수치 없음" 문제를 실제로 개선했으며, 개선 폭은 2지망 > 1지망 > 3지망 순이다. 2지망은 신뢰도 임계값(90%)과 월간 리포트 집계 로직(주기·지표·형식)을 구체적 수치·절차로 제시했고, 온톨로지 적용 범위도 사례 1개로 좁혀 실제 패턴 예시를 붙였다. 1지망은 Clo.D/AI-Studio 매칭을 신호-규칙-제안 표로 구조화하고 온톨로지 노드/엣지 예시(`기업 --(취급업종)--> 패션` 등)를 추가해 1차에서 가장 취약했던 두 항목을 직접 해소했다. 3지망은 오케스트레이션에 재시도 로직 한 문장을 추가했지만, 도구/프레임워크·노코드 플랫폼명 등 인프라 수준의 미명시는 그대로 남아 개선 폭이 가장 작다. 다만 세 지망 공통으로 "신뢰도 산출 알고리즘의 구체 근거"(왜 그 수치인지, 어떤 모델/함수로 계산하는지)와 "문서·그래프 저장 기술" 같은 백엔드 구현 디테일은 여전히 개념 수준에 머무른다.

#### 1지망 — 큰삼촌컴퍼니: **중 → 상**

근거: 1차에서 지적한 "규칙 기반 검증에 실제 if-then 예시가 없다"와 "온톨로지 관계 예시가 없다"는 두 항목이 이번 수정안에서 직접 해소됐다. "Clo.D / Clo.D AI-Studio 매칭 로직" 표는 "자체 촬영 스튜디오 언급 없음 + SNS 상품 이미지 품질 낮음 → Clo.D AI-Studio", "사입·소싱 물량이 크고 정산 프로세스가 수기로 언급됨 → Clo.D B2B ERP 연동 제안"처럼 감지 신호·판별 규칙·추천 제안을 3행 표로 명시했고, "지식 구조" 문단은 `기업 --(취급업종)--> 패션`, `기업 --(촬영역량없음)--> AI-Studio 적합`라는 실제 노드-엣지 예시를 제시해 1차에서 "선언뿐"이라 지적한 부분을 구체화했다.

여전히 남은 모호한 구절:
1. "탐색·분석·전략 생성 단계는 신뢰도 기준(예: 수집된 연락처의 출처 신뢰도, 정보 최신성)을 충족하면 자동으로 다음 단계까지 진행합니다." → 신뢰도의 산출 신호(출처·최신성)는 명시됐으나, 이를 어떻게 점수화하는지(가중치? 0~100점 환산?)와 "충족"의 구체적 임계값(예: 80점 이상)은 여전히 제시되지 않음.
2. "요구사항과 조건은 단계별 문서로 관리되어, LLM이 이를 참조함으로써 사용자의 지시를 일관되게 이행합니다." → 1차 지적(문서 형식·저장 위치·구조 불명)이 문구만 다듬어졌을 뿐(환각없이→일관되게) 그대로 남아 있음. 마크다운/JSON/DB 여부, 고객별/단계별 저장 단위 모두 미정.
3. 매칭 표의 "SNS 상품 이미지 품질 낮음"이라는 판별 기준 자체가 정성적이라 실제 규칙 엔진으로 구현할 때 무엇을 측정하는지(이미지 해상도? 브랜드 사진 유무?) 불명.

#### 2지망 — 잇뉴: **중 → 상**

근거: 1차 지적 세 가지(신뢰도 임계값 없음, 온톨로지 실제 예시 없음, 월간 리포트 집계 로직 불명) 모두에 구체적 응답이 붙었다. 품목 신뢰도는 "문자열 유사도 기반 신뢰도 점수(예: 90% 이상 자동 확정, 그 이하는 담당자 확인)"로 수치 임계값이 제시됐고, 온톨로지는 "특정 상권 + 특정 품목군 조합에서만 반복되는 이탈 전조 패턴"이라는 사례 1개로 좁혀져 지시받은 대로 범위가 구체화됐다. 월간 리포트는 "매월 1일 기준 직전 30일 데이터를 집계해 (1) 신규·재이용·이탈 고객 수 전월 대비 증감률, (2) 품목군별 주문량 상위/하위 변화, (3) 이상치 품목·고객군을 LLM이 3줄 요약 + 원인 후보로 정리하고, 상세 지표는 표로 첨부"처럼 주기·지표·형식이 모두 명시돼 1차에서 "한 문장"이라 지적한 부분이 가장 크게 개선됐다.

여전히 남은 모호한 구절:
1. "문자열 유사도 기반 신뢰도 점수" → 어떤 유사도 알고리즘(편집거리? 자카드? 임베딩 코사인 유사도?)인지는 여전히 미명시. "90%"가 그 알고리즘의 어떤 출력값 스케일인지도 불명.
2. "다중 관계를 동시에 추적해야 하는 분석에 한해 지식그래프를 적용합니다" → 사례는 좁혀졌지만 지식그래프가 실제로 이 패턴을 "어떻게" 탐지하는지(그래프 순회 알고리즘? 임계값 이상의 co-occurrence?)와 저장·조회 기술은 여전히 없음.
3. "데이터 분석과 규칙 기반 분류는 고객 이용 패턴과 이탈 위험을 탐지하는 데 활용" → 1차에서 지적한 "머신러닝" 표현 자체는 삭제되어 모호성은 줄었으나, 그 대체로 제시된 "규칙 기반 분류"의 실제 규칙(예: 몇 회 미이용 시 이탈 위험으로 분류하는지 구체적 컷오프)은 여전히 제시되지 않음.

#### 3지망 — 휴플: **하 → 중**

근거: 1차 지적 중 "재시도·실패 처리 로직 없음"은 "검증 실패 시 해당 항목만 담당자 확인 후 재생성을 요청하는 재시도 로직을 둡니다"로 일부 해소됐다. 그러나 "오케스트레이션 도구/프레임워크 미명시"와 "노코드 플랫폼/템플릿 엔진 불명"은 수정안에서도 그대로 남아, 세 지망 중 개선 폭이 가장 작다.

여전히 남은 모호한 구절:
1. "AI 오케스트레이션은 상품 정보 분석 → 콘텐츠 생성 → 규칙 기반 검증 → 웹페이지 반영의 단계를 관리하며" → 1차 지적대로 어떤 오케스트레이션 도구/프레임워크(예: 상태 머신 라이브러리, LLM 체이닝 프레임워크 등)를 쓰는지 여전히 명시가 없음. "관리"의 실제 구현 방식(코드 기반 워크플로우? LLM 자체 판단?) 불명.
2. "검증을 통과한 콘텐츠만 노코드 웹페이지 템플릿에 자동 반영합니다" → 어떤 노코드 플랫폼/템플릿 엔진인지, 구조화 필드가 화면 컴포넌트로 매핑되는 구체 방식(예: 필드명-컴포넌트ID 매핑표)은 1차와 동일하게 미제시.
3. "검증 실패 시 해당 항목만 담당자 확인 후 재생성을 요청하는 재시도 로직을 둡니다" → 재시도 로직 자체는 추가됐으나, 담당자에게 "어떻게" 표시되는지(알림 채널·화면)와 재시도 횟수 제한·우선순위 기준은 1차 지적대로 여전히 빠져 있음.

### differentiation-agent (차별성) — 2차

**총평(공통 패턴) — 2차**: 1차에서 지적한 "결론 문장 의존"(~를 통해 차별성을 확보할 수 있습니다) 문제에 대해 세 지망 모두 형식적으로는 반응했다 — 1지망은 매칭 규칙표, 2지망은 사례 1개 한정, 3지망은 젠톡 비교 문장을 각각 추가했다. 그러나 "문장을 추가했다"와 "차별화 메커니즘이 실제로 생겼다"는 다르다. 세밀히 보면 1·3지망은 실질적 개선이 있으나 여전히 절반의 숙제만 마쳤고, 2지망은 추가된 사례가 오히려 온톨로지 불필요론을 스스로 입증해 실질 개선이 없다. 결론 문장 뒤에 최소한의 근거가 붙었다는 점에서 총점은 소폭 상향되지만, "경쟁 대안 대비 왜 더 나은가"라는 가장 근본적인 질문에는 세 지망 다 여전히 답하지 못한다.

**1지망(큰삼촌컴퍼니) — 1차 등급: 하 → 2차 등급: 중**

근거: `수행 아이디어 1순위`에 신규 추가된 "Clo.D / Clo.D AI-Studio 매칭 로직" 표(감지 신호 → 판별 규칙 → 추천 제안)는 1차에서 요구한 "Clo.D의 실제 강점을 어떤 해외 고객 특성과 매칭하는지"에 정면으로 답한다 — "자체 촬영 스튜디오 언급 없음 + SNS 이미지 품질 낮음 → AI-Studio(실촬영 대비 1/3 비용·1~2주)", "사입·소싱 물량 크고 정산 수기 언급 → Clo.D ERP 연동"은 웹조사로 확인된 Clo.D의 두 실제 사업(ERP 디지털화, AI 비주얼 콘텐츠 대행)을 각각 다른 고객 신호에 연결한 것으로, 5회 반복되던 "강점 연결"이라는 빈 변수 대신 실제 if-then 규칙이 생겼다. 온톨로지 부분도 `기업 --(촬영역량없음)--> AI-Studio 적합`처럼 노드·엣지 예시를 붙여 "관계 구조화"라는 선언에서 한 걸음 나아갔다.

다만 회의적으로 보면 절반만 해결됐다:
1. **판별 규칙의 판정 기준 자체는 여전히 모호하다.** "SNS 상품 이미지 품질 낮음"을 무엇으로 판정하는지(육안 판단? 해상도 임계값? LLM 채점?), "사입·소싱 물량이 크고"의 "크다"를 어떤 수치로 가르는지 전혀 정의되지 않았다 — 즉 매칭 "구조"는 생겼지만 그 구조에 입력되는 신호의 산출 방법은 1차 specificity-agent가 지적한 "신뢰도 기준" 문제와 동일하게 비어 있다.
2. 1차 보강 요구 2번("자연어 파이프라인 조정이 이 브리프에서만 가능한 이유")과 3번("일반적 대안 대비 비교")은 수정안에 전혀 반영되지 않았다. "전역 LLM 에이전트와의 대화로 조회", "자연어 명령으로 재분석·조건변경·중단"은 수정안에서도 문구만 재배치됐을 뿐 여전히 어떤 리드-투-이메일 과제에도 붙일 수 있는 범용 UX로 남아 있다.
3. 매칭 표의 "위 신호가 모두 약함 → 초기 소개 메일만 발송, 자동 후속 조사 예약" 분기는 형식은 갖췄으나, 이 회사가 아니면 나올 수 없는 설계라기보다는 리드 스코어링 툴의 표준적인 "저관여 트랙" 처리 방식에 가깝다.

종합: 표 형태의 실제 매칭 로직이 생겨 "결론 문장뿐"이라는 1차 핵심 비판은 해소됐으므로 등급을 올리지만, 판정 기준의 산출 방법과 경쟁 대안 대비 우위 논증이 빠져 있어 "상"으로 가기엔 이르다.

**2지망(잇뉴) — 1차 등급: 하 → 2차 등급: 하 (변화 없음)**

근거: 수정안은 온톨로지 적용 범위를 "특정 상권 + 특정 품목군 조합에서만 반복되는 이탈 전조 패턴" 하나로 좁히고, "고객·주문·품목·지역 관계는 관계형 데이터로 대부분 충분하지만"이라는 문장으로 스스로 관계형 DB의 충분성을 인정한 뒤 이 한 사례만 지식그래프의 몫으로 남겼다. 형식상으로는 1차 보강 요구 1번("온톨로지가 아니면 불가능한 구체적 사례 1개 제시")에 정확히 대응하는 모양새다.

그러나 회의적으로 뜯어보면 오히려 역효과다: "특정 상권 × 특정 품목군 조합의 주문 추이·이탈률"은 `GROUP BY 상권, 품목군` 후 시계열 증감을 보는 표준 SQL 집계(OLAP 큐브)로 충분히 계산 가능한 다차원 집계 문제이지, 그래프 특유의 다중 홉 순회(multi-hop traversal)나 연결 패턴 탐지가 필요한 사례가 아니다. 즉 지원자가 "지식그래프가 아니면 안 되는 사례"로 제시한 바로 그 예시가, 사실은 관계형 DB로 더 간단히 풀리는 문제다 — 이는 1차에서 지적한 "이름만 바꾼 데이터 모델링"이라는 진단을 스스로 재확인해 준 꼴이다. 표현이 "관계형 데이터로 대부분 충분"이라고 먼저 인정해버린 것도, 온톨로지 도입의 필요성을 지원자 스스로 약화시킨 셈이다.

1차 보강 요구 대비 처리 현황:
1. 온톨로지 필수 사례 제시 → **표면적으로는 시도, 실질적으로는 실패**(선택한 사례가 관계형으로 더 쉽게 풀림)
2. 관계형 대비 그래프 실익 비교 → 여전히 없음(오히려 "대부분 충분"이라 인정)
3. 제주 단일 지역 규모에 맞는 차별화 재정의 → `기업 활용 제안`에서 "물류 인력 배치" 표현은 삭제되어 현실성·부합도 이슈는 완화됐으나, 이는 차별성 문제와는 별개다.
4. 비정형 품목명 표준화의 회사 특수성 → 여전히 일반적 "유사 표현·오탈자 통합" 서술에 머묾, '얼른' 취급 품목의 특수 패턴 언급 없음.

종합: 문장은 추가됐지만 선택된 근거 사례 자체가 자기모순적이라 실질적 차별화 논증이 성립하지 않는다. 등급을 올릴 근거가 없다.

**3지망(휴플) — 1차 등급: 하 → 2차 등급: 중**

근거: 1차의 핵심 비판은 "젠톡의 존재를 전혀 언급하지 않고 백지 상태인 것처럼 서술한다"는 것이었다. 수정안은 이를 정면으로 다룬다 — "'젠트립'이 이미 운영 중인 생성형 AI 기능('젠톡')은 여행자 대상 추천 챗봇으로, 본 제안은 담당자 대상 콘텐츠·페이지 제작 자동화로 대상과 활용 시점이 다르며"라는 문장은 기존 서비스를 명시적으로 인지하고 사용자군(여행자 vs. 담당자)과 기능(추천 vs. 제작)을 실제로 구분한다. 이는 지어낸 차이가 아니라 원 브리프(담당자용 콘텐츠·페이지 제작 자동화)와 웹조사 결과(젠톡=여행자용 챗봇)에 부합하는 사실 기반 구분이라, 1차에서 지적한 "우연히 안 겹칠 뿐 인지하고 설명한 게 아니다"라는 문제는 해소됐다.

다만 남은 절반은 여전히 약하다:
1. 이 구분은 "대상이 다르다"는 선언 수준을 벗어나지 못한다 — 왜 담당자용 콘텐츠 제작 도구가 젠톡과 기술적으로도 겹치지 않는지(예: 젠톡의 생성 파이프라인을 내부적으로 재사용할 수도 있는데 왜 별도 구축이 필요한지), 혹은 향후 젠톡이 담당자 기능으로 확장될 가능성까지 검토했는지는 전혀 다루지 않는다.
2. "1,400여 개 여행지 정보를 참조 데이터로 활용"은 구체성은 높아졌지만(1차 대비 실제 자산명 언급), 이것이 독자적 메커니즘인지는 의문이다. 기존 DB를 프롬프트/RAG의 참조 데이터로 붙이는 것은 콘텐츠 생성 파이프라인에서 통상적인 구성이며, 오히려 젠톡도 이미 같은 1,400개 데이터를 내부적으로 활용 중일 가능성이 높은데 그 중복 여부조차 검토되지 않았다 — "차별성 확보"의 근거로 내세우기엔 취약하다.
3. 1차 보강 요구 2번("시각적 완성도의 실체")과 3번("여행자 유형별 분기가 프롬프트 템플릿 이상의 메커니즘인지")은 수정안에서 전혀 다뤄지지 않았다. "여행자 유형에 따라 강조 요소와 표현 방식을 다르게 구성"은 수정안에서도 문구가 거의 그대로 남아, 마케팅 콘텐츠 도구의 표준 세그먼트별 템플릿 변형 수준이라는 1차 지적이 유효하다.

종합: 가장 컸던 결함(경쟁 서비스 인지 부재)이 사실 기반으로 해소된 점은 명확한 실질 개선이므로 등급을 올리지만, 그 비교가 "다르다"는 선언에 머물고 시각적 차별화·유형 분기 메커니즘·데이터 중복 여부가 그대로 남아 있어 "상"으로는 부족하다.

**3지망 (휴플) — 1차 등급: 상 → 2차 등급: 상 (유지)**

근거: 1차에서 이미 가장 높은 등급이었고, 2차에서도 1차 리라이트 제안 두 건(예시 4개 나열 → 축 우선 압축, "구조화 출력은 ~ 활용합니다" → 결과 중심 문장)이 거의 문장 그대로 반영됐다. 젠트립 데이터·젠톡 비교 서술이 추가되며 정보량은 늘었지만 문단 분리가 유지되어 가독성은 떨어지지 않았다. 세 지망 중 유일하게 이미 상한선이라 등급 변화는 없으나, 실질적 개선은 확인된다.

잔존 이슈(참고, 1건): "AI 오케스트레이션은 상품 정보 분석 → 콘텐츠 생성 → 규칙 기반 검증 → 웹페이지 반영의 단계를 관리하며..."는 화살표 요약 자체는 좋으나, 1지망 파이프라인 개요의 화살표 표기와 형식이 동일해(두 지망을 이어서 읽으면) 같은 도구를 재사용한다는 인상을 준다. 다만 이는 표현력보다 차별성 영역에 더 가까운 지적이라 감점 요인으로 보지는 않았다.

---

**수행 역량 섹션 — 1차 등급: 하 → 2차 등급: 중**

근거: "관련 경험 및 보유역량"이 지망별로 분리되고 각각 새 어휘(1지망: 규칙 기반 매칭 로직·온톨로지 스키마 / 2지망: RFM 기반 고객 분류·문자열 유사도 기반 품목 표준화 / 3지망: 프롬프트·구조화 출력·노코드 템플릿 연동)를 사용해, "이미 읽은 내용 재진술" 문제와 "1지망 어휘 편중" 문제가 이 항목에서는 실질적으로 해소됐다.

잔존 이슈(2건):
1. "강화하고 싶은 역량" 섹션은 분리되지 않고 여전히 1지망 어휘("해외영업 과정", "다국어 기업 정보의 신뢰도", "이메일 반응 데이터", "매칭 규칙과 제안 전략")로만 쓰여 있다. 특히 "단계별 자동화 정책과 전역 LLM 에이전트를 결합해 사용자가 자동화 범위를 직접 제어할 수 있는 시스템을 구현하고자 합니다"는 1지망 해결아이디어의 "자동화 정책" 문단과 사실상 같은 내용을 문구만 바꿔 반복한다 — 헤딩에는 "[지망별로 분리]"라고 표시돼 있지만 실제로는 보유역량 항목만 분리됐을 뿐 강화하고싶은역량은 분리되지 않아, 표시와 내용이 어긋난다.
2. "다국어 기업 정보의 신뢰도를 판별하는 로직"처럼 1차 리라이트 제안에서 요구한 구체화(부족 지점 명시)는 반영됐지만, 그 문장이 여전히 1지망 사례에만 한정돼 있어 2·3지망에 대한 "강화하고 싶은 역량"은 이 섹션에서 전혀 확인할 수 없다.

## 2차 종합 리뷰

### 등급 변화 매트릭스 (1차 → 2차)

| 기준 | 1지망 큰삼촌컴퍼니 | 2지망 잇뉴 | 3지망 휴플 |
|---|---|---|---|
| 현실성 | 하 → 중 | 중 → 중 | 상 → 상 |
| 구체성 | 중 → 상 | 중 → 상 | 하 → 중 |
| 차별성 | 하 → 중 | 하 → 하 (변화 없음) | 하 → 중 |
| 정합성 | 상 → 상 | 중 → 상 | 중 → 중 |
| 기업니즈부합도 | 중 → 상 | 중 → 상 | 상 → 상 |
| 표현력 | 하 → 상 | 중 → 상 | 상 → 상 |

정적 기준만 보면 전반적으로 확실히 개선됐다. 특히 2지망은 차별성을 제외한 5개 기준에서 "상"에 도달했다. 다만 이 개선이 **문장 수준의 보강**(용어 대신 표·수치·비교 문장 추가)에서 온 것이지, 그 표·수치·규칙이 실제로 앞뒤 단계와 맞물려 작동하는지는 정적 검토만으로는 검증되지 않는다 — 이는 아래 데모 시뮬레이션에서 드러난다.

### 유일하게 개선 안 된 항목: 2지망 차별성 (하 → 하)

온톨로지 적용 범위를 "특정 상권+품목군 조합 이탈전조" 사례 하나로 좁혔지만, differentiation-agent가 지적했듯 이 사례는 지원자 스스로도 "관계형 데이터로 대부분 충분"이라 인정할 만큼 표준 `GROUP BY` 집계로 풀리는 문제라 그래프 특유의 다중 홉 추론이 필요 없다. 좁힌 근거 사례가 오히려 1차 지적("이름만 바꾼 데이터 모델링")을 재확인해 준 역설적 결과다.

## 데모 시뮬레이션 종합

정적 검토(위)에서는 1·2지망 모두 5개 기준 중 다수가 "상"으로 올라섰지만, 실제 샘플 데이터를 넣어 손으로 끝까지 추적해보니 **3개 지망 전부 핵심 메커니즘이 실행 단계에서 무너진다**는 사실이 드러났다. 정적 검토가 "용어가 구체화됐는가"를 봤다면, 시뮬레이션은 "그 구체화된 내용이 실제로 앞뒤 단계와 맞물려 굴러가는가"를 봤고, 결과는 정적 검토보다 훨씬 비판적이다.

| 지망 | 시뮬레이션 등급 | 핵심 결함 |
|---|---|---|
| 1지망 (큰삼촌컴퍼니) | 하 | 매칭 표가 요구하는 판별 신호(촬영 스튜디오 여부, SNS 이미지 품질 등)를 앞 단계(잠재고객 탐색)가 애초에 수집하지 않음 — 단계 간 데이터 단절 |
| 2지망 (잇뉴) | 하 | 90% 유사도 임계값을 실제로 계산하면 완전 동일 상품("감귤 1박스" vs "감귤박스(2호)")조차 자동확정을 통과 못함. "상권" 필드가 스키마에 없어 차별화 근거였던 지식그래프 사례 자체가 재현 불가능 |
| 3지망 (휴플) | 중 | 검증 규칙("날짜·가격·인원 불일치")이 확인하려는 값이 구조화 스키마에 독립 필드로 없어 값 대 값 비교가 설계상 성립하지 않음. 근거 없이 지어낸 콘텐츠(프리미엄 유형)는 검증을 그대로 통과 |

**가장 중요한 결론**: 2차 수정에서 추가한 "구체화 장치"(1지망 매칭표, 2지망 90% 임계값·상권 필드, 3지망 검증 규칙)는 정적으로 읽었을 때는 그럴듯하지만, 실제 데이터로 돌려보면 셋 다 하나같이 **"이 값이 어디서 오는지"가 빠져 있다** — 즉 출력 형식·규칙은 새로 생겼는데 그 규칙에 넣을 입력을 만드는 앞 단계가 설계되지 않은 동일한 패턴의 결함이 반복된다. 표현만 다를 뿐 세 지망 모두 같은 종류의 실수를 하고 있다는 뜻이다.

### 다음 우선 보완 (시뮬레이션 기반, 서면 수정보다 우선순위 높음)

1. **1지망**: 잠재고객 탐색 단계의 수집 필드에 매칭 표가 요구하는 신호(촬영 인프라 여부, 이미지 품질 등)를 명시적으로 추가하거나, 아니면 매칭 표의 신호를 "탐색 단계가 실제로 수집 가능한 필드" 기준으로 다시 설계할 것. 해외 고객 대상 이메일의 발신 언어 정책도 추가.
2. **2지망**: 90% 임계값을 실제 데이터로 검산해 현실적인 값으로 재설정하거나, 유사도 알고리즘 자체를 문자열 유사도 대신 의미 기반(임베딩)으로 바꿀 것. "상권" 필드를 실제 데이터 스키마(예: 배송 행정동)에 추가하지 않으면 차별화 근거였던 지식그래프 사례를 통째로 빼야 함.
3. **3지망**: 구조화 출력 스키마에 날짜·가격·인원을 독립 필드로 추가해 검증 규칙과 실제로 맞물리게 할 것. "근거 없는 창작 방지"를 위한 별도 규칙(예: 원본에 없는 구체적 숫자·시설명 생성 금지)을 추가할 것.

시뮬레이션 상세 근거(가상 샘플, 단계별 추적)는 아래 3개 섹션 참조.

## 데모 시뮬레이션 검토 (수정안 기준)

정적 기준(현실성/구체성/차별성/정합성/기업니즈부합도/표현력) 검토와 별개로, `demo-simulation-agent`가 실제 코드를
작성하지 않고 구체적 가상 샘플 입력을 넣어 `문제수행계획서_수정안.md`의 파이프라인을 단계별로 손으로 추적(dry-run)한다.
목적은 "설계 문서가 실제로 끝까지 실행 가능한가"를 검증하는 것 — 실행 불가 지점과 논리 오류를 찾는다.

### 1지망 시뮬레이션

**가상 샘플 입력** (재현용, 이하 이 값으로 고정)
- 진출 대상 국가: 일본
- 업종: 패션 소매(편집숍)
- 목표 고객 유형: 자체 촬영 스튜디오 없는 중소 온라인 셀러
- 가상 기업: 「ハラジュク・クローゼット株式会社(하라주쿠 클로젯 주식회사)」 — 도쿄 소재, 인스타그램·라쿠텐에서 여성 스트리트웨어를 판매하는 1인~소수 인력 온라인 편집숍. 상품 사진은 스마트폰으로 촬영해 셀프 편집 후 업로드. 월 신규 입고 약 40~60종.

등급: **하** (핵심 단계인 매칭 로직 자체가 실행 불가 — 아래 근거)

---

**1단계 — 잠재고객 탐색**
문서 인용: "사전에 확보한 검증된 B2B 디렉토리·업계 데이터베이스를 우선 소스로 사용하고... LLM이 서비스 특성과 예상 고객 요구를 바탕으로 검색어를 생성하고, 수집된 기업명·주요 사업·제공 상품·연락처를 구조화한 뒤 중복·무관 기업을 제외합니다."

시도한 산출물: LLM이 "Japan online fashion select shop, no in-house photography, Instagram/Rakuten seller"류 검색어를 생성했다고 가정하고, 구조화 레코드를 다음과 같이 만들어 봄.
```
기업명: ハラジュク・クローゼット株式会社
주요 사업: 온라인 패션 편집숍(여성 스트리트웨어)
제공 상품: 캐주얼 의류·액세서리
연락처: info@harajuku-closet.jp
```
**실행 불가 지점 1**: "검증된 B2B 디렉토리·업계 데이터베이스"가 구체적으로 무엇인지(예: 특정 무역 디렉토리명, 협회 회원사 명부, 유료 DB 등) 문서 어디에도 지정되어 있지 않다. 실제로 하라주쿠 클로젯 같은 기업을 "어느 소스에서" 가져올지 결정할 근거가 없어, 이 단계는 소스를 임의로 지어내지 않고는 재현 불가능하다.

---

**2단계 — 기업 정보 구조화**
문서 인용: 1단계와 같은 문단에서 "수집된 기업명·주요 사업·제공 상품·연락처를 구조화" — 즉 구조화 스키마는 **이 4개 필드**뿐이다.

**실행 불가 지점 2 (가장 치명적)**: 다음 3단계(매칭 로직)가 요구하는 판별 신호 — "자체 촬영 스튜디오 언급 없음", "SNS 상품 이미지 품질", "사입·소싱 물량 규모", "정산 프로세스가 수기인지 여부" — 는 이 4개 필드(기업명·주요 사업·제공 상품·연락처) 중 어디에도 담을 자리가 없다. 즉 2단계 산출물을 그대로 3단계에 넣으면 판별에 쓸 입력값이 아예 없다. 이는 용어가 모호한 수준이 아니라, 파이프라인 두 단계 사이에 데이터가 실제로 이어지지 않는 구조적 단절이다.

---

**3단계 — Clo.D/AI-Studio 적합도 판별 (매칭 로직 표 적용)**

표를 하라주쿠 클로젯에 그대로 적용 시도:
| 신호 | 판정 시도 |
|---|---|
| 자체 촬영 스튜디오 언급 없음 | 샘플 설정상 "없음" — 해당 |
| SNS 상품 이미지 품질 낮음 | **판별 불가** — "낮음"을 무엇으로 재는지(해상도? 배경 유무? LLM Vision 점수 임계값?) 문서에 정의가 없어, 사람이 육안으로 봐도 "낮다"는 것을 시스템 규칙으로 재현할 수 없음 |
| 사입·소싱 물량이 크고 정산 프로세스가 수기로 언급됨 | 샘플상 소규모 셀러이므로 비해당으로 가정 |

**실행 불가 지점 3**: "SNS 상품 이미지 품질 낮음"의 판별 기준(지표·모델·임계값)이 전혀 없다. 이 신호 없이는 표의 첫 행 자체를 발동시킬 수 없다.

**논리 오류 1**: "사입·소싱 물량이 크고 정산 프로세스가 수기로 언급됨"은 기업의 내부 매입·회계 운영 방식에 대한 정보로, 통상 홈페이지·SNS·B2B 디렉토리 같은 외부 공개 소스에서는 확인되지 않는 항목이다. 즉 이 규칙이 요구하는 근거를 1~2단계가 애초에 수집할 방법이 없다 — 규칙 자체가 자신이 참조할 데이터 소스와 어긋난다.

| "감귤 1박스"(O2) vs "감귤 1박스"(O5) | **100%** | 완전 동일 문자열(유일하게 자동확정 가능) |

→ **논리 오류 ①**: 90% 이상만 자동확정한다는 규칙을 그대로 적용하면, 완전히 같은 상품이지만 띄어쓰기·괄호만 다른 O1↔O6, O3↔O8조차 50%로 90% 문턱을 넘지 못해 전부 "담당자 확인"으로 넘어간다. 즉 손으로 계산해보면 자동확정되는 경우는 사실상 "원문이 토씨 하나 안 틀리고 완전히 같은 경우"뿐이라, "비정형 품목명 표준화로 수작업 분류 시간을 줄인다"(101행, 기업 활용 제안 2순위)는 약속과 정반대로 수작업 부담이 거의 줄지 않는 결과가 나온다. 공백·괄호 제거 같은 전처리를 먼저 거치면 결과가 크게 달라지지만, 이 전처리 단계 자체가 문서 어디에도 없다.
→ **논리 오류 ②**: "감귤 1박스" vs "감귤박스(2호)"가 20%로 낮게 나온 것은 알고리즘이 "수량 표기"와 "규격 코드"라는 의미 차이를 이해해서가 아니라, 우연히 문자 구성이 갈렸기 때문이다. 즉 이 방식은 맞을 때도 "우연히" 맞는 것이라 신뢰할 수 없는데, 문서는 이를 핵심 자동화 장치로 서술한다.
→ 확인 결과(4단계 지시사항): "그 산출 방식이 문서에 정의되어 있는가" → **아니오.** 어떤 유사도 알고리즘(편집거리, 바이그램, 코사인 임베딩 등)인지, 정규화(공백/괄호 제거, 오탈자 사전) 여부, 90%라는 숫자가 어떤 척도에서 나온 것인지 전혀 정의되어 있지 않다. 알고리즘 선택에 따라 같은 쌍도 20%~100%까지 결과가 널뛴다.

#### 3단계 — "상권+품목군 이탈전조" 지식그래프 사례 재현 시도

인용(63~64행): "고객·주문·품목·지역 관계는 관계형 데이터로 대부분 충분하지만, '특정 상권 + 특정 품목군 조합에서만 반복되는 이탈 전조 패턴'처럼 다중 관계를 동시에 추적해야 하는 분석에 한해 지식그래프를 적용합니다."

→ **실행 불가 지점 ③(가장 심각)**: 내 샘플 데이터(그리고 문서 전체에 서술된 어떤 데이터 스키마)에도 "상권"에 해당하는 필드가 없다. 주문 레코드는 주문일·고객ID·품목명·수량뿐이고, 회원 데이터에 대한 서술(59~61행)에도 지역·상권·수거 권역 항목이 언급되지 않는다. 이 순위 전체에서 지식그래프 적용을 정당화하는 유일한 구체적 예시가 바로 이 사례인데, 그 사례를 구동할 입력 필드 자체가 정의돼 있지 않아 손으로도 재현이 안 된다.

시뮬레이션을 진행해보려고 임의로 "상권" 필드를 만들어 붙여봤다(문서에 없는 내용을 내가 발명한 것임을 명시): C001·C004·C005를 "제주시 A동", C003을 "서귀포시 B동"으로 가정하면, "제주시 A동 + 감귤류" 조합에서 C004가 5/2 이후 무주문 상태라는 정도는 만들어낼 수 있다. 그러나 —
→ **실행 불가 지점 ④**: "반복되는 패턴"이라 부르려면 최소 몇 건의 유사 사례(최소 지지도)가 있어야 통계적으로 의미가 있는데, 8건짜리 샘플에서 같은 상권+품목군 조합에 해당하는 고객은 사실상 1~2명뿐이라 "반복"을 주장할 근거가 없다. 이 최소 지지도(예: "동일 조합에서 3건 이상")도 문서에 없다.
→ 결론: 이 사례는 (a) 입력 필드 부재, (b) 반복 판정 최소 건수 부재라는 이중의 벽에 막혀, 임의로 데이터를 발명하지 않고서는 한 걸음도 진행할 수 없다.

#### 4단계 — 월간 리포트 자동화

인용(67행): "매월 1일 기준 직전 30일 데이터를 집계해 (1) 신규·재이용·이탈 고객 수 전월 대비 증감률, (2) 품목군별 주문량 상위/하위 변화, (3) 이상치로 감지된 품목·고객군을 LLM이 3줄 요약 + 원인 후보로 정리하고, 상세 지표는 표로 첨부."

품목군은 2단계의 90% 자동확정이 거의 작동하지 않으므로, 담당자가 수동 확정했다고 가정하고 진행(감귤류: O1,O2,O3,O5,O6,O8 / 한라봉류: O4 / 축산물: O7).

| 지표 | 5월(전월) | 6월(당월) | 증감 |
|---|---|---|---|
| 신규 고객 수 | 1 (C001) | 2 (C002, C005) | +100% |
| 재이용 고객 수 | 1 (C004) | 1 (C001) | 0% |
| 이탈위험 고객 수 | 산출 불가(임계값 미정) | 산출 불가(임계값 미정) | 산출 불가 |
| 감귤류 주문 건수 | 1 | 3 | +200% |
| 한라봉류 주문 건수 | 1 | 0 | -100%(소멸) |
| 축산물 주문 건수 | 0 | 1 | 신규 진입 |

LLM 3줄 요약(직접 작성해봄):
1. "6월 신규 고객은 전월 대비 2배 증가(1명→2명)했고, 재이용 고객은 1명으로 유지되었습니다."
2. "감귤류 주문은 전월 대비 3배로 늘어 1위를 유지했고, 한라봉류는 6월 주문이 끊겨 순위에서 사라졌습니다."
3. "이탈위험 고객 수와 이상치 품목·고객군은 판정 기준(이용주기 대비 지연일수, 이상치 탐지 알고리즘)이 정의되지 않아 자동 산출이 불가능했습니다."

→ (2)번 지표(품목군 상위/하위 변화)는 담당자 수동 확정을 전제하면 실제로 계산이 끝까지 진행된다 — 이 부분은 문서의 의도대로 작동하는 몇 안 되는 지점이다.
→ **실행 불가 지점 ⑤**: (3) "이상치로 감지된 품목·고객군"의 판정 방법(z-score, IQR, 이동평균 대비 편차, 혹은 LLM의 주관적 판단인지)이 문서에 없어, 무엇을 "이상치"라 부를지부터 합의가 없으면 이 항목은 사람이 별도 정의를 내려주기 전까지 자동 생성되지 않는다.
→ **논리 오류 ③**: "신규→재이용" 전환의 판정 시점(주문 발생월 기준인지 리포트 생성월 기준인지)이 없어서, 이번 달 "신규"로 잡힌 고객(C005)이 다음 달에도 주문하면 "재이용"이 되는데, 두 리포트가 같은 고객을 다른 이름표로 두 번 언급하면서도 "이번 달 신규 증가분"이 다음 달 "재이용 증가분"과 어떻게 정합적으로 이어지는지 검증할 방법이 없다. 즉 월별 리포트를 연속으로 두 번 손으로 돌려보면(6월, 7월) 같은 고객이 서로 다른 범주로 옮겨가면서 두 리포트 사이의 숫자가 서로를 설명하지 못하는 자기모순이 드러난다.

#### 종합

**등급: 하**

부분적으로는 작동한다 — 완전히 동일한 문자열의 자동확정(2단계 100% 사례), 품목군별 물량 상위/하위 비교(4단계 (2)번 지표, 담당자 수동 확정을 전제할 때)는 손으로 끝까지 계산이 된다. 그러나 이 순위의 핵심 근거로 제시된 지식그래프 사례는 입력 필드조차 없어 원천적으로 재현 불가능했고, 고객 분류·이탈 판정·이상치 탐지 등 나머지 핵심 로직은 임계값·알고리즘이 없어 다수의 지점에서 실행이 멈췄다.

**실행 불가 지점 (5건)**
1. 이탈위험 판정 임계값(지연일수 기준) 부재 — C003(81일 공백)과 C004(60일 공백, 정상 주기일 수도 있음)를 구분해 확정할 수 없음.
2. "이탈 고객 수" 집계에 필요한 전체 활성 고객 명부의 존재·위치가 문서에 없어, 이탈 지표의 분모를 정의할 수 없음.
3. 지식그래프 사례("상권+품목군 이탈전조")의 핵심 입력 필드인 "상권"이 회원·주문 데이터 스키마 어디에도 정의되어 있지 않음 — 이 순위 전체에서 지식그래프를 정당화하는 유일한 구체 사례가 재현 불가.
4. 위 사례를 임의로 데이터를 발명해 진행해도, "반복되는 패턴"을 주장하기 위한 최소 지지도(동일 조합 최소 발생 건수)가 정의되어 있지 않음.
5. 월간 리포트 (3) "이상치로 감지된 품목·고객군"의 판정 알고리즘(z-score/IQR/LLM 주관 판단 등)이 없어 자동 생성이 사람의 사전 정의 없이는 멈춤.

**논리 오류 (3건)**
1. "문자열 유사도 90% 이상 자동확정" 규칙을 실제 유사 표현(공백·괄호 차이)에 적용하면 완전 동일 상품조차 50% 선에 그쳐 자동확정되지 않는다 — "수작업 시간을 줄인다"는 활용 제안과 정반대 결과가 나올 수 있다.
2. 유사도 점수가 낮게 나와 다른 상품처럼 "정확히" 갈린 사례("감귤 1박스" vs "감귤박스(2호)", 20%)도 실제로는 알고리즘이 의미(수량 표기 vs 규격 코드)를 이해해서가 아니라 우연히 문자 구성이 갈린 것뿐이라, 신뢰할 수 없는 방식임에도 핵심 자동화 장치로 서술되어 있다.
3. "신규→재이용" 전환의 기준 시점이 없어, 연속된 두 달의 리포트를 손으로 돌려보면 같은 고객(C005)이 서로 다른 리포트에서 다른 범주로 집계되며 두 리포트의 숫자가 서로를 설명하지 못하는 자기모순이 생긴다.

**정적 검토가 놓쳤을 새로운 발견**
- 정적 검토(fit-agent, specificity-agent)는 이미 "온톨로지·지식그래프가 굳이 필요한지 의문"이라거나 "신뢰도 산출 방식이 불명확하다"는 추상적 지적을 했다. 손으로 데이터를 넣어 추적해보니 이보다 한 단계 더 구체적인 문제가 드러난다: 지식그래프는 "불필요할 수도 있다"는 수준이 아니라, 서술된 데이터 스키마로는 그 유일한 예시조차 물리적으로 구동할 필드가 없다는 것이다("필요성 의문"이 아니라 "재현 자체가 불가능").
- "90% 자동확정"도 정적 검토는 "임계값의 산출 방식이 안 밝혀져 있다"는 데서 멈췄지만, 실제로 손으로 대표적인 한국어 띄어쓰기·괄호 변형 사례에 계산기(문자 바이그램 Jaccard)를 대입해보면, 완전 동일 상품조차 이 임계값을 통과하지 못한다는 것이 확인된다. 즉 "수치가 안 밝혀졌다"가 아니라 "밝혀지지 않은 채로 이 임계값을 그대로 쓰면 자동화 효과가 사실상 없어질 수 있다"는, 더 구체적이고 더 나쁜 결론이다.
- 신규→재이용 분류가 "월 단위 스냅샷"으로 반복 실행될 때 발생하는 시점 간 정합성 문제(두 번째 리포트가 첫 번째 리포트의 분류를 뒤집는 자기모순)는, 문서를 한 번 읽는 정적 검토로는 드러나지 않고 실제로 두 개의 연속된 리포트 주기를 손으로 돌려봐야만 보이는 문제였다.

**단계 1 — 상품 정보 분석**

문서 인용: "관광상품의 기본 정보와 보유 자료를 입력하면 소개 문구, 주요 일정, 추천 대상, 핵심 관광 요소, 이용 안내와 웹페이지 구성안을 생성하는 AI 콘텐츠 제작 파이프라인을 구현합니다."

드라이런: 위 샘플 입력을 그대로 파싱하면 시간대(09:00~13:00), 가격 2단계(성인/소인), 인원 범위(2~8인), 포함/불포함, 운영기간, 유의사항까지는 필드 단위로 추출 가능하다 — 이 단계 자체는 실행 가능.

**실행 불가 지점 1**: 담당자가 웹용 폼에 입력하는 시점에 "지역"이 별도 구조화 필드(드롭다운 등)로 존재하는지, 아니면 상품명 자유 텍스트("우도 반나절…") 안에서 LLM이 지명을 추출해야 하는지가 문서에 없다. 후자라면 "우도"라는 지명이 상품명에 없는 경우(예: "반나절 스노클링 투어"만 입력) 3단계(젠트립 데이터 연동)에서 무엇을 기준으로 검색할지 정의되지 않는다.

**단계 2 — 콘텐츠 생성 (유형별)**

문서 인용: "동일한 상품도 가족 여행, 청년 여행, 프리미엄 여행 등 고객 유형에 따라 강조 요소와 표현 방식을 다르게 구성합니다."

실제로 나올 법한 결과물:
- **청년 여행자용**: "성산항에서 배로 15분, 우도의 에메랄드빛 바다에 풍덩! 장비 대여 포함이라 몸만 오면 되고, 스노클링 끝나면 우도 카페에서 인생샷과 시원한 음료 한 잔까지. 4시간이면 충분한 반나절 완전 정복 코스, 45,000원."
- **가족 여행자용**: "아이와 함께 안전하게 즐기는 우도 물놀이. 스노클링 장비는 모두 대여되고, 만 8세 미만은 보호자 동반이 원칙이라 안심하고 참여할 수 있습니다. 물놀이 후엔 우도 카페에서 함께 쉬어가는 4시간 코스."
- **프리미엄 여행자용**: "번잡함 없이 즐기는 우도 소규모 프라이빗 스노클링. 여유로운 페이스로 바다를 즐긴 뒤, 우도 카페에서 온전히 나만을 위한 휴식 시간을 가져보세요."

**논리 오류 1**: 프리미엄 버전 문구의 "소규모 프라이빗"·"여유로운 페이스"는 원본 입력 어디에도 근거가 없다. 샘플 입력은 최대 8인 단체 운영, 고정 장비·고정 일정이라 "프라이빗"·"전용 가이드" 같은 프리미엄 차별화 속성이 원천적으로 없다 — LLM이 페르소나 지시를 이행하려면 입력에 없는 속성을 지어낼 수밖에 없는 구조다. 이 지점은 뒤의 검증 단계(단계 4)에서도 잡히지 않는다(아래 참조).

**실행 불가 지점 2**: 3개 유형이 상품 등록 시 자동으로 모두 생성되는지, 담당자가 유형을 지정해야만 생성되는지가 불명확하다. "여행자 유형과 상품 조건에 따라 콘텐츠와 화면 구성이 달라지는 기능"(선택사유)이라는 서술만으로는, 최초 실행 시 화면에 무엇이 먼저 뜨는지(기본값 1종? 3종 동시?) 결정할 수 없어 이 단계의 첫 출력물 자체를 확정할 수 없다.

**단계 3 — 구조화 출력 (제목/요약/일정/관광지/이동정보/준비사항/유의사항)**

문서 인용: "생성 결과는 제목, 요약, 일정, 관광지, 이동 정보, 준비사항과 유의사항 등 구조화된 형식으로 관리해, 웹페이지 템플릿과 안정적으로 연결하고 특정 항목만 재생성할 수 있도록 합니다."

실제 채운 예시(청년형 기준):
```
제목: 우도 반나절 스노클링+카페 투어
요약: 성산항에서 배로 15분, 우도 바다에서 스노클링을 즐기고 우도 카페에서 마무리하는 4시간 코스. 장비 대여·음료 1잔 포함.
일정: 09:00 성산항 집합 → 09:30 도항선 승선 → 09:50 우도 도착 → 10:00~11:30 스노클링 → 11:30~12:30 카페 투어 → 12:30 도항선 승선 → 13:00 종료
관광지: 우도(서빈백사·검멀레해변 인근 스노클링 포인트), 우도 카페거리
이동정보: 성산항 여객선터미널 ↔ 우도 도항선(편도 약 15분)
준비사항: 수영복, 여벌옷, 수건, 자외선 차단제 (스노클링복 개인 지참 — 현장 대여 가능 여부는 입력값에 없음)
유의사항: 우천·풍랑주의보 시 자동 취소·전액 환불, 만 8세 미만 보호자 동반 필수, 최소 2인~최대 8인
```

**논리 오류 2 (핵심 발견)**: 검증 대상인 "날짜·가격·인원"이 이 7개 스키마 필드 어디에도 독립 필드로 존재하지 않는다. 가격(45,000원/35,000원), 운영기간(2026-08-01~09-30), 인원(2~8인)은 모두 "요약"이나 "유의사항"의 자유 텍스트 안에 산문 형태로 섞여 들어갈 뿐이다. 즉 다음 단계(규칙 기반 검증)가 "날짜·가격·인원 불일치를 확인"하려면 구조화된 필드 대 필드 비교가 아니라, 자유 텍스트에서 숫자·날짜 패턴을 다시 파싱해내야 한다 — 스키마 설계와 검증 설계가 서로 다른 표현 형식을 전제하고 있어 그대로는 맞물리지 않는다.

**단계 4 — 규칙 기반 검증 (일정 순서 · 필수 정보 누락 · 날짜·가격·인원 불일치)**

문서 인용: "규칙 기반 검증은 일정 순서, 필수 정보 누락, 날짜·가격·인원 불일치를 확인하며, 검증을 통과한 콘텐츠만 노코드 웹페이지 템플릿에 자동 반영합니다."

샘플에 실제로 적용:
- **일정 순서**: 청년형 "일정" 필드는 09:00→13:00 시간순으로 통과. 다만 가독성을 위해 가족형 "요약"에서 "우도 카페에서 여유롭게 시작해 물놀이로 마무리"처럼 서사 순서를 실제와 다르게 쓸 수 있는데, 검증이 구조화된 "일정" 필드만 보는지 "요약" 문장까지 보는지 문서에 명시가 없어 후자라면 오탐(false positive) 가능성이 있다.
- **필수 정보 누락**: 7개 필드 중 무엇이 "필수"인지 정의가 없다. 내 샘플의 "스노클링복 미지참 시 현장 대여 가능 여부 미기재"가 "누락"으로 플래그되어야 정상일 텐데, 이 항목이 필수 판정 대상에 포함되는지조차 규칙이 없어 통과/실패 여부를 손으로도 결정할 수 없다.
- **날짜·가격·인원 불일치**: 단계 3에서 지적한 구조적 문제 때문에 여기서 실제로 막힌다. 예컨대 프리미엄형 문구에 "소규모 프라이빗 그룹"이라는 표현이 들어가더라도, 이는 원본과 "모순"되는 값(예: "최대 20인"처럼 8인과 충돌하는 명시적 숫자)이 아니라 원본에 없는 값을 새로 지어낸 것이라, "불일치 확인"이라는 규칙의 정의(값 대 값 비교) 자체가 이런 종류의 오류를 겨냥하지 않는다. 즉 **모순은 잡아도 근거 없는 창작은 통과시키는** 구조다.

**논리 오류 3**: 검증 규칙명은 "불일치"(contradiction)를 탐지 대상으로 못박고 있어, 위와 같이 "모순되진 않지만 근거 없는 값"이 삽입되는 상황(내 샘플의 프리미엄 버전)은 정의상 규칙의 탐지 범위 밖에 있다. 검증 통과 → 다음 단계로 자동 진행되므로, 이 상태 그대로면 근거 없는 프리미엄 문구가 노코드 웹페이지에 그대로 반영된다.

---

**단계 5 — 젠트립 기존 여행지 데이터(1,400여 개) 연동**

문서 인용: "LLM은 입력된 관광상품 정보와 함께, 젠트립이 보유한 기존 여행지 정보(1,400여 개)를 참조 데이터로 활용해 주변 연계 관광지·이동 동선을 소개 콘텐츠에 반영합니다."

드라이런(우도 샘플에 적용): "우도"라는 지역이 인식됐다고 가정하면, 1,400개 중 우도 관련 후보로 우도봉·서빈백사·검멀레해변·하고수동해수욕장·우도 등대공원·땅콩아이스크림 거리 등이 뽑혀 "관광지" 필드나 요약에 "투어 종료 후 도보 거리의 우도 땅콩아이스크림 거리에서 마무리하기 좋습니다" 같은 문장으로 반영될 수 있다 — 이 자체는 그럴듯하다.

**실행 불가 지점 3**: 1,400개 데이터가 "지역" 같은 구조화 태그로 검색 가능한 DB인지, 자유 텍스트 설명을 임베딩 검색(RAG)해야 하는 비정형 자료인지 문서에 없다. 전자라면 "우도"로 필터링해 후보를 뽑는 절차가 명확하지만, 후자라면 "카페"라는 단어가 우도가 아닌 다른 지역 카페를 연상시켜 엉뚱한 연계 관광지가 섞여 들어올 위험이 있고, 어느 쪽인지 몰라 이 단계의 신뢰도를 손으로도 가늠할 수 없다.

**실행 불가 지점 4**: "이동 동선을 소개 콘텐츠에 반영"하려면 최소한 지점 간 거리·소요시간 데이터(좌표, 도보/차량 이동시간)가 필요한데, 1,400개 데이터가 명칭·설명 수준인지 좌표·이동시간까지 포함하는지 불명이다. 후자가 아니라면 "이동 동선 반영"은 별도의 지도·라우팅 API 연동을 전제해야 하나 문서 어디에도 그런 연동은 언급되지 않는다.

---

**단계 6 — 웹페이지 반영 (노코드 템플릿)**

문서 인용: "검증을 통과한 콘텐츠만 노코드 웹페이지 템플릿에 자동 반영합니다."

**실행 불가 지점 5**: 노코드 플랫폼이 구체적으로 무엇인지(젠트립 자체 CMS? Webflow류 외부 툴? 자체 제작 템플릿 렌더러?) 문서에 전혀 없어, "제목→헤더 컴포넌트, 일정→타임라인 컴포넌트"처럼 필드-화면 매핑을 흉내조차 낼 수 없다. 단계 3의 7개 필드를 그대로 화면에 흘려 넣는다고 가정해도, 이미지(보유자료로 준 스노클링 포인트 사진 5장·카페 사진 3장)를 어느 필드에 어떤 개수·배치로 넣을지 규정이 없어 "웹페이지 구성안"의 최종 산출물을 손으로도 완성할 수 없다.

---

**종합**

등급: **중**. 단계 1·2·5는 (일부 실행 불가 지점을 남기더라도) 손으로 그럴듯한 결과물을 만들어낼 수 있었고, 세 지망 중 가장 끝까지 따라가기 쉬운 파이프라인이라는 기존 정합성·기업부합도 검토의 평가와 일치한다. 다만 단계 3~4에서 구조화 스키마와 검증 규칙이 서로 다른 값 표현(필드 vs 자유 텍스트)을 전제하는 설계 결함이 실제로 걸림돌이 되었고, 단계 6은 정보 부족으로 아예 흉내를 낼 수 없었다.

**실행 불가 지점 (5건)**
1. 상품명 자유 텍스트에서 지역을 추출하는지, 별도 구조화 필드가 있는지 불명(단계 1) — 젠트립 데이터 연동의 검색 기준 자체가 불확실.
2. 3개 고객 유형이 자동 전체 생성인지 담당자 지정 생성인지 불명(단계 2) — 최초 실행 결과물을 확정할 수 없음.
3. 젠트립 1,400개 데이터가 구조화 태그 검색인지 자유 텍스트 임베딩 검색인지 불명(단계 5) — 연계 관광지 추천의 정확도를 가늠할 수 없음.
4. 이동 동선 반영에 필요한 좌표·소요시간 데이터가 1,400개 DB에 포함되는지 불명(단계 5) — 별도 라우팅 API 필요 여부 불확실.
5. 노코드 플랫폼/템플릿 엔진이 무엇인지 전혀 언급 없어(단계 6) 필드-컴포넌트 매핑과 이미지 배치를 흉내낼 수 없음(정적 검토도 이미 지적했으나, 드라이런으로도 실제 마지막 단계 전체가 막힘을 재확인).

**논리 오류 (3건)**
1. 구조화 출력 스키마(제목/요약/일정/관광지/이동정보/준비사항/유의사항)에 가격·날짜·인원이 독립 필드로 없는데, 검증 규칙은 "날짜·가격·인원 불일치"를 확인한다고 명시 — 검증 대상 값의 존재 위치(자유 텍스트)와 검증 방식(값 비교)이 스키마 설계와 맞물리지 않는다.
2. "불일치(모순) 확인"이라는 규칙 정의는 원본과 상충하는 값은 잡아도, 원본에 없던 값을 새로 지어내되 기존 값과 충돌하지 않는 경우(예: 프리미엄형의 "소규모 프라이빗 그룹")는 정의상 탐지 범위 밖이라 그대로 통과된다.
3. "일정 순서" 검증이 구조화된 "일정" 필드 대상인지 "요약" 등 서술문 안의 순서까지 포함하는지 불명해, 서사적 재배열(가독성을 위해 카페를 먼저 언급하는 표현)이 실제 오류가 아닌데도 오탐될 여지와, 반대로 검증을 좁게 설계하면 서술문 안의 실제 시간 모순은 못 잡을 여지가 공존한다.

**정적 검토가 놓쳤을 새로운 발견**
- 기존 specificity-agent(2차)는 3지망을 "1차 지적 중 재시도 로직은 반영됐으나 오케스트레이션 도구·노코드 플랫폼 미명시는 그대로"라고 진단했지만, 이번 드라이런에서 드러난 더 근본적인 문제는 그 이전 단계 — **구조화 출력 스키마 자체가 검증 규칙이 요구하는 값(가격·날짜·인원)을 필드로 담고 있지 않다**는 설계 층위의 불일치다. 정적 검토는 "노코드 플랫폼이 뭔지 안 적혀 있다"는 누락은 잡았지만, "적혀 있는 두 절차(스키마·검증)가 서로 다른 데이터 형태를 전제해 맞물리지 않는다"는 점은 문장 단위 검토로는 포착되지 않았다.
- "규칙 기반 검증"이 정의상 모순(contradiction)만 겨냥하고 무근거 창작(fabrication)은 겨냥하지 않는다는 점도 새로운 발견이다 — 이는 프리미엄 유형처럼 원본 입력에 차별화 근거가 없는 페르소나를 생성할 때 특히 위험한데, 프리미엄 유형 자체가 이런 위험에 가장 취약하다는 점 역시 기존 6개 정적 에이전트 리뷰에서는 언급된 적이 없다.
- 젠트립 연동을 실제로 손으로 돌려보니, "1,400여 개 여행지 정보"라는 숫자는 여러 차례(선택사유·해결아이디어·기업활용제안) 반복 인용되지만, 그 데이터가 검색 가능한 구조인지조차 문서 전체에 한 번도 서술되지 않는다는 점이 두드러진다 — 반복 인용된 숫자의 신뢰도와 실제 활용 가능성은 별개라는 점을 정적 검토는 다루지 않았다.

**새로 발견/잔존하는 실행 불가 지점 및 논리 오류 (5개)**

1. **[신규, 최중대] "자체 촬영 여부" 신호의 관찰 방법과 매칭 의도의 불일치** — 문서가 제시한 관찰 방법(스톡사진 표기·이미지 중복검색)은 "본인이 찍었는가"만 판별하며 "전문 스튜디오 촬영인가 스마트폰 셀프촬영인가"는 구분하지 못한다. 그 결과 스마트폰 셀프촬영 셀러(전형적 AI-Studio 타깃)가 오히려 "자체 촬영 여부: 예"로 분류되어 규칙 1의 발동 조건("아니오")을 충족하지 못한다. 필드명과 관찰 방법이 실제로 판별하려는 개념(전문 촬영 인프라 유무)을 담아내지 못하는 설계 결함.
2. **[신규] "이미지 갱신 빈도" 임계값의 방향이 목표 고객 프로필과 충돌** — "주 1회 미만이면 낮음"이라는 기준을 활발히 신상품을 올리는 소규모 셀러(월 40~60종)에 적용하면 "높음"으로 판정되어 규칙 1의 두 번째 조건도 불충족된다. 그러나 "저비용으로 이미지를 자주 만들어야 하는" 고빈도·저품질 셀러야말로 AI-Studio의 실질적 잠재 수요층에 가까울 수 있어, 임계값의 방향이 실제 목표 고객 정의와 어긋난다.
3. **[신규, 동일 계열 재발] "취급 SKU 규모: 큼"의 수치 임계값 부재** — v1이 지적했던 "SNS 이미지 품질 낮음, 판별 기준 없음"과 동일한 유형의 문제가 필드만 바뀐 채 재발했다. "판매채널 수 ≥3"처럼 명시적 수치가 있는 항목이 있는 반면 "큼"은 여전히 정성적 표현에 머물러 있고, 샘플에 주어진 정보(월 신규 입고량)만으로는 값 자체를 산출할 방법도 없다.
4. **[잔존, 미해소] 잠재고객 탐색 소스 미지정** — "사전에 확보한 검증된 B2B 디렉토리·업계 데이터베이스"가 구체적으로 무엇인지는 v2에서도 v1과 동일한 문구로 남아 있어 여전히 지정되지 않았다. 이 소스가 무엇인지 정의되지 않으면 1단계부터 재현 불가능하다는 v1의 지적이 그대로 유효하다.

(참고, 5개 한도 밖) "접근 메시지 톤 결정" 단계가 새로 추가한 기준 중 "신규 채널 확장이 목적으로 보이는 기업"은 4개 매칭 신호 수집 필드 어디에도 대응하지 않는 새로운 미관찰 신호이며, 이 역시 "표에 쓸 값을 어느 단계가 수집하는가"라는 동일한 성격의 소규모 단절이다.

→ 다만 **완전히 해소되지는 않는다(부분 해소)**: 정규화 후에도 문자열이 다른 나머지 쌍(예: "제주감귤2호박스" vs "감귤박스2호" — 접두사 "제주" 유무만 다르고 사실상 동일 규격일 가능성이 큼)은 임베딩 0.85 임계값 구간으로 넘어가는데, 이 구간의 실제 통과 여부는 실제 임베딩 모델을 돌려보기 전에는 손으로 검증할 수 없다. 즉 v1의 결함은 "정규화가 필요한 흔한 변형(공백·괄호)"에 대해서는 완전히 고쳐졌지만, "정규화로 못 잡는 접두사·어순 차이" 구간은 여전히 검증 불가능한 블랙박스(임베딩 모델의 실제 거동)로 남는다.

#### 4. 지식그래프 — 행정동 필드 재현 + 최소 지지도 5건 재계산

인용(84~85행): "'행정동'은 별도 신규 조사 없이 회원 배송 주소 데이터에서 행정동 단위를 추출해 저장하는 필드로 정의합니다. 동일 조합이 최근 3개월 내 5건 이상 반복돼야 패턴으로 인정."

→ **필드 정의 문제(v1 실행 불가 지점③)는 해소**된다 — "상권"이라는, 문서 어디에도 스키마가 없던 발명된 필드 대신, v2는 회원 배송주소(당일 수거·배송 서비스라면 반드시 존재)에서 파생 가능한 "행정동"으로 대체했다. 한국 배송주소는 통상 "OO시 OO동" 표기를 포함하므로 이 전제는 현실적이며, 실제로 이번 표에 [행정동] 열을 데이터 발명 없이 채울 수 있었던 것 자체가 그 증거다.

최소 지지도(3개월 내 5건)를 실제로 적용:

| 조합 | 전체 이력상 건수 | "최근 3개월"(4/1~6/30, 7/1 기준) 내 건수 |
|---|---|---|
| 이도이동 + 감귤류 | 5건(O1,O3,O5,O6,O8) | **4건**(O3,O5,O6,O8 — O1은 3/1이라 3개월 창 밖) |

→ **최소 지지도 규칙 자체의 부재 문제(v1 실행 불가 지점④)는 해소**된다(수치가 명시돼 계산 가능). 그러나 실제로 계산해보니, 이 순위의 지식그래프 적용을 정당화하는 유일한 사례가 **정확히 문턱값에 1건 못 미쳐 패턴으로 인정되지 않는다** — 8건짜리 샘플의 규모 한계도 있지만, '얼른'이 제주 단일 지역·소규모 물류 서비스라는 실제 사업 규모(공통 컨텍스트 웹조사 결과)를 고려하면, 행정동 단위로 세분화할수록 5건 문턱을 채우기가 구조적으로 어려울 수 있다. 5건이라는 숫자가 실제 주문량 규모에 맞춰 보정된 근거는 문서에 없다.

#### 잔여 실행 불가 지점·새로운 논리 오류 (5건)

1. **[새 논리 오류] 신규 기간 내 재구매가 오히려 "재이용"으로 인정되지 않는 역설**: "재이용 = 신규 기간(30일) 이후 추가 주문"이라는 정의 때문에, C001(14일 만에 재주문)·C005(24일 만에 재주문)처럼 가장 빠르게 재구매한(가장 충성도 높아 보이는) 고객이 재이용이 아닌 신규로 남는다. 실무적으로 "재구매 여부"가 아니라 "재구매 시점이 임의의 30일 경계를 넘었는지"가 재이용의 판정 기준이 되어, 정의와 직관이 어긋난다.
2. **[새 상태 공백] 31~59일 미분류 구간**: 신규 기간(30일) 종료 후 이탈위험(60일) 도달 전 구간에서 재구매가 없는 고객(C001이 7/1 스냅샷에서 실제로 이 구간에 해당함을 손 계산으로 확인)에게 부여할 상태가 4개 라벨 중 어디에도 없다. 월간 대시보드에서 이런 고객이 어느 카운트에도 잡히지 않고 누락될 위험이 있다.
3. **[부분 해소, 잔여 불확실성] 임베딩 0.85 임계값의 실제 타당성 미검증**: 정규화로 처리되는 공백·괄호류 변형은 100% 규칙으로 해결됐지만, 정규화 후에도 문자열이 다른 준-동일 품목(예: "제주감귤2호박스" vs "감귤박스2호")이 실제 임베딩 모델에서 0.85를 넘을지, 혹은 반대로 실제로 다른 규격 상품("감귤 1박스" vs "감귤박스(2호)"류)이 우연히 0.85를 넘어 오분류될지는 손 계산으로 검증할 방법이 없다.
4. **[계산 결과 residual] 최소 지지도 5건이 이 사업 규모에 맞는지 근거 없음**: 8건 샘플에서 이 순위 전체의 지식그래프 적용 근거가 되는 유일한 조합("이도이동+감귤류")이 최근 3개월 기준 4건으로 문턱(5건)에 미달했다. 제주 단일 지역·소규모 물량이라는 '얼른'의 실제 서비스 규모를 고려하면, 행정동 단위로 세분화한 조합이 5건을 채우는 일 자체가 구조적으로 드물 수 있어, 지식그래프 기능이 실제로는 거의 발동하지 않을 위험이 있다.
5. **[새 엣지케이스] 이상치 판정의 0-기준값(전월 0건) 미정의**: 전월 주문이 0건이던 품목군이 당월 처음 등장하면(이번 샘플의 축산물처럼) 증감률이 수학적으로 정의되지 않는데, 이 경우를 자동으로 이상치 처리할지에 대한 규칙이 없다.

#### 종합

**1차 시뮬레이션 등급 하 → 2차(v2) 시뮬레이션 등급 중**

v1에서 지적한 7개 결함 중 5개(①②③④⑤)는 임계값·필드·규칙이 명시적으로 추가되어 손 계산만으로 결정적 결과에 도달할 수 있게 되었고, 특히 v1의 핵심 실행 불가 지점이었던 "지식그래프 사례 자체가 재현 불가능"(③) 문제는 "행정동" 필드 도입으로 실제로 해소되었다(표에 값을 채워 계산까지 진행함). 나머지 2개(⑥⑦)는 v1이 지적한 구체적 사례(공백·괄호 변형, 이중집계)에 한해서는 실제로 해소됐지만, 그 해소 방식(정규화+임베딩, 30일 신규기간+스냅샷)이 각각 새로운 잔여 불확실성(임베딩 블랙박스)과 새로운 논리적 부작용(31~59일 상태 공백, 빠른 재구매의 역설)을 낳아 "부분 해소"로 판정한다. 또한 최소 지지도(5건) 문턱은 존재 자체는 개선이지만, 실제로 계산해보니 이 순위의 대표 사례가 문턱에 못 미쳐, 규칙의 존재와 규칙의 실효성은 별개 문제임이 드러났다. 종합적으로 v1의 "하"(실행 불가 지점이 지식그래프 핵심 사례 자체를 막는 수준)에서, 대부분의 계산이 끝까지 진행되되 몇몇 구조적 빈틈이 새로 드러나는 "중"으로 격상한다.

| 인원.최대 | 8 |

이 표는 실제로 채워진다 — v1에서 "날짜·가격·인원이 요약·유의사항의 자유 텍스트 안에 산문 형태로만 존재해 검증이 값 대 값 비교를 할 수 없다"고 지적했던 지점이, v2에서는 6개 필드가 프리미엄/가족/청년 세 버전 모두에서 동일한 숫자·날짜 타입으로 독립 존재하므로 실제로 비교 가능해졌다. 예컨대 세 유형을 각각 생성해도 가격.성인=45000이 유지되는지, 운영일이 세 버전에서 동일한지를 필드 대 필드로 즉시 대조할 수 있다.

**실행 불가 지점 1 (잔존, 경미)**: "제외일"은 원본 입력에 대응 값이 없다. 원본의 취소 조건은 "우천·풍랑주의보 시 자동 취소·전액 환불"로, 사전에 정해진 고정 휴무일(예: 매주 화요일)이 아니라 발생 시점에 결정되는 조건부 이벤트다. "제외일" 필드는 고정 날짜를 전제한 설계로 읽히는데, 이런 기상조건부 동적 취소 규칙을 어느 필드에 넣을지는 v2에도 규정이 없다. 다만 이 필드가 "값 없음"으로 비어 있는 것 자체는 오류가 아니므로 v1의 핵심 결함(필드 부재)보다는 훨씬 가벼운 잔여 이슈다.

**단계 B — 규칙 기반 검증(범위 명시) 재현**

v2 문구: "규칙 기반 검증은 위 스키마의 구조화 필드(일정, 운영일·제외일, 가격, 인원)에만 적용해 순서·누락·불일치를 확인하며, 요약·소개 문구 같은 자유 서술문의 표현 순서는 검증 대상에서 제외합니다."

이 규칙을 손으로 적용하면: (1) "일정" 필드가 "일자별 배열"로 09:00→13:00 순서를 담고 있다고 가정하면 순서 검증은 이 필드만 보면 되므로 v1이 지적했던 "일정 필드만 보는지 요약 문장까지 보는지" 모호함은 제거된다 — 가족형 요약에서 서사 순서를 뒤바꿔 써도("카페에서 여유롭게 시작해…") 그 문장은 애초에 검증 대상이 아니라고 명시돼 있어 오탐 소지가 사라진다.

**실행 불가 지점 2 (신규, 부분적)**: 검증 범위를 구조화 필드로 좁힌 대가로, 정작 고객이 실제로 읽는 화면 문구(요약·소개 문구)에 값이 잘못 재진술되는 경우는 이제 명시적으로 검증 대상에서 제외된다. 예를 들어 요약 문구가 "45,000원"이 아니라 "50,000원"이라고 잘못 서술해도, 가격.성인 필드 자체는 45000으로 정상이므로 규칙은 이 불일치를 잡지 않는다. 즉 v1이 지적한 "값 대 값 비교 불가" 문제는 스키마 층위에서는 해소됐지만, 그 해소 방식(자유 서술문을 검증에서 제외)이 사용자에게 실제로 노출되는 텍스트의 오류를 걸러내지 못하는 새로운 사각지대를 만든다.

**단계 C — 근거 없는 창작 방지 규칙 재현 (프리미엄 유형 재생성)**

v2 문구: "입력 자료에 없는 구체적 수치·시설명·옵션은 생성하지 않으며 … 프리미엄 유형처럼 강조 표현을 쓰는 경우에도 톤과 어휘만 바꿀 뿐 원본에 없는 새로운 사실을 추가하지 않습니다. 생성 후 규칙 기반 검증 단계에서 원본 입력에 없는 고유명사·숫자가 결과에 포함되면 자동으로 담당자 확인 대상으로 표시합니다."

동일 샘플로 프리미엄형을 다시 생성해본다.

- 재생성 시도 A(원칙만 지시대로 충실히 따른 경우): "여유로운 페이스로 즐기는 우도 스노클링. 스노클링 후에는 우도 카페에서 편안한 휴식 시간을 가져보세요." → 원본에 없는 사실이 없다. 규칙이 잘 작동한 사례.
- 재생성 시도 B(v1에서 실제 관찰된 실패 패턴을 그대로 재현): "번잡함 없이 즐기는 우도 소규모 프라이빗 스노클링. 전담 가이드와 함께 여유로운 페이스로 바다를 즐긴 뒤, 우도 카페 프리미엄 라운지에서 온전히 나만을 위한 휴식 시간을 가져보세요."

시도 B를 자동 검증 규칙에 그대로 대입하면: "전담 가이드", "프리미엄 라운지"는 원본에 없는 서비스를 가리키는 **명사**이지만 특정 인물·장소를 지칭하는 **고유명사**는 아니며, 숫자도 아니다. 규칙의 자동 판정 기준이 "고유명사·숫자가 포함되면"으로 좁게 정의돼 있어, 이 사례처럼 보통명사 형태의 창작(전담 가이드, 프리미엄 라운지)이나 "소규모"·"프라이빗" 같은 형용사형 창작은 문자 그대로는 탐지 대상에 안 걸릴 가능성이 크다.

**논리 오류 1 (v1 문제의 부분 재발)**: v2가 명시한 방지 "원칙"(구체적 수치·시설명·옵션 금지)과 실제로 서술된 자동 "탐지 기준"(고유명사·숫자 포함 여부) 사이에 범위 불일치가 있다. "시설명"이라는 원칙상 금지 대상은 일반적으로 고유명사가 아닌 보통명사(가이드, 라운지, 웰컴 드링크 등)로 표현되는 경우가 많은데, 탐지 규칙은 고유명사·숫자만 스캔하므로 원칙이 금지한 창작의 상당 부분을 자동 검증이 실제로는 놓칠 수 있다. 즉 v1이 지적한 "모순은 잡아도 근거 없는 창작은 통과시키는" 실패 사례가 이번에도 완전히는 재현을 피하지 못하고, 부분적으로 다시 발생한다.

**단계 D — 노코드 웹페이지 반영(자체 템플릿 렌더러) 재현**

v2 문구: "자체 제작한 경량 템플릿 렌더러(구조화 필드를 값으로 채운 HTML 템플릿으로 변환하는 방식)를 우선 구현하며, 젠트립의 실제 CMS·앱과의 직접 연동은 접근 권한 확인이 필요한 별도 확장 과제로 둡니다."

이는 v1의 "노코드 플랫폼이 젠트립 CMS·노코드 툴 연동인지 자체 렌더러인지 불명확"했던 지점을 구체적으로 확정한다 — "자체 제작 경량 템플릿 렌더러"로 명시되었으므로, 구조화 필드(제목/일정/가격 등)를 HTML 템플릿 변수에 매핑하는 절차는 손으로도 재현 가능하다(예: `{{제목}}` → h1, `{{일정}}` → 타임라인 리스트).

**실행 불가 지점 3 (잔존)**: 다만 보유자료로 제공된 이미지(스노클링 포인트 사진 5장, 카페 사진 3장)를 템플릿의 어느 영역에 몇 장, 어떤 순서로 배치할지에 대한 규칙은 v2에도 여전히 없다. 필드→텍스트 컴포넌트 매핑은 확정됐지만, 필드→이미지 컴포넌트 매핑은 v1에서 지적된 그대로 미해결로 남아 있어 "웹페이지 구성안"의 최종 산출물을 손으로 완전히 완성할 수는 없다.

---

**v1 지적 사항별 해소 판정**

1. **"날짜·가격·인원 불일치" 검증 규칙이 확인할 값이 구조화 스키마에 독립 필드로 없어 값 대 값 비교가 성립하지 않는 문제 → 해소.** 운영일·제외일(날짜)·가격(성인/소인/그룹, 숫자)·인원(최소/최대, 숫자)이 요약·유의사항과 분리된 독립 필드로 추가되어, 단계 A에서 확인했듯 실제로 필드 대 필드 비교가 가능하다. 다만 그 해소가 "화면에 노출되는 자유 서술문의 값 오류"까지 막지는 못한다는 새로운 잔여 문제(위 실행 불가 지점 2)를 낳았다.
2. **규칙 기반 검증이 "모순"은 잡아도 "근거 없는 창작"은 통과시키는 문제(프리미엄 유형) → 부분 해소.** 방지 "원칙"은 명시적으로 추가됐고 숫자·고유명사 형태의 창작은 자동 탐지 대상에 든다. 그러나 단계 C에서 재현했듯, v1에서 실제 발견된 실패 패턴("소규모 프라이빗", "전담 가이드"류의 보통명사·형용사형 창작)은 탐지 규칙이 "고유명사·숫자"로 좁게 정의돼 있어 여전히 자동으로는 안 걸릴 가능성이 있다.
3. **노코드 플랫폼이 무엇인지 불명확한 문제 → 해소.** "자체 제작 경량 템플릿 렌더러"로 구체화되어 필드→화면 매핑을 손으로 재현할 수 있게 됐다. 다만 이미지 배치 규칙 부재라는 인접 문제는 별도로 남아 있다(실행 불가 지점 3).
4. **일정순서 검증이 구조화 필드 대상인지 서술문 대상인지 불명확한 문제 → 해소.** "구조화 필드에만 적용", "자유 서술문의 표현 순서는 검증 대상에서 제외"로 명문화되어 v1이 지적한 모호함은 사라졌다. 다만 이 명확화가 역설적으로 실행 불가 지점 2(화면 노출 문구의 오류가 검증 밖에 남음)를 만들어냈다.

---

**여전히 남은 실행 불가 지점 / 새로 생긴 논리 오류 (5건)**

1. (잔존, 경미) "제외일" 필드가 고정 휴무일을 전제해, 본 샘플의 "기상 조건부 자동 취소"처럼 사전에 정해지지 않은 동적 예외를 표현할 방법이 없다.
2. (신규) 검증 범위를 구조화 필드로 한정한 결과, 요약 등 자유 서술문에 값이 잘못 재진술돼도(예: 가격.성인=45000인데 요약 문구는 "50,000원") 이는 정의상 검증 대상 밖이라 걸러지지 않는다 — 필드는 맞아도 고객이 보는 화면 문구는 틀릴 수 있는 새로운 위험.
3. (부분 재발) 근거 없는 창작 방지의 자동 탐지 기준("고유명사·숫자")이 방지 원칙("구체적 수치·시설명·옵션")보다 좁아, "전담 가이드"·"프리미엄 라운지"·"소규모 프라이빗" 같은 보통명사·형용사형 창작은 v1에서 지적된 사례 그대로 자동 검증을 통과할 가능성이 남는다.
4. (잔존) 이미지(보유자료 사진 5장+3장)를 템플릿의 어느 위치에 몇 장 배치할지에 대한 규칙이 없어, 노코드 렌더러의 최종 산출물(웹페이지 구성안)을 손으로 완전히 확정할 수 없다.
5. (잔존) "일정"이 "일자별 배열"이라는 필드 타입은 확정됐지만 내부 시간 표현(문자열 vs. 시각 타입)과 "그룹" 가격처럼 값이 존재하지 않는 경우(그룹가 미운영 상품)를 "누락"과 "해당없음" 중 무엇으로 처리할지는 규정되지 않아, 순서 비교·필수 정보 누락 판정의 세부 구현은 여전히 확정할 수 없다.

**매칭 표 대입 결과**: 규칙 1("이미지 전문성 등급: 비전문")이 단독 조건으로 충족되어 **Clo.D AI-Studio가 우선순위 1로 추천된다.** 규칙 2("판매채널 수 ≥3 AND SKU ≥50개")는 SKU 조건(200≥50)은 충족하지만 채널 수 조건(1~2 <3)이 미충족이라 AND 전체가 발동하지 않는다. "두 조건 모두 해당" 행 역시 규칙2 자체가 발동하지 않으므로 적용되지 않는다. 최종 결과: 규칙1 단독 발동 → AI-Studio 단독 추천(ERP 후속 제안 없음).

**역설 해소 여부 — 해소.** v2의 근본 문제는 "자체 촬영 여부"라는 필드명·관찰 방법(스톡사진 표기·이미지 중복검색)이 "본인이 찍었는가"만 가려낼 뿐 "전문 촬영 인프라 유무"는 가리지 못해, 계획서가 스스로 정의한 전형적 타깃(폰카 셀프촬영 셀러)이 되레 "자체 촬영: 예"로 분류돼 규칙을 피해가는 역설이었다. v3는 필드를 "이미지 전문성 등급"으로 바꾸고 관찰 방법도 "스튜디오 배경·조명·구도 유무"라는 시각적으로 직접 확인 가능한 기준으로 바꿔, 이번엔 하라주쿠 클로젯이 정의 그대로 "비전문"으로 즉시 판정되고 규칙1이 실제로 발동해 AI-Studio를 추천한다. 손으로 실제 대입해 최종 추천 결과에 도달한 것은 v1(표에 채울 값 자체가 없음) → v2(값은 나오지만 표를 의도대로 못 돌림)를 지나 이번이 처음이다. 또한 방향이 반대로 작동하던 "이미지 갱신 빈도" 신호는 매칭 표에서 아예 삭제되어, 그 신호가 만들던 두 번째 실패 경로도 함께 사라졌다.

**두 번째 규칙(판매채널≥3) 미충족 확인**: "판매채널 수 2개 + SKU 200개(≥50)" 조합을 대입하면, SKU 조건은 통과하지만 채널 수 조건에서 AND가 끊겨 규칙2(ERP 연동)가 발동하지 않는다. 채널이 적은(대형 유통망 미보유) 소규모 셀러에게는 ERP 연동보다 AI-Studio 단독 제안이 우선되는 것이 설계 의도에 부합하며, 실제로 표는 그렇게 동작했다.

**(b) SKU 규모 "큼" 수치 기준 — 해소**

v3는 "50개 이상이면 '큼'"이라는 명시적 수치를 추가했다. 하라주쿠 클로젯 샘플에 "카탈로그 노출 상품 약 200개"라는, 관찰 방법이 요구하는 것과 정확히 같은 종류의 값(카탈로그 노출 수)이 주어져 있어 200≥50 → "큼"으로 즉시 계산된다. v2에서는 샘플에 "월 신규 입고 40~60종"(유입량)만 있어 "카탈로그 노출 상품 수"(누적 재고량)라는 다른 지표와 단위가 안 맞아 판정 자체가 불가능했는데, 이번엔 그 단절도 함께 해소됐다.

**(d) 회신 긍정/거절 분류 로직 — 해소**

2. **"이미지 전문성 등급"의 혼합 사례 미정의** — 등급이 전문/비전문 이분법인데, 카탈로그 내 이미지가 전문 촬영과 폰카 촬영을 섞어 쓰는(과도기) 셀러를 어떻게 판정할지 규칙이 없다. 하라주쿠 클로젯은 전량 폰카 촬영이라 문제가 드러나지 않았을 뿐, 실제 해외 셀러 다수는 혼합 사용 가능성이 있다.
3. **탐색 소스의 실제 접근성 미검증** — Kompass 등은 상세 연락처·담당자 정보가 유료 구독 또는 문의 절차 뒤에 있는 경우가 많다. "소스를 지정했다"는 문제는 해소됐지만, "그 소스에서 실제로 이메일 발송에 쓸 만한 공식 연락처까지 무료·직접 확보 가능한지"는 별도로 검증되지 않았다.

#### (a) 빠른 재구매 역설 — C001·C005 대입

인용(92~96행): 표는 열을 "누적 주문 횟수 1회" / "누적 주문 횟수 2회 이상"으로, 행을 "최근 주문 경과일"(0~59일/60~89일/90일 이상)로만 나눈다. **재구매가 신규 기간 안에서 일어났는지 밖에서 일어났는지는 규칙에서 완전히 빠졌다** — v2의 "재이용 = 신규 기간(30일) 이후 추가 주문"이라는 시점 조건 자체가 사라졌다.

| 고객 | 조건 | 대입 | 판정 |
|---|---|---|---|
| C001 | 14일 만에 재주문, 최근 주문 10일 전 | 누적 2회(1회 이상 재주문 확정) × 경과 10일(0~59일 행) | **재이용** |
| C005 | 24일 만에 재주문, 최근 주문 5일 전 | 누적 2회 × 경과 5일(0~59일 행) | **재이용** |

→ 두 고객 모두 재구매 간격(14일·24일)이 얼마든, 재구매가 "신규 기간 안"이든 "밖"이든 상관없이 "누적 2회 이상 + 0~59일"이라는 조건만으로 즉시 재이용으로 확정된다. v2가 지적한 역설(가장 빠르게 재구매한 고객이 오히려 재이용으로 인정 안 됨)의 원인이었던 "신규 기간 이후"라는 시점 제약 자체가 v3 규칙에는 존재하지 않으므로, 이 역설은 **해소**된다.

#### (b) 31~59일 공백 상태 — 45일 경과·1회 대입

v2에서 C001이 "신규 기간(30일) 지남 + 재주문 없음 + 이탈위험(60일) 미달"인 31~59일 구간에 빠져 4개 라벨 중 어디에도 속하지 못했던 것이 문제였다. v3 표는 이 구간을 별도 행으로 쪼개지 않고 "0~59일" 행 하나로 병합했다.

| 조건 | 대입 | 판정 |
|---|---|---|
| 45일 경과, 누적 1회, 재주문 없음 | 경과 45일(0~59일 행) × 누적 1회(1회 열) | **신규** |

→ 0~59일 전체를 하나의 행으로 묶고 60/90일 두 경계만 남겼기 때문에, 이제 30~59일이라는 별도 구간 자체가 표에 존재하지 않는다. 45일이든 5일이든 59일이든 누적 1회면 예외 없이 "신규" 셀 하나로 귀결되어, v2가 실제로 겪었던 미분류 공백은 **해소**된다(모든 (경과일, 횟수) 조합이 6개 셀 중 정확히 하나에 대응하는 전수 매핑임을 표로 확인했다).

#### (c) 최소 지지도 미달 — "3개월 내 4건" 대입

v3 문구: "이미지는 상품당 최대 5장까지 업로드하며, 웹페이지 상단 갤러리에 업로드된 순서 그대로 배치합니다. 5장을 초과하면 초과분은 반영하지 않습니다."

지시대로 사진 7장이 입력된 상황을 가정해 손으로 적용: 업로드 순서대로 1~7번 사진 중 1~5번만 갤러리에 그대로 배치하고, 6~7번은 반영하지 않는다. 규칙에 조건 분기나 예외가 없어 기계적으로 바로 실행 가능하다 — v2의 문제(이미지 배치 규칙 부재로 웹페이지 산출물을 손으로 완성할 수 없던 문제)는 해소된다.

다만 규칙을 이 샘플(스노클링 5장 + 카페 3장, 도합 8장이지만 지시받은 7장 가정 시 예: 스노클링 5장+카페 2장)에 실제로 적용해보면 새로운 위험이 보인다: 만약 업로드 순서상 스노클링 사진이 먼저 5장 모두 올라가 있다면, 규칙대로 앞의 5장만 반영 시 카페 관련 사진은 0장이 되어 상품명 자체가 "스노클링+카페 투어"인데도 웹페이지에 카페 요소가 전혀 노출되지 않을 수 있다. 규칙은 순서 기준(FIFO)만 정의할 뿐 카테고리 간 최소 노출 보장이나 대표성 기준이 없어, 기계적 실행은 가능해도 결과물의 품질(상품 구성요소의 균형 있는 노출)까지 보장하지는 않는다.

---

**(e) 그룹가 결측값 처리 — 판정: 해소**

v3 문구: "그룹 가격처럼 상품에 따라 값이 없는 필드는 공란으로 두고, 웹페이지에는 '그룹 문의' 같은 대체 문구를 자동 표시합니다."

샘플에 손으로 적용: 가격.그룹 필드는 원본에 그룹가 언급이 없으므로 공란으로 유지되고, 웹페이지 템플릿의 그룹가 표시 영역은 공란을 감지해 "그룹 문의"로 대체 표시한다. 값이 없는 필드에 대한 화면 처리 규칙이 없어 표시 자체가 불가능했던 v2의 문제는 실제로 해소된다(구체적 문구 표기 세부사항은 수정안 서문이 명시한 대로 개발 단계 디테일로 남겨둘 수준이며 설계 로직상 결함은 아니다).

---

**새로 발견된 문제 (3건)**

1. **명사구 추출 규칙의 오탐(false positive) 구조적 위험**: (a)에서 확인했듯 "원본에 없는 새 명사구는 모두 걸린다"는 문언은 사실 오류가 없는 정상적인 의역·동의어 표현(예: "4시간" → "반나절 코스")까지 담당자 확인 대상으로 만든다. 동의어 정규화나 유사도 임계값 같은 예외 처리가 없으면, 프리미엄 유형처럼 표현을 다양하게 바꾸는 콘텐츠일수록 오탐이 누적되어 담당자가 매번 대량의 확인 큐를 받게 되는 "경보 피로" 위험이 있다.
2. **숫자 교차 검증이 값만 보고 라벨(성인/소인/그룹)을 확인하지 않음**: (c)에서 확인했듯, 요약문이 올바른 필드의 숫자를 잘못된 라벨에 붙여 서술해도(예: 그룹 문의) 그 숫자가 어떤 구조화 필드에든 존재하기만 하면 검증을 통과한다. "값 존재 여부"가 아니라 "값-라벨 결합"까지 대조해야 이 사각지대가 닫힌다.
3. **이미지 배치 규칙이 순서(FIFO)만 정의하고 카테고리 균형은 보장하지 않음**: (d)에서 확인했듯, 두 가지 체험(스노클링+카페)을 함께 파는 상품에서 업로드 순서가 한쪽에 몰리면 다른 쪽 이미지가 전부 잘려나가 상품 핵심 요소가 화면에서 누락될 수 있다.

---

**종합**

v2에서 지적한 5개 문제 중 (b) 운영조건·제외일 공존, (c) 숫자 교차 검증(지시된 테스트 케이스), (d) 이미지 배치 규칙, (e) 결측값 처리 4건은 손으로 직접 재현했을 때 실제로 해소를 확인했다. (a) 근거 없는 창작 방지는 v2의 핵심 실패 사례("소규모 프라이빗 그룹", "전담 가이드")를 실제로 잡아내는 데는 성공했지만, 규칙의 정의가 정상적인 의역까지 포함해 지나치게 넓어 새로운 오탐 위험을 낳아 부분 해소로 판정한다. 그 외에도 (c)의 라벨 미결합, (d)의 카테고리 편중처럼, 지시받은 특정 테스트 케이스는 통과하지만 살짝 변형한 인접 케이스에 적용하면 다시 허점이 드러나는 패턴이 3건 발견되었다 — v2 대비 구조적 결함은 크게 줄었으나, 세부 판정 기준(라벨 결합, 동의어 처리, 카테고리 대표성)의 정밀도는 아직 완전하지 않다.

**2차(v2) 등급 → 4차(v3) 등급: 상 → 상**

근거: v2에서 남아 있던 5개 문제 중 4개가 실제 재현에서 해소로 확인되고 나머지 1개도 핵심 실패 사례는 해소되어 전반적으로 실행 가능성이 더 개선되었으나, 새로 발견된 3건이 모두 "지시된 테스트는 통과하되 인접 변형 케이스에서 다시 허점 노출"이라는 동일한 성격의 잔여 리스크여서 등급을 한 단계 더 올릴 만큼의 근본적 개선은 아니라고 판단해 v2와 동일한 "상"으로 유지한다.
