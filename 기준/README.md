# 기준 — 사람이 읽고 고치는 판정 기준

**여기 있는 것은 "손잡이"다.** 돌려도 구조가 안 부서지는 값과 문장만 모았다. 기획을 다시 읽지 않아도 이 디렉터리만 열어서 고칠 수 있게 만드는 것이 목적이다.

## specs/ 와 무엇이 다른가

| | `specs/` | `기준/` (여기) |
|---|---|---|
| 무엇 | **구조** — 무엇을 만드는가, 어떤 형태로 내놓는가, 실패하면 어떻게 되는가, 성공을 어떻게 세는가 | **값과 문장** — 무엇을 보고 O/X를 주는가, 어떤 말이 나오면 어느 칸인가, 표본을 몇 개 보는가 |
| 바뀌는 빈도 | 드물게. 바뀌면 만드는 방식이 바뀐다 | **자주. 바뀌어도 만드는 방식은 그대로다** |
| 누가 고치나 | 기획을 다시 판단할 때 | **실제로 판정해 본 사람이 그 자리에서** |
| 예 | "관찰 항목과 그 근거를 같은 행에 붙여 1행으로 낸다" | "가격만 있고 구매 버튼이 없으면 커머스 없음으로 본다" |

**값을 두 곳에 적지 않는다.** `specs/`는 판정 문장을 직접 쓰지 않고 여기를 가리킨다. 같은 값이 두 곳에 있으면 하나만 고치고 나머지는 썩는다.

**단 운영 변수는 예외다.** 판정에 쓰이는 값(O/X를 가르는 선)은 이 카드가 정본이지만, **"얼마나 많이·얼마나 오래"를 정하는 값(캐파·담당자 가용 시간·발송 상한·최소 수주 금액)은 `../docs/50_실사용_도입설계.md`가 정본이다.** 이 카드에 그런 값을 적으면 값이 왔을 때 카드만 낡는다 — 실제로 이 사고가 `../docs/90_미결정과_리스크.md` 리스크 26으로 한 번 났다.

**이 원칙은 Spec의 「실패 시 어떻게 되는가」 표에도 그대로 적용된다.** 표의 각 행은 **제어 흐름**(멈추나·계속하나·어디로 넘기나)과 **판정 값**(어느 라벨·어느 등급인지의 매핑)으로 나뉜다 — 앞은 Spec, 뒤는 여기(기준 카드)다. Spec이 뒤 조각까지 옮겨 적으면 지워도 출력이 안 바뀌는 문장이 되고, 이 카드를 고칠 때 Spec의 복사본만 낡는다(`../docs/33_설계근거.md` D13).

→ **Build Order를 돌리는 사람은 `specs/`의 Spec 1개 + `기준/`의 기준 카드 1개, 두 파일을 함께 받는다.** 자체 완결의 단위가 "파일 하나"에서 "두 파일 한 세트"로 바뀐 것이고, 저장소 전체를 볼 필요는 여전히 없다.

## 고칠 때의 규칙 — 하나뿐이다

**바꾼 줄과 이유를 각 파일 맨 아래 「변경 이력」에 한 줄 남긴다.**

이유를 안 남기면 두 가지가 무너진다.

1. **다음 사람이 되돌린다.** 왜 그렇게 됐는지 모르면 "이상하네" 하고 원래대로 바꿔 놓는다.
2. **심사에 답할 게 없다.** 심사가 보는 것은 결과가 아니라 *"왜 그 기준이고, 그 정확성을 확인했는가"*다. **"실제로 10곳을 봤더니 가격만 있는 곳이 3곳이어서 이렇게 갈랐다"가 그 답이다.** 이력이 곧 검증 기록이다.

이력 한 줄에 들어갈 것 — **날짜 / 무엇을 / 왜(무엇을 보고)**. 그 이상은 필요 없다.

## 값이 아직 없는 칸

`(미확인)`으로 표시된 것은 **기업에 물어야 아는 값**이다. **추정치로 채우지 않는다.** 그럴듯한 숫자를 넣으면 근거 없는 기준이 하나 늘고, 나중에 실제 값이 오면 그 숫자로 판정한 결과를 전부 다시 봐야 한다.
