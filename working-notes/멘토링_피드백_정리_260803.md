# 멘토링 피드백 정리 (2026-08-03)

> 원본: `음성녹음 원본 텍스트.txt`, `음성녹음 AI 요약본.txt`

멘토가 강조한 핵심: **MCP를 먼저 정하지 말고, 이메일 통신의 기술적 원리를 먼저 이해한 뒤 그 원리에 맞는 MCP를 고를 것.**

---

## 1. 통신 방식 (OSI 7계층 관점)

이메일 발송은 **OSI 7계층 중 응용 계층(Application Layer)**에 속하고, 표준 프로토콜은:

- **SMTP** (포트 587/STARTTLS 또는 465/SSL) — 메일 **발송**
- **IMAP/POP3** — 메일 **수신/조회** (발송만 하면 필요 없음)
- (참고) **Gmail API 같은 REST/HTTPS 방식** — SMTP를 우회해 OAuth2 인증 + HTTP로 처리하는 대안

프로젝트가 "메일을 보내기만" 하면 되는지, "받은 메일 확인/관리"까지 필요한지가 먼저 정해져야 어떤 MCP가 필요한지 바로 보인다.

## 2. 실제로 존재하는 이메일 MCP 후보

대부분 **SMTP/IMAP 표준 프로토콜을 그대로 감싼 래퍼(wrapper)** 형태.

| 유형 | 예시 | 용도 |
|---|---|---|
| SMTP 발송 전용 | [mcp-server-smtp](https://github.com/samihalawa/mcp-server-smtp) | 발송만 필요할 때 |
| SMTP+IMAP 풀기능 | [email-mcp-server](https://github.com/gabigabogabu/email-mcp-server), [codefuturist/email-mcp](https://github.com/codefuturist/email-mcp) | 발송+수신/검색까지 필요할 때 |
| 경량 | [mcp-mail-server](https://github.com/yunfeizhu/mcp-mail-server) | 간단한 발송/수신 |

**채용 기준**: 발송만 필요 → SMTP 전용 MCP로 충분. 발표에서 "왜 이 MCP인가"를 물으면 "발신만 필요해서 SMTP(587, STARTTLS)만 wrap한 가벼운 MCP를 썼고, IMAP 기능이 있는 무거운 MCP는 과했다"고 근거 있게 답할 수 있다.

## 3. "MCP가 없으면 어떻게 해결했을까?"

MCP 이전/없이는 언어별 SMTP 라이브러리를 코드로 직접 호출했다:

- Python: `smtplib` + `email.mime`
- Node.js: `nodemailer`
- Java: `JavaMail`

즉 계정/앱 비밀번호(또는 OAuth2 토큰)로 TLS 연결을 열고, MIME 형식 메일을 만들어 SMTP 서버에 직접 전송하는 코드를 짰던 것. **MCP는 이 로직을 `send_email(to, subject, body)` 같은 표준 tool 인터페이스로 감싸서 LLM이 호출하기 쉽게 만든 것뿐**이고, 내부적으로는 결국 같은 SMTP 라이브러리를 실행한다. 이 사실을 알고 있으면 발표에서 "MCP 내부가 실제로 뭘 하는지" 질문에 답할 수 있다 — 멘토가 가장 강조한 부분.

## 4. 바로 할 수 있는 액션

1. 후보 MCP(예: mcp-server-smtp) 코드를 열어서 실제로 smtplib/nodemailer를 호출하는지 직접 확인 → 발표 근거 자료로 활용
2. 우리 프로젝트는 "발송 전용"인지 확정 → IMAP 필요 없으면 가벼운 SMTP 전용 MCP로 결정
3. "MCP 없이 직접 SMTP 코드로 구현한 버전"을 짧게라도 만들어 비교 → "직접 구현 대비 MCP를 쓴 이유(재사용성, 표준 tool-call 인터페이스, 유지보수)"를 발표에 반영
4. 발표 자료에 SMTP 인증 → MIME 구성 → 전송 흐름을 다이어그램으로 추가 (플로우 다이어그램 부재 지적)

## 5. (참고) 그 외 멘토링 피드백

### 타임아웃 문제 (상세)

**현재 상황**
- 프로젝트 구조를 g1~g11까지 11단계로 나눠 스펙 문서로 설계함
- 타임리(플랫폼)에서 구현하려니 타임아웃 발생 → 구현이 안 됨
- 여러 번 반복해서 겨우 한 번 성공했으나, 그 이후 **단일 에이전트 → 멀티 에이전트로 전환하니 데이터 누락**이 발생 → 오히려 단일 에이전트보다 성능이 떨어짐
- 인풋을 최대한 줄여 스펙 문서를 다시 만들었는데도 가끔 여전히 타임아웃 발생, 처리할 기업(데이터) 수가 많아지면 또 다른 문제 발생

**원인 분석 (멘토 설명)**
- 타임아웃은 기본적으로 **양적으로 너무 많은 인풋을 한 번에 줬을 때** 발생
  - 멘토가 실제로 본 사례: 업스테이지 AI 스튜디오 에이전트 시스템에 500페이지짜리 PDF를 넣었을 때도 타임아웃이 났음 → 절대적인 규모의 문제
- 에이전트가 내부적으로 거치는 과정: **문서 파싱 → 문자열 벡터화 → 임베딩**
  - 이 임베딩 과정이 (트랜스포머 기반) 연산이라 서버의 RAM/리소스를 많이 소모함
  - 즉, 인풋이 많을수록 파싱~임베딩 단계에서 시간과 메모리가 기하급수적으로 늘어나 타임아웃으로 이어짐

**시도해볼 수 있는 해결 방향**
1. **단계(인풋 양) 자체를 줄이기** — 지금 시도 중인 방향
   - g1~g11 단계를 줄여서 에이전트에게 한 번에 쏟아붓는 인풋 양을 확연히 감소
   - 단점: 단계를 줄이면 스펙이 구체성을 잃고 원하지 않는 방향(누락, 부정확)으로 갈 수 있음
   - 대안: 구현 목표 자체를 더 단순화 — 예: "기업 찾기 → 메일 보내기"만 되는 최소 플로우(MVP)부터 완성하고 이후 단계적으로 기능 추가
2. **설계를 나눠서 처리 (분할 설계)**
   - 인풋을 줄이는 게 어렵다면 전체 파이프라인을 여러 개의 독립된 단계로 쪼개서 각각 처리
   - 주의: 나눈 결과물을 다시 이어붙이는 과정(state 전달, 컨텍스트 유지)이 오히려 더 어려워질 수 있음 — 설계 시 이 부분을 먼저 검토
3. **압축(compression) 후 전송**
   - 멘토가 과거 RAG 개발 시 겪었던 동일한 문제(인풋 과다 → 해석 시간 초과)에 시도했던 방법
   - 인풋을 압축해서 보내면 전송량은 줄어들지만, **서버 쪽에서 압축을 다시 해제하는 작업이 추가로 필요**함 (트레이드오프)
   - 멘토도 "확실한 해결책은 아니고, 잘 안 될 수도 있다"고 언급 — 검증 목적의 시도로 접근할 것
4. **멀티 에이전트 데이터 누락 원인 규명**
   - 왜 멀티 에이전트로 전환했을 때 데이터가 누락되는지 구조적 원인 파악이 우선 (에이전트 간 컨텍스트/상태 전달 방식 점검)
   - 원인 파악 전까지는 단일 에이전트 + 인풋 축소 조합이 더 안전한 선택일 수 있음

**액션 아이템**
- [ ] g1~g11 스펙을 리뷰하며 "최소 동작 플로우(기업 검색 → 메일 발송)"만 남기고 나머지는 2차 목표로 분리
- [ ] 파싱~임베딩 단계에 실제로 어느 정도 크기(글자수/토큰수)의 인풋이 들어가는지 로그로 측정 → 타임아웃 발생 임계치 파악
- [ ] 압축 전송 방식 소규모 프로토타입으로 테스트 (효과 있는지 빠르게 검증)
- [ ] 멀티 에이전트 전환 시 어느 단계에서 데이터가 누락되는지 로그/중간 결과 비교로 원인 특정

### LLM 모델 선택
- 현재 플랫폼(타임) 종속으로 솔라(Solar) 오픈툴 사용 중
- 메일 작성처럼 단순한 작업에는 굳이 큰 파라미터 모델이 필요 없음 (예: 파인튜닝된 0.5B~1.5B 모델도 충분)
- 발표 시 "외부 서버 연동으로 더 광범위한 모델 선택이 가능했다면 이 정도 파라미터 수는 선택하지 않았을 것"이라고 설명할 수 있어야 함 ("쥐 잡는 데 소잡는 칼" 비유)

### 기획서/설계 문서 보완 방향 (상세)

**멘토가 짚은 핵심 문제: "문서의 타겟이 누구인가"**
- 문서를 잘 만들었는지 판단하는 기준은 결국 **보는 사람(대상) 기준**
- 지금 보여준 문서(프로젝트 구조, g1~g11 스펙)는 "멘토링을 수월하게 하기 위한 문서" = **멘토를 타깃으로 작성된 문서**
  - 그래서 멘토 입장에서 보기엔 괜찮지만, **개발팀과 협업하는 관점에서는 큰 도움이 안 됨** (부정적 평가가 아니라 애초에 목적이 다르다는 의미)
  - 실제 개발팀 회의에 들어가거나 회의 전 문서를 준비한다면, 지금 형태와는 "결이 많이 다를 수 있음" → 개발자/엔지니어 대상 문서 포맷을 별도로 검색해서 참고할 것

**개발자 관점에서 문서에 반드시 있어야 하는 것**

1. **한계점(Limitation)과 그 해결 방안에 대한 구체적인 기술 내용**
   - 단순히 "이런 기능을 만든다"가 아니라 "이 기술적 한계를 이렇게 극복했다/극복할 것이다"가 핵심
   - 예: 타임아웃 문제, MCP 선택 근거, LLM 파라미터 선택 이유 등이 여기에 해당 (위 섹션 내용 그대로 문서화 대상)

2. **데이터 흐름을 도식화한 다이어그램**
   - 플로우 다이어그램(Flow Diagram) 또는 시퀀스 다이어그램(Sequence Diagram) 필요
   - 현재 문서에는 이 부분이 빠져 있음 → 클라이언트 구성, MCP 연동 지점, 외부 서버와의 통신 흐름을 시각적으로 표현해야 함
   - 특히 "외부 서버 ↔ 타임(플랫폼) MCP ↔ 클라이언트"가 어떻게 연동되는지는 멘토도 고민한 흔적이 있다고 언급한 부분 — 이 연동 구조를 다이어그램으로 명확히 정리하면 발표에서도 강점이 됨

3. **테스트 방법에 대한 계획**
   - 현재 문서에는 "이걸 어떻게 테스트하는지"가 전혀 나와 있지 않음
   - 대표적인 두 가지 테스트 방법론:
     - **유닛 테스트(Unit Test)**: 코드 레벨에서 개별 함수/모듈 단위로 동작을 검증하는 방식. 과거 TDD(Test-Driven Development, 테스트 주도 개발)가 유행했었지만, 멘토는 "TDD가 전부는 아니다"라고 언급
     - **E2E 테스트(End-to-End Test)**: 실제 사용자가 클라이언트(웹 브라우저 등)를 통해 제대로 조작할 수 있는지를 검증하는 방식. 멘토는 "결국 제일 중요한 건 사용자이기 때문에 E2E 관점이 중요하다"고 강조
   - 프로젝트가 "잘 만들어지고 있는지" 스스로 검증할 수 있는 단계가 필요하며, 이 테스트를 **어떻게 할 것인지가 중요한 포인트**라고 명시적으로 언급함
   - 두 방법론 모두 검색해서 개념을 학습하고, 우리 프로젝트에 어떻게 적용할지 계획을 문서에 포함시킬 것

**전체 평가**
- 지금 진행 중인 작업 자체는 명백히 엔지니어링(개발)이 맞지만, 기획 요소가 상당히 세게 가미된 형태로 흘러가고 있음 (해커톤 특성상 어쩔 수 없는 부분)
- 구현에 대한 고민 자체는 충분히 잘 되어 있었다고 평가함 (클라이언트 구성, MCP 붙이는 지점, 외부 서버-MCP 연동 방식 등)
- 다음 멘토링(8/5, 목)까지 이 구현이 어느 정도 진행되어 있을지가 관전 포인트 — 기술적 피드백을 계속 많이 받을 수 있도록 준비할 것
