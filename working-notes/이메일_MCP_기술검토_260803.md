# 이메일 MCP 기술 검토 (2026-08-03)

> 참고 스펙: `AI_Bootcamp_Corporate-assignment-project/specs/G5_제안메일제작발송.md`, `specs/G6_발송결과판정.md`, `docs/50_실사용_도입설계.md`
> 관련 메모: `멘토링_피드백_정리_260803.md` (이메일 MCP 채택 배경이 된 멘토링 피드백)

**결론 먼저**: 이메일 관련 MCP는 **SMTP 전용 MCP가 아니라 ESP(트랜잭션 메일 서비스) API 기반 MCP(예: Resend)를 채택한다.** 이유는 아래 2절.

---

## 1. 우리 프로젝트의 이메일 요구사항 (스펙 기준)

이메일이 걸리는 기능은 두 개이고, **요구사항이 서로 다르다.**

| 기능 | 필요한 동작 | 스펙 원문 근거 |
|---|---|---|
| **G5** (제안 메일 제작·발송) | 발신 + 발신 전용 서브도메인 + 일일 발송 상한 준수 + 법정 표시 4종 삽입 | `specs/G5_제안메일제작발송.md` |
| **G6** (발송 결과 판정) | 발신 후 **반복적으로 재조회**해서 바운스 코드(하드/소프트) 확인 | `specs/G6_발송결과판정.md` |

G6 스펙 원문:

> 도구 권한: **메일 시스템 응답(바운스 로그) 조회** + 결과 파일 쓰기까지만
> 이 기능은 1회성이 아니라 **반복 조회**다 — 같은 발송 건을 시간을 두고 여러 번 다시 확인할 수 있다
> **하드 바운스와 소프트 바운스를 다른 결론으로 다룬다**

이 한 줄 때문에 "이메일 MCP = SMTP MCP"라는 초기 결론은 **틀렸다.**

## 2. 왜 순수 SMTP MCP로는 안 되는가

SMTP는 **발신 프로토콜**이다. "메일을 보냈다"까지만 책임지고, 그 이후 상대 서버가 어떻게 처리했는지(수신 성공/하드 바운스/소프트 바운스)는 **SMTP 프로토콜 자체에 조회 기능이 없다.**

실제로 바운스 정보가 오는 경로:
- 상대 메일 서버가 실패를 감지하면 **발신자 메일함으로 반송 메일(NDR, Non-Delivery Report)을 보냄**
- 이걸 받으려면 SMTP 발신 기능과는 별개로 **IMAP으로 발신자 메일함을 모니터링**해야 함
- NDR 형식은 메일 서버마다 제각각이라, 그 안에서 "하드/소프트 바운스"를 파싱해내는 로직을 직접 짜야 함

즉 **SMTP 전용 MCP + IMAP MCP를 조합해도**, 이 파싱 로직은 우리가 직접 구현해야 하고, G6가 요구하는 "판정 근거 = 바운스 코드 원문"의 신뢰성이 우리가 짠 파서 수준에 갇힌다.

## 3. 대안 — ESP(트랜잭션 메일) API 기반 MCP

Resend·SendGrid·Mailgun 같은 **트랜잭션 메일 서비스(ESP)**는 발신 API와 별도로 **"이 메일 지금 상태 어때?"를 물어볼 수 있는 조회 API**를 함께 제공한다.

| | SMTP 전용 MCP | ESP API MCP (예: Resend) |
|---|---|---|
| 발신 | O | O |
| 상태 조회 | ✗ (NDR을 IMAP으로 직접 파싱해야 함) | **O — ID로 조회하면 sent/delivered/bounced 상태를 그대로 반환** |
| 바운스 구분 | 우리가 파서를 직접 짜야 함 | ESP가 이미 하드/소프트를 구분해서 내려줌 |
| 웹훅으로 실시간 바운스 수신 | ✗ | O |
| 발신 전용 서브도메인 설정 | 별도 설정 필요 | 기본 기능으로 지원 (도메인 인증만 하면 됨) |

**결론**: G5·G6 두 기능을 하나의 MCP로 커버하려면 ESP API 기반 MCP가 맞다. "더 강력해서"가 아니라 **G6가 명시한 "반복 조회"·"바운스 코드"를 API 호출 한 번으로 해결**할 수 있어서다.

**참고 후보**: [Resend MCP](https://github.com/resend/resend-mcp) — 발신 + ID로 상태 조회(sent/delivered/bounced) + 웹훅 바운스 추적 지원. SendGrid·Mailgun도 동급 API를 제공하나, Resend가 설정 난이도·문서 측면에서 더 단순.

## 4. 이게 G5의 다른 요구사항도 같이 풀어준다

- `docs/50_실사용_도입설계.md` 1-1절의 **"발송 전용 서브도메인 분리"**(도메인 평판 보호, 회사 기존 거래 메일 보호) → ESP는 커스텀 발신 도메인 인증이 기본 기능
- G5의 **"일일 발송 상한"** 로직 → ESP API가 발신 건수·상태를 추적하므로 그 위에서 카운팅 로직을 얹기 쉬움
- G5의 **소프트 바운스 재시도** 로직 → ESP가 소프트/하드를 이미 구분해 리턴하므로 "재시도 후에도 실패해야 주소 오류" 판정이 바로 가능

## 5. "MCP 없이 했다면?" (발표 대비 — 근거 있는 답변용)

MCP 없이 직접 구현했다면 Python `smtplib`로 발신하고, `imaplib`로 발신자 메일함을 폴링하며 NDR 메일을 정규식으로 파싱해 하드/소프트 바운스를 나눴을 것이다. **MCP는 이 파이프라인을 감싼 것이 아니라, ESP라는 별도 서비스가 이미 이 파싱을 표준화된 API로 대체해준 것**이다 — 즉 "MCP 유무"보다 **"SMTP+자체파싱 vs ESP API" 선택이 더 본질적인 기술 결정**이라는 걸 발표에서 짚을 수 있다.

## 6. 다음에 확정해야 할 것

- [ ] 바운스 상태 조회를 G6 실행체가 어떤 주기로 재조회할지(폴링 주기 vs 웹훅 수신) 결정
- [ ] 무응답 판정 대기 기간(현재 미확인)이 확정되면 G6 재조회 로직에 반영

## 7. Resend 비용·테스트 제약 (2026-08-03 확인)

**결론: 지금 단계(MCP 연결·파이프라인 검증)는 100% 무료로 가능하다.**

| 항목 | 내용 |
|---|---|
| 무료 요금제 | 월 3,000건 / 일 100건, **가입에 신용카드 불필요** |
| 도메인 인증 전 제한 | 발신 주소는 `onboarding@resend.dev`로 고정, **가입한 본인 이메일로만 수신 가능**(임의 수신자 발송 불가) |
| 도메인 인증 비용 | 무료 — DNS에 TXT/DKIM 레코드 추가만 하면 됨. 인증 후 커스텀 발신 주소·임의 수신자 발송 가능 |
| 유료 전환 시점 | 월 3,000건 초과 또는 여러 도메인 필요 시 — Pro $20/월(5만 건)부터 |
| Rate limit | 초당 2 요청 (도메인 인증 후 요청 시 상향 가능) |

**시사점**
- G5·G6 파이프라인 자체(발신 → 상태 조회 → 바운스 판정)를 붙여보는 테스트는 도메인 인증 없이도 가능 — 단 수신자를 가입한 본인 이메일로 한정해야 함
- "일본 기업 실제 주소로 발송" 테스트를 하려면 **도메인 인증(무료, DNS 설정 필요)**이 먼저 필요함 — `docs/50` 1-1절의 "발송 전용 서브도메인" 요건과 이 시점에 함께 처리하면 작업이 중복되지 않음
- 무료 요금제의 **일 100건 상한**이 `docs/50` 1-1절이 요구하는 "낮은 값에서 시작해 담당자가 직접 늘려가는" 초기 발송 상한과 방향이 맞아, MVP 단계에서는 별도 컷오프 로직 없이 이 상한을 그대로 초기값으로 써도 됨

### 연결 절차
1. resend.com 가입(무료, 카드 불필요) — 사용자가 직접 진행
2. API 키 발급
3. API 키는 `.env`에만 보관, 대화·문서에 값 자체를 남기지 않음 (`CLAUDE.md` 6절 보안 규칙)
4. Claude Code에 Resend MCP 서버 연결

## 8. MCP 연결 완료 기록 (2026-08-04)

- **명령어**: `claude mcp add resend -e RESEND_API_KEY=*** -- npx -y resend-mcp`
- **저장 위치**: `~/.claude.json`(로컬 전용 설정) — 프로젝트 git 저장소 파일에는 키를 쓰지 않음. `.gitignore`에 `.env` 계열은 이미 등록돼 있으나, 이번엔 그조차 필요 없이 로컬 스코프로만 저장해 커밋 경로 자체를 차단함
- **연결 상태**: `claude mcp list` 결과 `resend: npx -y resend-mcp - ✔ Connected`
- **주의 — 세션 재시작 필요**: MCP를 새로 등록한 뒤 도구가 바로 이 대화창에 뜨지 않는다. **다음 세션(또는 대화 새로고침)부터** resend 관련 도구가 로드된다
- **다음 실제 테스트 시 체크할 것** (도메인 인증 전 제약 그대로 적용됨, 7절 참조):
  - [ ] 새 세션에서 "resend로 테스트 메일 보내줘" 요청 → 발신 주소 `onboarding@resend.dev`, 수신자는 가입한 본인 이메일로만
  - [ ] 발신 후 메일 ID로 상태 조회(sent/delivered/bounced) 확인 — G6가 요구하는 "반복 조회"가 실제로 동작하는지 여기서 검증됨
  - [ ] 검증되면 도메인 인증(무료) 진행 → 커스텀 발신 주소·임의 수신자 테스트로 확장
