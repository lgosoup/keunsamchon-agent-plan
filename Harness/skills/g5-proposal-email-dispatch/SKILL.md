# g5-proposal-email-dispatch — 세그먼트 1개분 문안 제작·검증·승인·발송

이 스킬은 **정본 문서를 그대로 실행하는 호출 계약**이다 — 새 판정 규칙을 만드는 자리가 아니다.

- **구조(무엇을 만들고 어떤 형태로 내놓는가)**: `specs/g5-proposal-email-dispatch.md`
- **번역 검증 판정 문장**: `criteria/g7-reply-processing.md` — **G5 전용 카드는 없다.** 그 카드 3절이 스스로 *"G7 전용이 아니다, G5의 발신 번역도 이 기준을 그대로 쓴다"*고 지정했고, 층3만 방향이 반대라 「G5(발신)」 행이 따로 있다. **카드 전체를 읽고 그중 3절이 이 판정의 자리다** — 새 번역 기준을 만들지 않는다.
- **운영 변수(일일 발송 상한·승인 화면 형태)**: `../../docs/deployment-assumptions.md` **1·1-1·1-2절**이 유일한 출처다. **값을 이 파일에 옮겨 적지 않는다** — 매 실행마다 그 문서를 읽어 그때의 값을 쓴다.

**매 실행마다 위 셋을 다시 읽는다.** 이 스킬 본문과 그 문서들이 어긋나면 **문서가 이긴다.**

## 실행 단위가 넷이다 (2026-08-06 — 승인 판독 분리로 셋에서 늘어남)

| 단위 | 누구 | 왜 갈랐나 |
|---|---|---|
| 오케스트레이션·추출·발송 기록 | **이 스킬** | 검증 입력을 **추출**하는 자리와 발송 권한을 쥔 자리는 같아야 한다 — 게이트를 통과시키는 쪽이 문안을 만든 쪽이면 게이트가 아니다. **단 승인 여부 자체를 판독하는 일은 이 자리에서 뗐다(아래)** |
| 문안 제작·일본어 작성 | `g5-copy-drafting` | 재번역이 **앞 회차를 못 본 컨텍스트**에서 일어나야 하고, Spec 「독립 컨텍스트」가 세그먼트 1개를 제작의 1단위로 못박았다 |
| 번역 검증 | `g5-translation-verification` | Spec 「제약」 — *"발신 번역은 발신 주체가 스스로 검증하지 않는다"*. 검증자에게는 **한국어 의도와 일본어 문안 두 블록만** 준다 |
| 승인 판독 | `g5-approval-check` | Spec 「제약」(2026-08-06 신설) — *"승인 여부 판독은 발송 권한을 쥔 실행 단위가 스스로 하지 않는다"*. 이 스킬은 발송 기록을 쓸 `Write` 권한이 있어, 같은 실행이 승인란까지 스스로 읽고 판정하면 **발송 권한을 쥔 쪽이 스스로 승인을 판단하는 것과 물리적으로 다르지 않다**. `g5-approval-check`은 `Read`만 가지고 있어 승인란을 대신 채울 수 없다 |

**`g7-translation-verification`을 재사용하지 않았다.** 기준 카드는 공용을 선언했지만 그 서브에이전트의 「받는 것」이 *"일본어 원문 + 한국어 해석"* 한 방향으로만 쓰여 있고, 층3도 카드의 「G7(회신 해석)」 행을 향한다. G5는 원문이 한국어이고 번역이 일본어라 **같은 카드의 다른 행**을 써야 한다 — 방향이 반대인 실행체를 돌려쓰면 카드의 어느 줄을 볼지가 실행 중에 갈린다.

## 산출물 자리

G1 산출물(`data/candidates/후보목록.md`)과 같은 디렉터리 층에 둔다 — `g7-reply-processing`가 `data/replies/`를, `g2-segmentation`가 `data/segments/`를, `g4-contact-acquisition`가 `data/contacts/`를 놓은 것과 같은 규칙이다.

| 무엇 | 자리 |
|---|---|
| 입력 — 세그먼트 정의 | `data/segments/SEG-{축코드}-v{버전}.md` 중 **가장 최신 1개** |
| 입력 — G1 관찰 근거 | `data/candidates/후보목록.md` (**식별자로 해당 섹션만** 조회) |
| 입력 — 연락처 | `data/contacts/{기업식별자}.md` |
| 입력 — 수신 거부 목록 | `data/발송금지.md` |
| 출력 — 승인 화면(제작 모드) | `data/발송대기/{세그먼트ID}-{작성일}.md` |
| 출력 — 검증 입력 감사 기록 | `data/발송대기/_검증입력/{기업식별자}-r{n}.md` |
| 출력 — 발송 기록(발송 모드) | `data/발송기록/{기업식별자}-{발송일시}.md` |

- **`data/발송금지.md`가 없으면 등재 0건이다.** 파일 부재를 확인 근거로 그대로 적는다. **이 스킬은 그 파일을 만들지도 고치지도 않는다** — G7·G1이 쓰는 자리다.
- **Spec 「출력 형식」이 이름 붙인 것은 `data/발송기록/` 하나뿐이다.** `data/발송대기/`와 `_검증입력/`은 승인 게이트와 검증 감사가 실제로 걸리려면 있어야 하는 자리라 이 실행체가 잡았다 — 사람이 Spec에 다른 자리를 써 넣으면 그쪽이 이긴다.
- **`_검증입력/`은 감사 기록이다** — 검증 단위가 실제로 무엇만 봤는지의 증거이자, 재번역이 일어났을 때 두 일본어 문안을 보존하는 자리다. 지우지 않는다.

## 인자

```
/g5-proposal-email-dispatch 제작 S1
/g5-proposal-email-dispatch 발송 data/발송대기/{세그먼트ID}-{작성일}.md
```

**인자에 세그먼트가 둘 이상 식별되면 실행하지 않고** "세그먼트 1개씩 나눠 호출해 달라"고 되돌린다 — Spec의 「세그먼트 1개 = 대표 문안 제작의 컨텍스트 1단위」 경계를 실행 층에서 지키는 조치다.

**모드를 생략하면 「제작」으로 본다. 「제작」이 「발송」으로 이어서 넘어가는 경로는 없다** — 아래 4번.

# 모드 1 — 제작

**1. 대상 확정.** 최신 세그먼트 정의에서 그 세그먼트의 **무리 규정 · 대표 식별자 · 소속 목록**을 읽는다. 소속 각각에 대해 `data/contacts/{기업식별자}.md`를 열어 상태를 확인한다.

| 상태 | 처리 |
|---|---|
| **[확보]** | 발송 대상 |
| [발송 금지]·[메일 없음]·[미확보] | **발송 대상에서 뺀다**(Spec 「입력」이 받는 것은 [확보]뿐). 뺀 사유를 승인 화면에 남긴다 |
| `data/contacts/` 파일 자체가 없음 | 같음 — **G4를 아직 안 돌린 것**이고 이 스킬이 대신 찾지 않는다 |

- **대표가 [확보]가 아니어도 대표 문안은 만든다.** Spec 「입력」의 단위 M은 세그먼트 정의·G1 관찰 근거·회사 자산만 요구하고 연락처를 요구하지 않는다 — 연락처는 단위 E의 입력이다. 대표는 발송 대상에서만 빠지고, 그 문안은 확장의 틀로 그대로 쓰인다.
- **세그먼트 정의 파일 머리에 「시험 실행 — 확정 배정 아님」 표시가 있으면 승인 화면과 보고에 그대로 옮겨 적는다.** 거르지도 멈추지도 않는다 — Spec 「입력」에 시험 실행본을 거르는 조건이 없어 이 실행체가 그 조건을 만들면 발명이 된다.

**2. 재료를 뽑는다.** 문안 단위는 저장소를 스스로 뒤지지 않는다 — 프롬프트로 넘길 블록을 여기서 만든다.

| 넘긴다 | 넘기지 않는다 |
|---|---|
| 대상 기업의 **G1 관찰층 전문**(식별자로 조회한 그 섹션만) | 후보 목록 전체 · 다른 세그먼트 기업의 관찰값 |
| **허용된 회사 자산 블록** — 무엇을 만드는 회사이고 무엇을 제공하는가, 다국어 대응 여부 | **레퍼런스 사례**(인용 허가 `(미확인)`) · **가격·단가·할인율**(회사 비공개 자료) |
| 법정 표시 4종에 채울 값 — **확인된 것만.** 미확인은 `(미확인)`이라고 그대로 넘긴다 | 승인 상태 · 앞 회차 검증 결과 |

**3. 문안 — `g5-copy-drafting`을 Agent 도구로 호출한다. 순서를 지킨다.**

- **먼저 모드 M(대표 1곳)을 호출하고, 그 응답을 받은 뒤에 모드 E(소속 전체)를 호출한다.** 동시에 부르지 않는다 — Spec 「성공 기준」의 *"대표 문안 제작이 세그먼트 단위로 먼저이고 확장이 그 뒤에 옴(순서 위반 0건)"*은 이 자리에서만 지켜진다.
- **확장 대상이 0곳이면 0곳인 채로 진행한다.** 대표 문안 1건만 승인 화면에 올리고, 확장 0곳과 그 사유(어느 기업이 어떤 상태라 빠졌는가)를 승인 화면에 적는다. **없는 대상을 만들어 확장을 시연하지 않는다.**
- 모드 E 호출에는 **소속 기업 각각의 관찰층을 따로** 넣는다 — 인용을 기업마다 다르게 하려면 그 재료가 각자 있어야 한다.

**4. 검증 입력을 뽑는다 — 여기가 문안 단위와 검증 단위를 가르는 지점이다.**

문안 1건마다, 응답에서 **한국어 발신 의도 전문**과 **일본어 발신 문안(제목 + 본문)**, 이 둘만 복사해 `data/발송대기/_검증입력/{기업식별자}-r1.md`에 쓴다.

| 넣는다 | 넣지 않는다 |
|---|---|
| 한국어 의도 전문 (**손대지 않고 그대로**) | 인용한 관찰 근거 항목·세그먼트 ID·기업 식별자 |
| 일본어 제목 + 본문 전문 (**그대로**) | 제안한 것 요약 · 법정 표시 자리 표 · 문안 틀 |
| | 문안 단위가 보고한 걸린 것 · 이 스킬의 자체 점검 결과 · 승인 상태 |

**5. 검증 — `g5-translation-verification`을 Agent 도구로 호출한다. 문안 1건 = 호출 1회다.**

**검증 단위에게 파일 경로를 주지 않는다.** 4번의 두 블록을 **프롬프트에 그대로 인라인**해 넘긴다(요약·재서술하지 않는다). 돌려받은 판정을 **그대로** 승인 화면의 그 건에 옮겨 적는다.

**6. 분기.**

| 상태 | 처리 |
|---|---|
| 3층 전부 일치 | 7번으로 |
| 한 층이라도 불일치 (1회차) | **`g5-copy-drafting`을 모드 R로 새로 호출해 재번역 1회.** 한국어 의도 전문 + 검증이 지목한 불일치 지점만 준다 — **1회차 일본어 문안은 주지 않는다.** 새 문안으로 `-r2.md`를 만들어 4번을 되풀이하고 **`g5-translation-verification`을 새로 호출한다**(검증한 컨텍스트가 이어지면 자기 지적을 통과시킨다) |
| 2회차도 불일치 | **그 건을 발송 대기열에서 뺀다.** 승인 화면의 그 건에 `발송 불가 — 번역 검증 2회 불일치`와 함께 한국어 의도·두 일본어 문안(`-r1`·`-r2`)·안 맞은 지점을 남기고, 8번 보고에서 사람에게 올린다. 어느 쪽 일본어도 확정으로 제시하지 않는다 |
| 검증을 못 받았다 (호출 실패·응답 없음) | 그 건에 `검증 미완 — 승인 대상 아님`을 남긴다. **무관용 판정은 검증층이 채워진 뒤에만 가능하다** |

**7. 승인 화면을 쓴다 — 그리고 여기서 종료한다.**

`data/발송대기/{세그먼트ID}-{작성일}.md`를 쓴다. **형태는 `../../docs/deployment-assumptions.md` 1-2절 「승인 화면 형태」 행이 정본이며, 그 행을 그때그때 읽어 그대로 따른다** — 여기에 요약해 옮기지 않는다.

**아래 표는 「무엇을 담는가」이지 「화면을 어떻게 짜는가」가 아니다** — 항목의 출처는 `specs/g5-proposal-email-dispatch.md`이고(「출력 형식」 — G6·G7·G11이 나중에 요구하는 것 포함, 그리고 「제약」·「성공 기준」 무관용 항목 전부가 발송 모드에서 확인하라고 정한 것), 배치·표시 형태는 위 `docs/50` 1-2절이다. 둘이 어긋나 보이면 **항목은 Spec, 형태는 `docs/50`**이 각각 이긴다.

한 건마다 아래를 담는다. **승인란은 비운 채 둔다.**

| 칸 | 내용 |
|---|---|
| 기업 식별자 · 수신 주소 · 유효 등급 | `data/contacts/`에서 |
| 세그먼트 ID · 대표인가 확장인가 | |
| 한국어 의도 전문 / 일본어 제목 / 일본어 본문 | 문안 단위 응답 그대로 |
| 인용한 G1 관찰 근거 | 항목 코드 + 값 + 본문의 어느 문장 |
| 제안한 것 | |
| 발신 언어 · 번역 검증 결과 | 3층 각각의 판정, 라운드 수 |
| 법정 표시 4종 확인 | 4종 각각 있음/`(미확인)` |
| `data/발송금지.md` 확인 | 등재 여부 + 확인일 |
| 일일 발송 상한 배정 | 이번 회차 포함 / 다음 회차 보류 |
| **승인란 — 승인 / 거부 · 승인자 · 승인일시 · 거부 사유** | **빈칸.** 사람이 직접 적는다 |

그리고 발송 상한을 계산한다 — `../../docs/deployment-assumptions.md` **1-1절**의 값이 이번 회차의 상한이다.

- **값이 범위로 적혀 있으면 하한을 쓴다.** 그 절이 이 값을 예외로 둔 이유가 도메인 평판의 비용 비대칭(넘치는 쪽이 손해)이므로 방향이 이미 정해져 있다. 이것이 새 판별선으로 읽힐 자리라는 것을 밝혀 둔다 — 사람이 정할 자리다.
- **값이 아예 없으면 발송하지 않고 전량 보류한다** — 그 절이 *"①~③과 달리 값이 없다고 무제한으로 밀어붙이지 않는다"*고 못박았다.
- 상한을 넘는 만큼은 **세그먼트별로 고르게(라운드로빈)** 다음 회차 보류로 표시한다. 한 세그먼트가 상한을 다 채우게 두지 않는다.

**⛔ 승인 정지점이다. 이 실행은 여기서 끝난다.**

- **발송 모드로 이어서 넘어가지 않는다. 승인을 기다리는 대기 루프를 만들지 않는다.** 대기 루프가 없으면 타임아웃도 없고, 자동 재개는 금지가 아니라 **불가능**이 된다. 이것이 브리프 요구 ③(반자동)의 구조적 실현이다.
- **이 모드는 `data/발송기록/`에 어떤 파일도 쓰지 않는다.**
- **승인란을 스스로 채우지 않는다.** 사람이 승인 화면 파일에 직접 적는다 — 이 스킬이 채운 승인은 승인이 아니다.

**8. 자체 점검과 보고.** `specs/g5-proposal-email-dispatch.md` 「성공 기준」 **서식 점검** 5항목으로 이 회차를 대조하고, 대조 결과를 승인 화면 파일 안에 남긴다 — 파일만 받은 사람이 점검이 돌았는지 알 수 있어야 한다.

- **인용 근거가 기업마다 다른지는 문안을 실제로 대조해 센다.** 같은 세그먼트 안에서 인용 문장이 완전히 동일한 건이 1건이라도 나오면 그 건을 `g5-copy-drafting` 모드 E로 되돌려 다시 만들게 하고, 다시 4~6번을 돈다. **"다르게 만들었다"는 문안 단위의 서술을 근거로 통과시키지 않는다.**
- **무관용 항목은 여기서 판정하지 않는다** — 승인 기록이 아직 없으므로 판정 자체가 성립하지 않는다. 발송 모드 2번이 한다.
- 보고는 **"무엇을 승인해야 하는가"**를 중심으로 한다. 승인 화면 경로 · 승인 대기 건수 · 발송 불가로 빠진 건과 사유 · 확장 0곳이면 그 사실이 사용자에게 도달해야 이 실행이 끝난다.

# 모드 2 — 발송

**사람이 승인 화면에 승인을 적은 뒤에 별도로 호출된다.** 문안을 만들지 않고 고치지 않는다 — 승인받은 문안과 발송되는 문안이 다르면 그 승인은 무효다.

**1. 승인란을 직접 읽지 않는다 — `g5-approval-check`을 Agent 도구로 호출한다.** 받은 발송대기 파일 경로를 그대로 넘긴다. **이 스킬 자신은 승인란을 읽고 판정하지 않는다** — 발송 기록을 쓸 권한을 쥔 실행이 승인 여부까지 스스로 판단하면 게이트가 아니다. 돌아온 판정을 **그대로** 따른다.

| `g5-approval-check` 판정 | 처리 |
|---|---|
| 승인 | 2번으로 |
| 미승인 | **발송하지 않는다.** 대기 상태로 둔다 |
| 거부 | **발송하지 않는다.** 거부 사유가 있으면 그 사유를 문안 개선 재료로 그 파일에 남긴다. 스스로 재승인을 요청하거나 문안을 고쳐 다시 올리지 않는다 |

**모든 건이 미승인이면 아무것도 발송하지 않고 종료한다.** 이 스킬은 승인란을 쓰지 않는다.

**2. 승인된 건마다 무관용 항목 전부를 재확인한다.** `specs/g5-proposal-email-dispatch.md` 「성공 기준」의 무관용 항목이 정본이며(개수는 여기서 세지 않는다 — 그 절이 정본), **하나라도 어기면 그 건의 발송 기록을 쓰지 않는다.**

| 확인 | 어디서 |
|---|---|
| 사람 승인 기록이 있다(승인자·승인일시) | 1번 결과 |
| 번역 검증 3층이 전부 일치 판정된 뒤다 | 승인 화면의 검증 결과 칸 |
| 법정 표시 의무 4종이 본문(또는 링크)에 모두 있다 | **일본어 본문을 직접 다시 본다.** `(미확인)`이 하나라도 남아 있으면 미충족이다 |
| 레퍼런스 사례·가격 자료가 인용되지 않았다 | 같음 |
| 수신 주소가 `data/발송금지.md`에 없다 | **`data/발송금지.md`를 지금 다시 연다** — 승인 이후에 등재됐을 수 있다 |

**3. 일일 발송 상한을 다시 확인한다.** `../../docs/deployment-assumptions.md` 1-1절의 값(제작 모드 7번과 같은 규칙)으로, 이번 실행에서 실제로 발송하는 건수를 센다. 넘는 만큼은 세그먼트별 라운드로빈으로 다음 회차 보류다.

**4. 발송한다.** 통과한 건마다 `data/발송기록/{기업식별자}-{발송일시}.md` 1개를 쓴다. 항목은 Spec 「출력 형식」의 표가 정본이며 **한 칸도 비우지 않는다** — 세그먼트·인용 근거·제안 내용·발신 언어와 번역 검증 결과는 G11이 나중에 요구하는 항목이고, **발송 시점에 안 남기면 소급해서 만들 수 없다.** 실제 메일 발송은 이 스킬이 하지 않는다(`disallowed-tools: Bash`) — 이 파일이 새로 쓰인 것을 감지해 실제로 보내는 것은 외부 시스템의 일이고, 그 자리의 더미는 `../../api/dummy_send_api.sh`다.

> **⚠ 이 저장소에는 실제 메일 발송 인프라가 없다.** 발송 전용 주소 등록·발송 서비스 연결은 사람이 하는 일회성 설정이며 이 스킬이 하지 않는다. **그때까지 「발송」은 위 발송 기록 파일을 쓰는 것으로 대체한다.** 실제 발송 도구가 붙으면 그 호출이 들어갈 자리는 **이 4번 안, 발송 기록을 쓰기 직전**이다 — 게이트(1·2번)의 위치는 그대로다.

**5. 자체 점검과 보고.** 「성공 기준」의 무관용 항목 전부 + 서식 점검 5 전부로 대조하고 결과를 각 발송 기록 파일에 남긴다. 걸린 항목이 있으면 그 건은 발송 기록을 쓰지 않고 사유와 함께 승인 화면 파일로 되돌린다.

보고는 **발송 건수 · 발송하지 않은 건과 그 사유 · 다음 회차 보류분**을 중심으로 한다.

## 규칙이 없는 경계에서 멈춘다

Spec이 침묵하는 자리에서 판정 문장을 스스로 만들지 않는다. 아래에 걸리면 그 건을 확정하지 않고 산출물에 「판정 보류 — 규칙 없음」과 무엇이 없는지를 적은 뒤 사용자에게 올린다.

| 자리 | 멈추는 조건 |
|---|---|
| **법정 표시 4종의 값** | 확인된 값이 없을 때. **추정치로 채우지 않는다** — 채우면 위법 표시를 우리가 만든 것이 된다 |
| **승인 해석** | 승인란에 「승인」·「거부」가 아닌 표현이 적혔을 때. **애매하면 승인이 아니다** |
| **발송 상한** | `docs/50` 1-1절에 값이 없을 때 — 전량 보류하고 무제한으로 읽지 않는다 |

## 이 스킬이 하지 않는 것

`specs/g5-proposal-email-dispatch.md` 「범위」의 제외 목록과 같다 — 세그먼트화(G2), 적합도 평가(G3), 연락처 탐색(G4), 번역 검증 기준을 새로 정하는 것(`criteria/g7-reply-processing.md` 3절이 정본), 발송 결과 판정(G6). 그리고 **승인을 대신하는 일**과 **판정 기준 문장 자체를 고치는 일**(실제로 보내 본 사람이 `criteria/g7-reply-processing.md`에 직접 고치고 그 카드 5절 변경 이력에 남긴다).
