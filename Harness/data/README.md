# data/ — 파이프라인 실행 산출물

`specs/`가 12개 기능의 **정의**(무엇을 어떻게 판정하는가)라면, 이 폴더는 그 기능들이 **실제로 돌 때 읽고 쓰는 값**이 쌓이는 자리다. 지금은 G1(대상 기업 발굴)부터 G7(회신 해석)·G12(질의응답)까지 한 번 실행한 결과가 채워져 있다 — 후보 12곳 → 세그먼트 3개(S1 여성 의류·S2 코스메틱·S3 푸드) + 미분류 4곳 → 연락처 확보 결과가 [확보]/[메일 없음]/[미확보]로 갈리고 → 대표 2곳(ingni-store-com·orbis-co-jp)에 실제로 발송해 서로 다른 회신(관심 표명 / 이유 있는 거절)을 받은 실행 1회분이다. G3·G8~G11(부가 기능)은 아직 착수 전이라 비어 있다.

## 메일 발송과의 경계 — 무엇이 이 폴더의 일이고 무엇이 아닌가

**실제로 메일을 발송·수신하는 행위(MCP·API 호출, SMTP 연결 등)는 이 하네스의 범위가 아니다** — 별도 인프라가 하는 일이다. 이 하네스가 책임지는 것은 **그 인프라에 넘길 내용을 만드는 것**까지다:

- **수신 주소** — `contacts/{기업식별자}.md`(G4가 확보)를 `발송기록/`을 쓸 때(G5) 그대로 옮겨 적는다.
- **발신 문안(제목·본문, 일본어)** — G5가 만들고 번역 검증까지 마친 뒤 `발송기록/`에 쓴다.
- **발송 여부 판단(승인 게이트)** — 사람이 승인 기록을 채운 건만 G5가 위 두 값을 확정해 `발송기록/`에 낸다.

즉 **`발송기록/{기업식별자}-{발송일시}.md` 한 파일이 "누구에게 무엇을 보낼지"의 최종 확정 값이다.** 실제 발송 도구는 이 파일을 입력으로 읽어 호출하면 되고, 그 호출 결과(성공/바운스)는 반대로 `상태/`에 다시 기록되는 입구가 된다(G6). 발송 성공·바운스·회신 수신 같은 **인프라 이벤트 자체**는 이 하네스가 관측할 수 없으므로, 그 이벤트가 도착했다는 사실을 사람이나 연동 도구가 G6·G7에 넘겨주는 것부터 다시 이 하네스의 일이다.

## 하위 자리 (기능이 실제로 만든다 — 여기서 미리 만들지 않는다)

| 자리 | 기능 | 내용 |
|---|---|---|
| `candidates/후보목록.md` | G1 | 후보 기업 단일 파일(섹션 append) |
| `candidates/보류목록.md` | G4 append | [메일 없음]·[미확보] 잔여 |
| `segments/` | G2 | 세그먼트 정의 |
| `scores/` | G3 | 적합도 채점·순위표 |
| `contacts/` | G4 | 연락처 확보 결과 |
| `연락처후보/` | G9 | 사람이 찾아온 연락처 원값 |
| `발송대기/` | G5(제작) | 승인 대기 큐 |
| `발송기록/` | G5(발송) | **수신 주소 + 발신 문안 확정본** — 위 경계의 핵심 산출물 |
| `상태/` | G6 | 발송 건 상태([회신]/[무응답]/[주소 오류]) |
| `replies/` | G7 | 회신 해석·분류 레코드 |
| `원인분석/` | G8 | 무응답·오류 원인 가설 |
| `위임브리프/` | G9 | 사람 접촉 위임 브리프 |
| `재수집대상/` | G10 | 재수집 판단 결과 |
| `집계/` | G11 | 세그먼트·조건별 반응 집계 |
| `질의응답로그/` | G12 | 질의응답 로그 |
| `발송금지.md` | G7 append(+G1) | 수신 거부 목록 (append 전용) |
| `실행상태.md` | run-orchestrator | 리듬·스텝·사람 대기 상태 |

각 파일의 정확한 형식(항목·키)은 해당 기능의 `../specs/`와 `../criteria/`가 정본이다 — 여기서 다시 정의하지 않는다.
