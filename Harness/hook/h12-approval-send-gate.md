# H12 — 발송 승인 게이트 (승인란 작성 감지)

| 항목 | 내용 |
|---|---|
| 트리거 종류 | 이벤트 — **이 실행 환경(Claude Code) 자신이 관측할 수 있는 사건**이라 H9와 같은 부류다(나머지 10개와 다르다) |
| 트리거 조건 | `data/발송대기/*.md` 파일에 대한 Edit·Write·MultiEdit 도구 호출이 끝났고, 그 변경이 「승인 / 거부」 칸을 **「승인」으로** 채웠다 |
| 캡처할 신호 | 그 발송대기 파일의 경로 |
| 호출 대상 | `/g5-proposal-email-dispatch` (발송 모드) |
| 인자 형식 | `발송 <발송대기 파일 경로>` |
| 비고 | **리스크 43(무인 실행 권한이 발송 모드와 공유될 위험)을 코드 레벨로 좁히는 자리다.** 이 훅은 "승인됐다"고 스스로 최종 판정하지 않는다 — 문자열이 「승인」으로 바뀐 것을 보고 발송 모드를 **트리거만** 할 뿐이고, 실제 승인 여부·법정 표시·번역 검증 같은 무관용 재확인은 여전히 `g5-proposal-email-dispatch` 발송 모드 1~2번(`g5-approval-check` 호출 포함)이 한다. 즉 이 훅이 오탐(예: 「거부」를 「승인」으로 잘못 감지)해도 실제로 그르게 보내지는 것을 막는 것은 여전히 그 아래 게이트다 — 이 훅은 "사람이 언제 승인했는지"를 코드로 감지해 그 시점에 자동으로 발송 절차를 시작시키는 것이 전부다. **거부·미승인으로 바뀐 편집에는 반응하지 않는다.** 같은 파일이 승인 이후 다시 저장돼도 중복 트리거될 수 있다 — 중복 발송 방지는 이 훅이 아니라 발송 모드 자신의 일이다(이미 발송된 건은 재확인 시 `발송기록/`에 흔적이 있어야 한다는 전제가 있다면 그쪽에서 막아야 한다 — 지금은 확인되지 않은 가정이라 `docs/93_구현_검증대기.md`에 등록한다). **전제**: 승인란을 Claude Code로(대화 세션 안에서 Edit/Write로) 직접 고칠 때만 작동한다 — 나중에 별도 화면(웹 등)으로 승인을 처리하게 되면 그건 이 환경 밖의 사건이라 나머지 10개처럼 별도 감지 수단이 필요하다 |
