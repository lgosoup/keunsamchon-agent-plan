# hook/ — 자동 트리거 명세

이 폴더는 이 하네스가 필요로 하는 12개 자동 트리거(Hook)의 명세다(H1~H11 + 2026-08-10 신설 H12). **구현(실제로 어떻게 감시·스케줄링할지)은 이 하네스를 실행하는 플랫폼에서 사람이 직접 한다** — 여기서는 각 Hook이 (a) 언제 눌려야 하는지 (b) 무엇을 신호로 캡처해야 하는지 (c) 어느 스킬을 어떤 인자 형식으로 호출해야 하는지만 정의한다. `skills/*/SKILL.md`는 전부 이 신호를 슬래시 명령 인자로 받는 것을 전제로 이미 만들어져 있다 — Hook은 그 인자를 채워서 호출만 하면 된다.

**부트캠프 템플릿 예시(`settings.json` + `subagent_log.sh`)와 형식이 다른 이유**: 그 예시는 Claude Code 자체의 후킹 메커니즘(도구 호출 전후 자동 로깅·검증)이다. 이 하네스의 실행 플랫폼은 Claude Code가 아니고, 그 플랫폼의 Hook 설정 형식은 아직 정해지지 않았다(구현은 사람이 별도로 한다). 그래서 이 폴더는 설정 파일 형식이 아니라, **어느 플랫폼에 옮기든 그대로 구현할 수 있는 조건·신호·호출 계약 명세**로 채운다.

## H9·H12는 실제 구현, 나머지 10개는 더미 모듈이 있다 (2026-08-10)

12개 중 **H9(criteria 수정 감지)·H12(발송 승인 감지)는 Claude Code 자체의 Hook 메커니즘으로 실제 구현**됐다 — 둘 다 criteria/발송대기 파일 수정이라는, 이 실행 환경(Claude Code) 자신이 관측할 수 있는 사건이기 때문이다. **나머지 10개 중 8개(H2·H3·H4·H6·H7·H8·H10·H11)도 자체 구현으로 닫혔다** — 이 실행 환경 밖의 사건(시간 경과·파일 상태 변화)은 `.claude/hooks/dummy_platform_poll.sh`가 `specs/` 실제 상태를 직접 훑어 판정하고, 이 폴러 자체는 Windows 작업 스케줄러(매일 09:00)가 주기적으로 돌린다 — **외부 플랫폼이나 팀원을 전제하지 않는다.** **H1(회신 도착)은 2026-08-14 IMAP 폴링으로 감지 층까지 실제 구현됐다(아래 절).** H5(신규 후보 소스)만 감지할 실제 원천 데이터가 없어 아직 못 닫았다.

## H1은 감지 층까지 실제 구현됐다 — `imap_reply_poller.py` (2026-08-14)

**10개 더미 중 H1만 "언제 불러야 하는가"(감지)까지 실물이 생겼다.** `imap_reply_poller.py`가 IMAP으로 메일함을 직접 열어 새 회신을 꺼내고, 이 폴더의 H1 카드가 정의한 계약(`mail_raw`·`from`·`received_at`·`subject`·`thread_id`·`attachments`·`matched_send_record`)을 **그대로** 채운다. `hook_h01_reply_detected.sh`는 손대지 않았다 — 그 더미가 남겨 둔 감지 앞단을 채운 것이지, 뒷단 계약을 바꾼 것이 아니다.

```
[메일함] → imap_reply_poller.py → h01 계약 JSON → /g7-회신처리 → specs/replies/*.md → 웹 회신함
             ↑ 지금까지 비어 있던 자리
```

- **왜 Resend inbound가 아니라 IMAP인가**: Resend로 회신을 받으려면 도메인 인증 + MX 레코드 지정이 필요한데, 발송 도메인 정책은 기업 답변 대기 항목이라 임의로 확정하지 않기로 했다(root `docs/10` 6절 #8). 회신은 어차피 발신에 쓴 계정의 받은편지함으로 오므로 IMAP은 **도메인 없이 지금 동작한다.**
- **기업 대조는 추측하지 않는다**: 제목(Re: 접두어 제거 후)으로 `specs/발송기록/`을 대조하고, 못 찾으면 빈 값으로 넘겨 G7이 이미 쓰는 `-미확정` 관례로 잇는다.
- **원시 캡처는 `specs/replies/`에 넣지 않는다** — 거기는 G7이 만든 완성 레코드만 있어야 하고 웹 회신함이 그 폴더를 통째로 읽기 때문이다. 캡처는 `specs/_수신함/`에 쌓인다.
- **가져오는 것만으로 읽음 처리되지 않는다**(`BODY.PEEK`). 저장에 성공한 뒤에만 `\Seen`을 붙인다 — 실패한 메일이 조용히 사라지면 회신 1건을 통째로 잃는다.
- **자기발신 제외 게이트**가 있다 — 이게 없으면 받은편지함의 무관한 메일까지 무차별로 가져온다. 판별은 제목이 우리 발송 제목과 일치하는지가 공통 필수 조건이고, 발신자가 우리 발신 주소 자신이면(자기 계정 시연 구성) 회신이 아니라 자기 발송분으로 제외한다.
- **시연 회신은 `합성시연-` 접두어로 구분되도록 G7에 지시한다** — 발신자가 `DEMO_RECIPIENT`와 같으면 실제 기업 응답이 아니라 우리가 우리에게 보낸 시연이라는 뜻이고, 그 사실이 파일명·집계·`발송금지.md`까지 전달돼야 실제 기업 주소가 시연 때문에 영구 차단되는 사고를 막는다(`specs/발송금지.md` 정정 기록 참고).
- **하트비트**(`specs/_watch.json`)를 매 회차 남긴다 — 이게 없으면 "회신이 안 온 것"과 "감시가 죽은 것"을 웹이 구분하지 못한다.
- 기본은 **감지·저장만** 하고 G7을 부르지 않는다. `--watch`(주기 폴링)·`--dispatch`(G7 자동 호출)를 붙여야 무인으로 돈다. `IMAP_USER`·`IMAP_PASS`(Gmail은 **앱 비밀번호**)가 없으면 접속조차 시도하지 않는다(세이프페일).

- `settings.json` — `PostToolUse`(Edit·Write·MultiEdit) 훅 등록. 부트캠프 템플릿 예시와 같은 형식이다. H9·H12 둘 다 여기 등록된다.
- `hook_h9_criteria_review.sh` — criteria 파일 수정을 감지해 변경 전/후 값으로 정합성 검토 질문을 조립하고 `/g12-qna`를 호출한다.
- `hook_h12_approval_send_gate.sh` — `data/발송대기/*.md`(`_검증입력/` 제외)의 「승인 / 거부」 칸이 「승인」으로 바뀐 것을 감지해 `/g5-proposal-email-dispatch 발송 <경로>`를 호출한다. **리스크 43(무인 실행 권한이 발송 모드와 공유될 위험)을 코드로 좁히는 자리** — "승인이 코드로 확인된 시점에만 발송 절차가 시작된다"는 것을 이 훅이 보장하고, 실제 승인·무관용 재확인은 여전히 발송 모드 자신(`g5-approval-check` 포함)이 한다.
- `hook_h01_reply_detected.sh` ~ `hook_h11_g9_brief_generation_cycle.sh`(10개) — **이 Harness 제출판 자체는 자기완결 예시로 남긴다.** "언제 불러야 하는가"(감지·스케줄링)는 이 스크립트 안에 없다 — 각 카드의 「인자 형식」대로 stdin에 JSON을 넣어 호출해 줄 것을 전제한다. 이 스크립트가 하는 일은 딱 셋뿐이다: (a) 입력 수신 로그 (b) 대상 스킬을 정해진 인자로 호출 (c) 전달 로그. 조건 계산(예: H3의 10영업일 경과 여부, H8의 5건 누적 여부)은 스크립트 안에 없다 — 호출됐다는 것 자체가 "그 조건이 이미 맞았다"는 전제다. 로그는 전부 `../data/hook로그/h0N.log`에 쌓인다. **감지·스케줄링을 실제로 채운 자리는 이 저장소의 라이브 사본(`.claude/hooks/`)이다** — `dummy_platform_poll.sh` + Windows 작업 스케줄러(위 절 참조). Harness 쪽은 제출 패키지의 이식성을 위해 감지 로직 없는 원형 그대로 둔다.

**이 Harness 제출판(`Harness/hook/*.sh`) 자체는 H9·H12를 제외하면 예시 구현으로 남긴다** — 무인 배치 환경에서의 권한·비용 처리와 실제 감지·스케줄링은 스크립트 주석에 남겨 두고 완결짓지 않았다(이식 대상 실행 환경마다 다를 수 있어서다). 다른 환경에 옮길 때는 각 스크립트를 그 환경의 감지 방식으로 바꿔치기하되, 스크립트 머리 주석의 입력 형식(stdin JSON 필드)만 유지하면 대상 스킬 호출부는 그대로 쓸 수 있다. **이 저장소 자신의 라이브 실행은 이미 그 감지·스케줄링을 자체 구현으로 채웠다** — 위 절 참조. **H12의 전제**: 승인란을 Claude Code로 직접 고칠 때만 작동한다 — 나중에 별도 화면(웹 등)으로 승인을 처리하게 되면 그건 이 환경 밖의 사건이라 다른 감지 수단이 필요하다(그때는 H12도 더미 쪽으로 넘어간다).

## 세 갈래로 나뉜다

- **독립 진입(외부 사건·스케줄)**: H1·H2·H3·H5·H6·H7·H8·H9·H11·H12 — 이 하네스 밖에서 오는 신호가 새 실행을 깨운다(H12는 "밖"이 이 환경 안의 사람 편집이라는 점이 H9와 같다).
- **종속 파생(다른 실행의 결과가 만드는 후속 호출)**: H4·H10 — 독립된 외부 신호가 아니라 다른 Hook이 이미 돌린 실행의 산출물이 그 자리에서 다음 호출을 만든다.
- **읽기 전용 조회는 이 목록에 없다**: `g12-qna`(H9 제외)는 사람이 언제든 직접 부르는 별도 진입점이라 Hook이 아니다.
