# 34. 사용자 흐름 — 완성 시 실제로 어떻게 쓰이는가

> **이 문서의 위치**: `31_기능구조.md`가 기능 경계·입출력을 확정했다면, 여기는 **그 기능들을 사람이 실제로 언제·어떻게 마주치는가**를 시간 축으로 다시 배열한 것이다. 기능 정의·판정 기준은 여기서 새로 쓰지 않는다 — `31`·`specs/`·`기준/`을 참조만 한다. **여기서 확정하는 것은 리듬(언제 도는가)과 사람이 실제로 멈추는 지점(어디서 기다리는가)이다.**
>
> **작성 시점(2026-08-05) 상태**: G1(대상기업발굴)·G2(세그먼트화)·G7(회신해석정리)만 실행체(Skill/Subagent)가 있고 실제로 돈다(`.claude/README.md`). 나머지는 Spec까지만 확정됐다. 이 문서는 **G1~G11 + G12까지 전부 실행체를 갖춘 완성 상태**를 그린다 — `31` 8-1절의 MVP/부가 구분은 그대로 가져와 표시한다.

---

## 0. 왜 흐름을 리듬으로 나누는가 — 의도

`31`은 기능을 입출력으로 잇는다. 입출력이 이어진다고 해서 사람이 그걸 하나의 연속 동작으로 겪는 건 아니다. 속도가 다른 세 가지가 섞여 있다.

- **조사(G1~G4)는 요청하면 바로 도는 것**이다.
- **발송(G5)은 사람이 한 번은 반드시 멈춰야 하는 것**이다 — 브리프의 "반자동" 요구가 문장이 아니라 실제 정지점으로 존재하는 유일한 자리다(`31` 5절 ①, `90` #8).
- **반응(G6~G7)은 기다려야 오는 것**이다 — 발송과 시간차가 있다.

이 셋을 하나의 순서(①②③…)로 뭉쳐 적으면 "사람이 언제 실제로 화면 앞에 있어야 하는가"가 사라진다. 그래서 리듬별로 나눈다. **이 구분이 없으면 오케스트레이터를 만들 때 세 리듬을 하나의 파이프라인으로 잘못 짜기 쉽다** — 8절에서 이 위험을 구체적으로 짚는다.

---

## 1. 리듬 1 — 조사 체인 (온디맨드/주기, 자동 연쇄)

| 순서 | 기능 | 범위 | 사람이 하는 일 |
|---|---|---|---|
| 1 | G1 대상 기업 발굴 | MVP | 트리거만 — 실행 요청 또는 주기 실행 |
| 2 | G2 세그먼트화 | MVP | 없음 — G1 산출물로 자동 진행 |
| 3 | (부가) G3 적합도 평가 | 부가 | 없음 — 착수되면 자동으로 이 자리에 낌 |
| 4 | G4 연락처 확보 | MVP | 없음 — 세그먼트 대표 우선으로 자동 진행(부가 착수 시 적합도 우선으로 전환) |

**이 구간엔 사람이 멈출 이유가 없다.** 아직 아무것도 밖으로 나가지 않기 때문이다 — `31` 1-5절("컨택 기회 확보가 1순위")이 사전 검증 게이트를 없앤 것과 같은 이유로, 여기서 사람이 매번 승인할 필요는 없다.

---

## 2. 리듬 2 — 발송 (필수 승인 게이트, 무관용)

| 기능 | 범위 | 사람이 하는 일 |
|---|---|---|
| G5 제안 메일 제작·발송 | MVP | **대표 문안 + 번역 검증 결과를 보고 승인한다 — 승인해야만 발송된다** |

**이게 이 흐름 전체에서 가장 중요한 지점이다.** 승인 없이 발송되는 경로가 있으면 브리프 요구 ③(반자동)을 정면 위반한다(`specs/G5` 무관용 성공 기준 1번). 오케스트레이터가 "타임아웃 시 자동 승인" 같은 걸 넣으면 안 되는 이유가 여기 있다 — 8절 참조.

---

## 3. 리듬 3 — 반응 (비동기, 기다려야 온다)

| 기능 | 범위 | 사람이 하는 일 |
|---|---|---|
| G6 발송 결과 판정 | MVP | 없음 — 바운스/무응답/회신 상태 자동 판정 |
| G7 회신 해석·정리 | MVP | **회신이 오면 원문+한국어 해석+분류를 읽는다 — 이 흐름의 명시된 종점** |

**G7 다음은 이 프로젝트 밖이다.** 기업이 직접 그렇게 말했다 — *"담당자와 접촉이 성립됐을 때는 아마 대응이 좀 필요하잖아요… 보내기에 집중하기보다는 그분들과 관계를 형성해 나가는 부분에 집중할 것"*(`13S` F16). 미팅·견적·계약은 설계하지 않는다(`31` G7절). **여기서 사람이 하는 일은 "다음 실무 행동을 판단하는 것"이지 도구 안의 조작이 아니다.**

---

## 4. 부가 확장 — 착수되면 추가되는 것

| 기능 | 리듬 | 사람이 하는 일 |
|---|---|---|
| G9 사람 접촉 위임 브리프 | 큐(비정기) | 브리프를 보고 사람이 직접 접촉(주변·협력사) — 찾은 연락처는 G4로 되돌아감 |
| G10 재수집 판단 | 주기(본 흐름과 다른 리듬) | 없음 — 무엇을 다시 열지는 자동 판단, 결과가 G1·G4로 되돌아감 |
| G11 반응 집계·기준 조정 | 주기(발송 데이터 누적 후) | **조정 제안을 검토·승인한다 — 승인해도 자동 반영되지 않고, 승인 후 별도 작업으로 G2·G3에 반영한다**(`specs/G11` 도구 권한: G2·G3 쓰기 불가) |

---

## 5. G12 — 파이프라인 밖의 진입점

G12(질의응답)는 위 어느 리듬에도 속하지 않는다. **1~4절이 만든 산출물을 읽기 전용으로 조회해 질문에 답하는 별도 진입점**이다 — 언제든 부를 수 있고, 다른 스텝의 완료를 기다리지 않는다. `-미확정` 식별자(G7 폴백)는 기업 단위 조인에서 제외하고 별도 표시한다(G11과 동일 규칙). 상세 설계는 `specs/G12_질의응답.md`(작성 완료, 2026-08-05) 참조 — 남은 것은 그 Spec의 "확인 후 채울 것"(답변 로그 보존 기간 등)뿐이다.

---

## 6. 사람이 실제로 멈추는 지점 — 요약

전체 흐름에서 사람이 **반드시** 개입하는 지점은 둘뿐이다.

1. **G5 발송 직전 승인** — 무관용, 건너뛸 수 없음
2. **G7 회신 확인** — 이 흐름의 종점, 이후 판단은 도구 밖

부가 기능이 붙으면 셋이 늘어난다 — G9 위임 처리(선택적, 큐가 있을 때만), G10·G11 검토(주기적, 승인 성격은 다름: G10은 결과만 보고 넘어가도 되지만 G11은 제안을 실제로 승인해야 의미가 생긴다).

---

## 7. 대시보드·웹과의 관계

기업이 요구한 "대시보드"(`13S` F9·F22)는 위 산출물(G1+G2+G4, 부가 시 G3)을 한 화면에서 보는 것이다. 웹으로 구현되든 다른 형태든, 화면 자체는 새 산출물을 만들지 않으므로 별도 기능 번호를 받지 않는다(2026-08-05 확정 — 근거는 "확인 후 채울 것" 참조). **웹이라는 그릇 안에 대시보드(목록형 뷰)와 G12(대화형 질의)가 함께 담긴다 — 웹=대시보드가 아니라 웹 ⊃ (대시보드 + G12).**

## 8. 추가 사항 — 오케스트레이터에 반영할 내용

> **2026-08-05 — 반영 완료.** 오케스트레이터가 `.claude/agents/run-orchestrator.md`로 만들어졌고 아래 5개 항목이 그 정의에 반영됐다(근거 `33` D23). **이 절은 이제 대기 항목이 아니라 그 에이전트가 매 실행 참조하는 요구 목록이다** — 여기 리듬·정지점이 바뀌면 `run-orchestrator`가 이긴 것이 아니라 이 문서가 이긴다.
>
> 아래 5개가 실제로 어떤 형태로 반영됐는지: 2번(자동 재개 금지)은 **금지 문장이 아니라 「정지점에서 대기하지 않고 종료」**로 구현됐다 — 대기 루프가 없으면 타임아웃이 걸릴 자리 자체가 없다. 그 대가로 상태를 파일에 남긴다.

사용자 흐름(1~7절)이 실행 구조에 요구하는 것 — G12 자체 설계와는 별개다.

1. **오케스트레이터는 단일 선형 체인이 아니라 세 리듬을 각각 다르게 취급해야 한다.** 조사 체인(1절)은 즉시 연쇄 실행 가능하지만, 반응(3절)은 발송과 시간차가 있어 별도 트리거(바운스 도착·회신 도착)로 재개돼야 하고, 부가 확장(4절)은 주기 실행이라 온디맨드 체인에 끼워 넣으면 안 된다.
2. **G5 승인 게이트는 "자동으로 재개되지 않는 정지점"으로 구현해야 한다.** 타임아웃 등으로 오케스트레이터가 자동 진행시키면 반자동 무관용 요건(`specs/G5`)을 위반한다.
3. **G7의 되돌아가는 두 출력을 배선에서 빠뜨리면 안 된다.** 수신거부 의사 → 발송금지 목록(G4·G5가 다음 발송 전 반드시 참조), 자동응답 판정 → G6 상태 정정. 단방향 파이프로만 짜면 누락된다(`31` 3-3절 고아검사에서 실제로 한 번 누락됐던 이력).
4. **G12는 파이프라인 스텝이 아니라 별도 진입점으로 배선해야 한다.** 조사 체인·발송·반응 어느 순서에도 끼워 넣지 않는다. 읽기 전용이라 다른 스텝의 완료를 기다릴 필요가 없다.
5. **사람이 실제로 멈춰서 기다리는 지점은 두 곳뿐임을 오케스트레이터의 상태 모델에 명시적으로 표현해야 한다.** G5 승인 직전, G7 결과 확인. 부가 기능(G9·G10·G11)이 붙기 전까지는 이 둘 외에 "사람 대기" 상태를 만들 필요가 없다.
