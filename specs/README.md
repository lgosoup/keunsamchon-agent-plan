# specs — 기능별 Spec (폭포수 3단계)

기능 하나하나를 **독립된 Build Order 대상**으로 만들기 위한 Spec 모음이다. 기능 경계와 입출력은 `../docs/31_기능구조.md`에서 확정됐고(2단계), 여기서 각 기능의 **목표·범위·제약·출력 형식·성공 기준**을 정한다(3단계). Build Order(② Skill 이후)는 이 문서를 재료로 돌린다.

```
① 전체 목표 구체화        → docs/31_기능구조.md 1~2절
② 기능 단위 + 입출력 확정  → docs/31_기능구조.md 3~6절
③ 기능별 Spec            ← 여기            ★ 현재
④ 하네스 엔지니어링        → 각 Spec의 5절 Build Order
```

## 형식 — 6절 고정, 짧게 쓴다

```
## 목표        무엇을 만드는가 (한 문단)
## 맥락        누가 쓰고 왜 필요한가 + 판정 기준 카드 위치
## 범위        포함 / 제외
## 제약        지켜야 할 조건 (목록)
## 출력 형식   파일명 · 항목 · 구조
## 성공 기준   체크박스. 세거나 대조해서 예/아니오로 갈리는 것만
## 확인 후 채울 것   미확인 값과 그것을 기다리는 이유
```

- **Spec은 길어지면 안 읽힌다.** 배경 설명·개념 정의·검증 절차·문서 간 대조는 여기 쓰지 않는다.
- **성공 기준은 체크박스로, 세어서 판정 가능하게.** "품질이 좋은가"는 안 되고 "빈 칸이 0건인가"는 된다.
- **판정 문장과 임계값은 여기 쓰지 않는다** — `../기준/`의 기준 카드가 정본이다. Spec은 **항목이 존재하는가와 출력 형식**만 정한다.

## 기준 카드와 한 세트다

| | `specs/` (여기) | `../기준/` |
|---|---|---|
| 무엇 | **구조** — 무엇을 만들고 어떤 형태로 내놓는가 | **값과 문장** — 무엇을 보고 O/X를 주는가, 임계값 |
| 바뀌는 빈도 | 드물게 | **자주. 실제로 해 본 사람이 그 자리에서 고친다** |

**값을 두 곳에 적지 않는다.** 하나만 고치고 나머지는 썩는다. **운영 변수(캐파·승인 시간·발송 상한 등)는 기준 카드에도 안 두고 `../docs/50_실사용_도입설계.md`를 참조만 한다** — 기업 답 하나가 여러 기능을 동시에 흔드는 값이라 `기준/`보다 더 위에서 한 번만 관리한다(`CLAUDE.md` 5절).

**「실패 시 어떻게 되는가」 표도 이 원칙을 따른다.** 각 행을 **제어 흐름**(멈추나·계속하나·어디로 넘기나 — Spec에 쓴다)과 **판정 값**(어느 라벨·어느 등급인지의 매핑 — 기준 카드에만 쓴다) 두 조각으로 가른다. 뒤 조각까지 Spec에 옮겨 적으면 지워도 출력이 안 바뀌는 문장이 되어 `CLAUDE.md` 5절의 절차 상한 판별법을 어긴다(근거 `../docs/33_설계근거.md` D13).

→ **Build Order를 돌리는 사람은 Spec 1개 + 기준 카드 1개, 두 파일을 받는다.** 저장소 전체를 볼 필요는 없다.

## 세 번째로 G2를 쓴 이유 — 브리프 요구 ②가 검증 없이 비어 있었다

G1·G7이 병렬 조건으로 선정된 것과 달리(아래), **G2는 공백 때문에 선정했다.**

- 브리프 요구 ②(**고객 특성에 맞춘** 제안 메일)의 담당이 초기 설계의 "제안 서비스 매칭"에서 **G2 세그먼트 + G5 그룹별 문안**으로 이관됐다. 그런데 **이관된 자리에 Spec도 검증 항목도 따라오지 않았다.**
- `../docs/40_검증계획.md`를 정리하며 그 공백이 드러나 **V7(세그먼트 축)**을 신설했고, V7이 이 Spec을 기다린다.
- **G2는 앞 기능(G1)에 의존한다** — 병렬로 *실행*할 수는 없다. 다만 **Spec은 지금 쓸 수 있다**. G1이 관찰 항목을 확정했으므로 **G2가 쓸 수 있는 축의 목록이 이미 정해져 있기 때문**이다(`../기준/G2_세그먼트기준.md` 0절, 코드 정본은 `../기준/G1_기업판정기준.json`의 `관찰항목코드`, 2026-08-05 마크다운에서 이관).

**2026-07-30 — G1~G11 전 기능의 Spec 작성이 완료됐다.** G3(적합도)부터는 `90` 3절의 의존성 순서(G3 → G4 → G5 → G6·G8·G9·G10 → G11)를 따라 채웠다. G11만 발송 데이터가 없어 구조만 확정(부분 확정)이고, 나머지는 전부 확정이다. 남은 것은 각 Spec의 「확인 후 채울 것」(기업 미팅 답·실제 발송 데이터 대기)뿐이며, 다음 단계는 Build Order ② Skill이다.

## G1·G7은 왜 이 두 개였나 — 병렬 작업을 위한 선정

두 기능을 팀원이 나눠 **동시에** 진행하기 위해, **앞 기능에도 짝에도 의존하지 않는 조합**을 골랐다. `31` 3-3절 입출력 연결 목록으로 검증한 결과 **G1 + G7이 그 조건을 만족하는 유일한 조합이다.**

| 기능 | 앞 기능 의존 |
|---|---|
| **G1** | **없음** — 입력이 전부 외부(국가·타겟 조건 3종·탐색 소스). G10 되돌림은 선택적 |
| **G7** | **사실상 없음** — 주 입력이 외부(일본어 회신 메일). 이음새는 G5 발신 문안 1건뿐이며, 그것은 *대조용 참조 텍스트*라 **없어도 작업이 성립하도록** Spec에서 닫았다 |
| G2·G3·G4·G5·G6·G8·G9·G10 | **있음** — 전부 앞 기능의 출력을 필수 입력으로 받는다 |

**두 기능 사이에는 간선이 없다.** G1 → G2·G3·G4 / G7 ← 외부·G5. 서로의 산출물을 기다리지 않는다.

**대신 감수한 것**: G7은 브리프 3대 요구(탐색·목록화 / 맞춤 메일 / 반자동)를 직접 담당하지 않는다. 그 정당성은 **기업이 직접 말한 요구**(회신 수신 / *"접촉이 성립되면 대응이 필요하다"*)에서 나오며, 근거는 `G7_회신해석정리.md` 0-1절에 적어 두었다. 브리프 요구 ②·③의 본체인 G2·G5는 **다음 차례**다.

`G1_대상기업발굴.md` 출력 형식이 정한 자리다. **2026-08-03부터 `후보목록.md` 단일 파일**(기업 1곳 = 섹션 1개, append) 형식이다. **이 디렉터리는 Spec이 아니라 Spec을 실행한 결과물**이므로 위 6절 형식을 따르지 않고 Spec이 정한 관찰층·규칙층 구조를 그대로 쓴다.

## `segments/` — G2 실제 산출물 (2026-08-05 신설)

`G2_세그먼트화.md` 출력 형식이 정한 자리다. **세그먼트 정의 1벌 = 파일 1개**(`SEG-{축코드}-v{버전}.md`)이며, `candidates/`와 마찬가지로 **Spec이 아니라 Spec을 실행한 결과물**이라 위 6절 형식을 따르지 않는다.

- **축을 바꾸면 새 파일이고 이전 파일은 지우지 않는다.** 축이 그대로인 채 관찰값만 채워져 배정이 바뀌면 새 버전을 만들지 않고 같은 파일의 2절을 갱신한다 — 어느 쪽인지의 판정은 `G2_세그먼트화.md` 「제약」이 정본이다.
- **축코드는 `../기준/G2_세그먼트기준.md` 1절이 이름 붙인 축의 식별자다**(안 A → `A`). 카드에 없는 축코드는 만들지 않는다. **이것은 잠정 처리이며 `{축코드}`의 정의는 아직 없다** — 잠정 권고가 "A 주축 + 커지면 그 안에서만 B로 쪼갬"이라 **A와 B가 함께 쓰인 회차의 표기가 비어 있다**(`../docs/90_미결정과_리스크.md` 3절 ①).

## `scores/` — G3 실제 산출물 (2026-08-05 신설)

`G3_적합도평가.md` 출력 형식이 정한 자리다. **기업 1곳 = 채점 파일 1개**(`{기업식별자}.md`) + **정렬 1회 = 순위표 1개**(`순위표-{작성일}.md`)이며, `candidates/`·`segments/`와 마찬가지로 **Spec이 아니라 Spec을 실행한 결과물**이라 위 6절 형식을 따르지 않는다.

## 발송 도메인 준비 — G5 구현 전 필수 (2026-08-03)

**G5(제안메일제작발송)를 실제로 돌리기 전에, 발송에 쓸 이메일 주소를 회사의 원래 업무 메일과 분리해야 한다.** 이유는 `../docs/50_실사용_도입설계.md` 1-1절 참조 — 자동 발송 메일이 많아지면 수신 서버가 그 주소를 스팸으로 판단할 수 있고, 회사 메인 도메인이 그렇게 찍히면 원래 업무 메일(동대문 거래처 등)까지 같이 막힌다.

**해야 할 일 (일회성 설정, 코드로 자동화하지 않는다)**:
1. 회사 메인 도메인과 분리된 서브도메인 또는 별도 주소를 만든다(`12` Q15 답으로 확정).
2. 그 주소를 실제 발송 도구(메일 발송 API·서비스, 예상되는 연결 방식은 MCP)에 등록·연결한다 — 이 등록·연결은 Build Order ③(하네스 엔지니어링) 단계에서 G5 실행체를 만들 때 함께 한다.
3. 하루 최대 발송 건수 초기값과 이후 조정은 코드가 아니라 `../docs/50_실사용_도입설계.md` 1-1절의 값을 사람이 직접 늘려가며 관리한다.

이 절차는 Spec(구조)도 기준 카드(판정 값)도 아니라서 별도 문서(`docs/`)로 보내기도 애매한, **한 번만 하면 되는 설정 안내**다 — 그래서 README(여기)에 둔다.

## 여기에 Spec을 추가할 때

1. **성공 기준을 가장 먼저 쓴다.** 기준이 구체적이어야 목표를 정의할 수 있고, 목표가 정의돼야 결과를 대조해 검증할 수 있다. 순서를 뒤집으면 **기준이 결과에 맞춰진다.**
2. **성공 기준을 (a) 지금 확정 / (b) 대기로 가른다.** 미확인 값이 있다고 전체를 비워 두면 Build Order ①이 영구히 미완이 되고, 숫자를 지어내면 근거 없는 임계값을 만든다.
3. **활용 방식(Chatbot / Workflow / Agent)을 선언한다.** 이걸 정하지 않으면 실패 경로가 설계에서 빠진다. **선언만으로 끝내지 말고 실패 시 무엇을 하는지 함께 적는다** — 그게 이 선언의 실질이다.
4. **Subagent 4경계**(입력 형식 / 출력 형식 / 도구 권한 / 독립 컨텍스트)를 정한다. 넷이 정해지지 않은 것은 Subagent가 아니다. **도구 권한 경계가 반자동·부분자동 원칙을 물리적으로 강제하는 주된 장치다**(예: G11의 G2·G3 쓰기 권한 없음, `run-orchestrator`의 발송 권한 없음, `g5-문안제작`·`g5-번역검증`의 쓰기 권한 없음) — 경계가 없으면 실행체가 스스로 권한 밖 행동을 할 수 있어도 막을 방법이 없다. **단 「유일한」은 아니다 — G5가 반례다.** `specs/G5` 4경계는 *"메일 발송 도구는 **접근 권한이 있으나** 사람 승인이 기록된 건에만 행사한다"*로 **권한을 빼지 않는 유일한 기능**이고, 거기서 반자동을 지키는 것은 권한 부재가 아니라 **실행 구조**(승인 정지점에서 종료 = 대기 루프가 없어 자동 재개가 불가능)다. 어느 쪽으로 강제되는지를 기능마다 구분해 적는다. (2026-08-03 — 이 근거를 사전 검증 V1-b 계열로 들었으나 그 검증 자체가 `31` 1-5절과 부딪혀 폐기됐다. `91` 2026-08-03 항목)
5. **출력이 나중에 집계·학습에 쓰이는지 확인한다.** `../docs/31_기능구조.md` 3-3절 연결 목록에서 **이 기능의 출력을 받는 곳을 전부 확인**하고, 그들이 요구하는 항목을 출력에 남긴다. **기록하지 않은 데이터는 소급해서 만들 수 없다** — 특히 **G11(반응 집계·기준 조정)**은 발송 데이터가 쌓인 뒤에야 돌지만, 그때 필요한 항목은 **발송 시점에 남겨야** 한다. G5가 세그먼트·인용 근거를 안 남기면 세그먼트별 반응 집계는 영구히 불가능하다.
6. **왜 이 Spec을 지금 만들었는지 `../docs/91_진행로그.md`에 한 줄 남긴다.**
